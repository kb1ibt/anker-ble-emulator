# anker-ble-emulator design

An emulated Anker Solix BLE device (the comms module and the device MCU behind it) for testing BLE clients. It plugs in under [bleak](https://github.com/hbldh/bleak) as a client backend, so the client's real stack (bleak, bleak-retry-connector, the client library) runs unchanged above it. There is no radio and no OS Bluetooth stack.

## Layers

| layer    | module        | role                                                                                                                                                                                                                                                                                                                                                              |
| -------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| frame    | `frame.py`    | `ff09` frame codec: length, pattern, cmd, payload, XOR checksum; fragmenting and reassembly at the fragment cap                                                                                                                                                                                                                                                   |
| fields   | `tlv.py`      | negotiation TLVs (`tag len value`, tags from `a1`)                                                                                                                                                                                                                                                                                                                |
| messages | `messages.py` | one typed layout per negotiation reply (`0801`, `0803`, `0829`, `0821`, `0827 09`, status-only); request fields typed per msgtype (`0003` MTU u16, `0005` method, `0022` time u32 / offset int32 / TZ, `0027` token, `002b` time u32 / account / zone)                                                                                                                                              |
| crypto   | `crypto.py`   | static GCM, session GCM, session CBC, P-256 device key pair                                                                                                                                                                                                                                                                                                       |
| module   | `module.py`   | the comms module: negotiation handlers, link state, authorization policy, the authorize timer, the relay to and from the MCU                                                                                                                                                                                                                                      |
| MCU      | `mcu.py`      | `McuScript`: recorded cleartext replies by message type, and pushes; for a command the product's layout handles and no recording answers, an ack whose status is the layout's check. Its starting state is every named value the recordings carry: the recorded `0490`'s fields (the 0.1 % `pack_soc` / `sub_package_pack_soc`, the bus slots), then the replies, the pushes and the cloud-only pushes over them, all over the layout's hidden-input defaults (`LayoutProtocol.defaults`) |
| layouts  | `layouts.py`  | `LayoutProtocol`, what `McuScript` and `EmulatedDevice` need from a product's layout; `LayoutError`; the TLV type bytes; the clock's state names (`RTC`, `EPOCH`, `CLOCK`, `RTC_SECOND_AT`); shared field codecs (`ui`, `ScalarField` and its constructors) |
| parameters | `parameters.py` | `Parameter` / `Parameters`, SolixBLE's TLV shape (optional type byte, optional status prefix); the layout bases `TableLayout` (a recorded device's telemetry, named by per-message tables of `FieldSpec`s and `FieldGroup`s), `ScalarFieldLayout` (flat single-value fields) and `CommandDispatchLayout` (per-command validators), and the table helpers `leaf_zeros`, `struct_zeros`, `one_field` and `flat`; the clock stamp (`clock_field`, `stamp_clock`); `validators.py` holds `OptionsValidator` |
| products | `products.py` | `Product` part numbers with their SolixBLE class and anker-solix-api category; `Transport`, `Outer`, `Path`                                                                                                                                                                                                                                                       |
| devices  | `devices/`    | `base.py`: `EmulatedDevice`, `ProductDevice` (a subclass names only its `PRODUCT`), `Profile`, `Advert`; one module per product holding its profile and subclass; `solix_c_gen2.py`: the display board's command set and codecs (the C Gen 2 line, and the S2000's shared tags); `prime.py`: what the A2345 and A91B2 share; recorded frames in `devices/data/`                                                                                                                                                           |
| backend  | `backend.py`  | `EmulatedBleakBackend(BaseBleakClient)`: GATT services from bleak's own classes (service `8c850001`, write `8c850002`, notify `8c850003`; `ff09` is only advertised), writes into the module, notifications out                                                                                                                                                   |
| testing  | `testing.py`  | `EmulatedConnection`: patches a client library's `establish_connection` (SolixBLE's by default) to return a real connected `BleakClient` on the emulator; keeps SolixBLE `MockDevice`'s names (`expect_ordered` as an optional write assertion, `refuse_after`, `disconnect`, `send_data`, `new_connection_error`, `allow_connect`, `check_assertions`, `writes`) |

The C Gen 2 models run one MainMcu build (firmware/mainmcu.md "Model and device identity"), so the emulator answers the same commands on all four: `4100` → `c900` + `c421`; `4057` → `4857`; `405e` → `485e` + `c421`; `4063` → `4863`; `4089` → `4889`; `4090`/`4091`/`4092` → `4890`/`4891`/`4892` + `c421`; `4101`–`4104` → `4901`–`4904` + `c421`. Frames that name the unit (`0421`, `0900`, `0490`, `0425`) come from each model's own recording, PN strings as recorded (the A1785's say `A1783`, firmware/mainmcu.md). The identity-free replies are shared (`solix_c_gen2.json`).

C Gen 2 state that follows the request rather than a setting:

- `4090` stores the plan as a1783-control.md's `4090` row and "TOU (`4090`)" describe; an `a7` past 18 bytes, the stack overrun, is acked and changes nothing. The active period (`d9[0]`, that section's conditions) and the Peak / Mid-Peak hold (its "What an active period does" table) show only in `mqtt_frame`, since condition 2 needs the cloud and the emulator's cloud has no BLE link. The hold is applied when the frame is built: AC input 0 W in `a6` and `a7`, the bus holder's `a5[1]` / `c0[24]` and a charging `a3[0]` as a1783-telemetry.md "Flow state" reads them under the hold, the SoC being c490 `pack_soc` (the recorded `0490`'s unless set). When a holding record ends, AC input ramps back over the recorded end of 2026-10-21 (a1783-control.md "TOU (`4090`)", by the device clock), scaled to the charge waiting: 0 W until 6 s, the recorded samples between, the full charge from 13 s. Its own reading: a record that wasn't holding ends with no ramp, one running into another held record keeps holding, and a clock set re-times it. `0503` publishes only while a period is active.
- `4100` sets `a3[10:12]` `silent_recharge_power` as a1783-control.md's `a3` `[10..11]` row gives it (1000 for the app's request, else 600); the v1.1.2.6 recordings (A1763, A1765) keep their 10-byte `a3`.
- Every request passes `fid0f_app_id_time_store` (a1783-control.md "Session frames", a1783-telemetry.md `fd`): a request's `fd` goes into the telemetry's, one without leaves it.

C Gen 2 mains and Battery-Only Power (`a4[31]` and `a7[3]` as a1783-control.md's `a4` `[31]` row and "`a4[31]` witnesses" give them), timed from a change of `ac_input_status` or `ac_input_disable_switch`. The power stage's AC-input flag, which the auto-off, the accept and the alert key on, is the hidden `ac_input_flag`, settling on `a7[3]` after the power stage's report and the 100 ms debounce. The report and the charge ramp are the power stage's, so the emulator takes them from the witnesses' bench runs:

- Mains lost: AC input reads 0 W at once and the flag drops after the power stage's loss report plus the debounce. The report is the DSP's, recorded at 0-1 s, so it is the hidden `power_stage_loss_report`, set per replay (unset 0 s, the flag 0.1 s on). The auto-off then reads state 2 whatever Battery-Only Power's state, clearing it if it was on, and wakes the screen (`a4[21]` 1). Battery-Only Power switched on with the flag already down reads state 2 at once, the same evaluation clearing it (no witness frame).
- Off-grid alert: the 5-tick commit of a1783-control.md "`a4[31]` witnesses", its Alert bullet (hidden `ac_input_flag_committed`), a tick that reads the committed flag resetting the count. Its 1 s timer runs free from boot, so the first counted tick's phase, 0-1 s after the flag changes, is free per the firmware: the hidden `alert_tick_phase`, set per replay from its run (unset 0, the change itself, so a drop commits 4 s after the flag). It places the run's first change on the grid, the hidden `alert_tick_grid`, and every later change counts from that grid's next tick. A flag change due at the 5th tick's own instant counts first, so that tick reads it back and commits nothing. The committed drop's `0425` 0x59 goes out on the A1783 and A1785 only, the models whose recordings carry a `0425`.
- Mains back: `a7[3]` 1; the flag returns after the power stage's return report plus the debounce, and a state 2 clears to 0 then (the accept). The report is the DSP's, recorded at 2-3 s by `fe`, so it is free per the recordings: the hidden `power_stage_return_report`, set per replay (unset 2.9 s, the accept 3.0 s on).
- AC charging: the 7 s one-shot counts from the branch's first 1 s tick, 0-1 s after the accept on the timer's free-running phase: the hidden `inverter_tick_phase`, set per replay from its run (the 2026-10-31 14:55 run's enable fell 7.2-8.2 s after its accept). Unset it is 0, the enable 7 s after the accept, the emulator's choice: no run settles 7 against 8. As with the alert, the run's first accept places the grid (the hidden `inverter_tick_grid`) every later one counts on. The power stage's ready bit enables it sooner, on the first tick at or after it: the hidden `power_stage_ready_report`, the seconds after the accept it sets, per replay (unset, none before the one-shot). The 2026-10-26 run is the ready bit's: its last 0 W frame came 4.04 s after its accept frame and 118 W at 6.97 s, under the one-shot's 7 s. On whole-second ticks that window allows an enable at 5 or 6 s; its replay picks 6 s, a value inside the recorded window. Then the ramp: 118 W at the enable, the emulator's deterministic pick from the recorded 38-155 W first steps after a mains return (a1783-control.md "`a4[31]` witnesses"), and the full charge 5 s on. The intermediate steps aren't modeled.
- The full AC charge follows the charge request (a1783-telemetry.md "AC charge request", `chg_src1_ac_limit_calc`): `maxInputPower` (`a3[4:6]` `max_input_power`, 1800 W here) less the AC-out draw (`a7[1:3]` `ac_output_power`), capped at the AC limit (`a4[4:6]` `ac_recharge_power`), + 10 W, and held to the recorded full-charge band whenever the request reaches it, as at an 1800 W limit (a1783-telemetry.md "AC charge request", its text and recorded table). The band is a recording, not a firmware value, so it is the hidden `full_charge_band_power`, set per replay from its run; unset, 1 583 W on the limit's path (the 1800 W limit's median and mode, 2026-10-31 15:15-15:39) and 1 643 W with the limit skipped (the plan windows' mode). The recorded ~20 W settle of AC in after the DC input came on isn't modeled. AC input is that plus the AC out, up to the inlet's `maxInputPower` + 33 W. The inlet and the inverter output are separate ratings (a1783-telemetry.md ratings), so the outlets' draw beyond what AC input supplies comes from the on-bus pack, whose current and flow state follow from the port powers below. DC-side loads aren't subtracted. The +10 W is the 1200 W limit's recorded mode (a1783-telemetry.md "AC charge request", with the modes at the other limits). The limit is stored as sent, any u16 (a1783-control.md `4101 a4`): above `maxInputPower` it is inert, and 0 requests no charge (AC in reads only the AC out). The pass-through's recorded limit + out + about 24 W (1 279-1 283 W at 56-57 W out, one case) isn't modeled: AC in adds the AC out to the charge. The request never goes negative (step 1 there): with charge source 2 able to charge (the hidden `charge_source_2_can_charge`, clear unless set) it is 0 once AC out reaches the ceiling, otherwise it holds to the floor from the on-bus pack's voltage (`.15.3`, pack field 0xf, which the headroom reads too). At 1 750 W out on an 1800 W unit at 53.5 V the floor makes AC in 1 824 W (source 2: 1 810 W); at 1 900 W or 4 000 W out AC in reads the 1 833 W cap either way, and the pack discharges the rest. A change of the limit, `maxInputPower` or AC out moves a charge at the full rate to the new request at once (`chg_src1_ac_limit_calc` re-runs each pass, a1783-control.md "TOU (`4090`)"; its period isn't documented); an AC input set by name off the full charge stays.
- With Ultrafast on (`a4[20]` `super_fast_charge_status`) or a backup window running (the Fast Charging Plan or Storm Guard, `tou_setting_system_status` ≠ 0), the firmware skips the limit and requests `maxInputPower` less AC out. The charge holds to the recorded band: min(`maxInputPower` − AC out, the band), no +10 W, and AC input adds the AC out. The band unset is 1 643 W here, the mode of the plan windows' 1 553-1 673 W (a1783-telemetry.md "AC charge request"). On the C1000 Gen 2 it holds to its 1 600 W UltraFast rating too: 1 600 W at 1800 W `maxInputPower`. Ultrafast on, a window starting or one ending moves a charge at the full rate the same way.
- One MainMcu build serves all four models (PiField firmware/mainmcu.md: the factory record's model index changes only names and PN strings), so the decoded rules (the charge request and its floor, `maxInputPower`, Ultrafast skipping the limit, `port_power_out_sum`) follow the build, not the model: they hold from v1.2.1.1, the first decoded build (the A1785 records v1.2.1.1, the A1783 v1.2.1.6). Of them, `maxInputPower`'s values and its AC-in ceiling key on the `0421` `f9` `mcu_version`. The A1763 / A1765 record v1.1.2.6, undecoded, with `maxInputPower` 1200 W; the emulator runs the same charge request there, so its UltraFast charge stops at the 1 200 W the request leaves. The AC-input disable mode (`4101 ab`, its mains auto-off and screen wake, Battery-Only Power blocking TOU) and the off-grid alert (`4103 b0`, the 0x59) come with v1.2.1.6, keyed on `mcu_version`. v1.2.1.1 has none of them (firmware/mainmcu.md "build diff": no `ac_input_autooff_eval` or `offgrid_alert_poll_tick`), and a `4101 ab` / `4103 b0` there is acked and sets nothing (a1783-control.md `4101 ab` and `4103 b0` rows: its handlers read `a2`–`a7` / `a2`–`ab` only). The undecoded v1.1.2.6 is assumed the same.
- On the C2000 chassis (A1783, A1785) on a decoded build, the AC charge's current holds to the on-bus pack's headroom (a1783-telemetry.md "AC charge request" step 3, `ac_charge_current_headroom`): MainBMS's allowed charge current (`+0xe0`, `charge_current_limit_calc`: 58.0 A, at most 245 760 / the pack voltage in 0.1 V, i.e. 2 457.6 W, and 40.0 A while its TOU bit is set) less the current the other sources hold (`chg_source_current_sum`, taken as the DC input's), at the on-bus pack's voltage (`.15.3`). So the AC charge gives way first and DC stays as set: UltraFast's 1 643 W with 800 W of solar reads 45.7 A at 53.5 V, under both caps; at 41.0 V the 58.0 A cap leaves 1 578 W. With the charge held to the band, the 2 457.6 W power cap can't bind below 58 A: even at the 16S top of 58.4 V it is 2 452 W, over the band's 1 643 W plus the XT-60i's 800 W; TOU's 40.0 A can. The derived pack current (the net port flow over the pack voltage) lands at the cap with no DC-side load; DC-side loads aren't subtracted, as in the request. The 58.0 A rides the C2000's state read-only (`pack_charge_current_limit`); the C1000 Gen 2's BMS isn't decoded, so it has none. A change of the DC input or a pack voltage moves a full charge to the new headroom at once. The power cap's division truncates (`0x3c000` / V, masked `0xffff`), and a pack reading 0 V drops only that term (firmware/pack-telemetry.md `+0xe0`): the 58.0 A and the TOU's 40.0 A still apply. The BP2000 runs the same MainBMS image, so on the bus it holds to the same cap at its own voltage.
- MainBMS's TOU bit (bit 7 of `0x20000a18`, the hidden `tou_status_bit`) is MainMcu's op-0x006 status bit `0x80`: a TOU period active (`tou_active_period_get` ≠ 0) and no backup window running (firmware/mainbms-control-fsms.md "The op-0x006 byte"). MainMcu sends the byte every 500 ms; as a modeling choice, which keeps long test clocks cheap, the emulator refreshes the bit every 10 s and 0.5 s after a change of what it reads (the plan, the TOU mode, mains, Battery-Only Power, the MainMcu version, the alternator, the backup window, the clock). A period is active only on the cloud, so over BLE the bit stays clear. An Off-Peak period on the cloud holds UltraFast with 800 W of solar at 53.5 V to 1 340 W, 40.0 A. A full charge follows the bit's change. Its other setter (MainBMS `canrx_cmd_11`, CAN `0x0042` sub `0x11`, the pack-switch code) and the other limits (2.0 A under a 2000 mV cell, 0 at 58.0 °C, the gate's 0 at 100.0 % SoC, and the temperature table `charge_current_limit_calc` takes first: the lower of two lookups at the tracked max and min temperature, 6.0 A at 2.0–5.0 °C up to 58.0 A at 20–60 °C and 0 outside, firmware/pack-telemetry.md `+0xe0`) aren't modeled in the charge current, since no value carries the pack temperatures it reads. A `total_input_power` set alone over the cap reads as set: AC takes the charge it would with no DC beside it, so a total past the cap leaves the pack over it.
- Battery-Only on with mains in: `a7[3]` 2 and AC input 0 W at once, and while it stays on every frame shows AC input 0 W and no charging state only AC could cause. Off with mains in: `a7[3]` 1 at once and AC charging 7.5 s on, the median of the witnesses' 6 s and 9 s restarts, by the same ramp; its 118 W first step is the mains return's, the two restarts having recorded 341 W and 131 W (a1783-control.md "`a4[31]` witnesses"). The two frames of `a4[31]` `00` between the `02`s on 2026-10-26 aren't modeled.
- AC charging goes into the pack below its cap (`a4[23]`), by the ramp above: the charge shows on the bus holder's flow (the 2026-10-23 06:03:00 run, the expansion already holding the bus); a main holding the bus at its cap charges until the charge-cap latch moves the charge to an attached expansion below its own (main → `0x12`, `c0[24]` 2; pack selection below); with every pack at its cap, no AC input.
- A name the triggering change sets itself stays as set; each step acts only if the state it needs still holds when it comes due.

C Gen 2 car socket and the USB-C ports: an edge of `car_charge1_output_status` (`b2[0]`), from a `4102 a2` or `set_values`, re-attaches the USB-C ports as a1783-control.md "`4102 a2` and the USB-C ports" records.

- The device is two hidden inputs per port, carried in no field and with no app name: `<port>_device_plugged` (0/1) and `<port>_device_power` (W). Unset, `pd1` holds the A1783 recording's 86 W load and `pd2`/`pd3` none (on the C1000 Gen 2 `pd1` none too); a port without a device stays 0.
- The emulator's timing, the medians of the collector logs' clusters: `[0]` 1 at 1 s after the edge and the device's power 3 s after that, with the output total and the port flow following. A port detached again before then draws nothing, and a port power the edge's own call sets stands with no power step after it.

C Gen 2 `0403` events: MainMcu's push as a1783-control.md "`0403` push" gives it, built on every model since no `0403` is recorded.

- Output timers: `ac_timer_value` (`a4[0..3]`) and `car_charger_timer_value` (`a4[8..11]`) run as that section's output-timer bullet gives them; the car socket going off at 0 is a socket edge (above).
- Low SoC: `0x52` / `0x50` follow that section's table on `battery_level`, an evaluation each 500 ms and one more per block-1 reply with an expansion attached (`sub_package_connection_status`).

C Gen 2 screen (`a4[21]` `screen_switch`, `a4[15..16]` `screen_off_time`; a1783-control.md "Screen wake", a1783-operation.md's 05:46:21 wake): a wake turns it on and re-arms the timeout. Wakes: `4103 a2` 1; a `4103 a3` brightness or `a9` language write (from `4103` or `set_values`; `4051`'s restore doesn't wake); the car socket (`4102 a2`) or the AC output (`4101 a2`) turned on (the state table's on rows, screen 1; its off rows, 0xa, only re-arm the timeout of a lit screen); DC-input presence (`a8[0]` `pv1_charge_status` 0 → 1); and the mains auto-off, with Battery-Only Power on or off. Brightness 0 turns the screen off instead. A `4103 a4` write re-arms the timeout only while the screen is on. A refused turn-on wakes too (the fault-match rows); refusals aren't modeled. The other setters and the `40xx` ops leave it. A wake runs at once, so the command's own reply shows the screen on.

C Gen 2 backup plans: `405e` writes its tables as a1783-control.md "`005e` means different things across families" gives them, and the window events are its "`0425` event report" table. Table 1 is `manual_backup_switch` with `manual_backup_start_time` / `_end_time` in the `d9` tail, table 2 `auto_backup_switch` with the hidden `auto_backup_plans` (3 × u32 start / end UTC, empty unset; no field carries it). How the emulator runs the window pass:

- It runs 100 ms after any change of a plan, a switch or the clock, and at each window's start and end, every 100 ms within a second of one, rather than every 100 ms throughout. A running window keeps going until it ends or its switch goes off; with none running, Storm Guard is chosen before the plan.
- A start sets `d9`'s type and active pair. While a window runs MainMcu sends the BMS a 100 % cap (fsms "Current-limit sources"), so the main's 0xc clears and, the cap latch set, expansion → `0x11` moves the charge and the bus to the main (`c0[24]` 0, `a5[1]` 2, `a3[0]` following; the 2026-10-06 21:00:04 run in "Telemetry from local state"); at 100.0 % its charge allowance is 0 and main → `0x12` hands the charge back 300 steps on (21:11:30). The `0425`s go out on the A1783 and A1785 only, whose recordings carry one; the others' `d9` tail moves all the same.

C Gen 2 flow state (a1783-telemetry.md "Flow state"), filled from the port powers, the pack currents and the bus holder. A flow-state name set by name (`charge_discharge_status`, `sub_package_status`, `work_status`, `on_bus_pack_status`, and `total_input_power` set with either input) reads as set until its inputs next change: the follow below skips a status set by name since the change of the pack currents that queued it (the hidden `flow_statuses_held`, which the next such change starts over). The Battery-Only / Peak hold still applies to a by-name `a5[1]` / `c0[24]`, since it reshapes the published frame:

- The port-flow code (`a5[1]` / `c0[24]`) follows that section's table at once; with no `c0` (the C1000 Gen 2) the main always holds the bus.
- The pack currents (`.14.29` / `.14#1.29`): the bus holder carries the net port flow over its voltage (`.15.3` / `.15#1.3`) in its current source's 10 mA, 10 mA = (Σ in − Σ out) × 1000 / V; the other pack carries 0. A current given in the same change, by name or drawn, stays.
- `a3[0]` `work_status` and `.23.7` `on_bus_pack_status` follow that section's ±0.3 A test, settled 2 s after a change of the settled value (its 20 samples). Battery-Only Power switched on with mains in leaves `a3[0]` charging for its lag (the 19:39:18 witness, a1783-control.md "`a4[31]` witnesses"); the Peak hold, built per frame, shows it idle at once.
- `.23.2` and `.23.4` (`port_power_out_sum`, `port_power_in_sum`; firmware/c490-schema.md) come from the `0421` state, the same sums `a6[0:2]` and Σ input read: one value each, where the recordings' pairs within 5 s agree in 5 432 / 6 395 of 6 464 (at most 86 / 20 W apart).
- `total_output_power` (`a6[0:2]`, `.23.2`) is the port outputs' sum (a1783-telemetry.md `a6`, `port_power_out_sum`). A change of any port output moves it by that change, as a USB-C device's power does, so AC out alone moves it and the on-bus pack discharges what AC in doesn't supply. A total set by name, alone or with ports, must equal the ports' sum after the change.
- `total_input_power` set alone splits: AC in takes the AC charge the request allows (0 W without mains or with Battery-Only on), at most the total, and DC in (`pv1_input_power`) the rest, so 1 950 W at the 1300 W limit reads 1 310 W AC and 640 W DC. `maxInputPower` bounds only the AC request, so AC + solar can pass it (a1783-telemetry.md ratings: AC + solar 2 600 W). Set with one input, the other is the rest; a total under that input is refused. Set with both, it reads as set.
- The +10 W over the limit is the split's default. AC in set by name is taken as given up to the ceiling below, since the overshoot varies on the unit (a1783-telemetry.md "AC charge request").
- AC in set by name holds to `maxInputPower` + 33 W whatever the limit, the same ceiling the charge request's AC in stops at. On a decoded build, `maxInputPower` is refused at any value `max_input_power_get` doesn't give (1500, 1800 or 2300 W; a1783-telemetry.md `a3` [4:6] row; the variant and country it derives them from aren't modeled, so any of the three sets); on v1.1.2.6 any value sets. More AC in, or a `maxInputPower` lowered under it, is refused. The inlet's 3 h / 12 A continuous rating (a1783-telemetry.md ratings) isn't modeled.
- The C1000 Gen 2 (A1763, A1765) holds to its own ratings (a1783-telemetry.md ratings) over the build's: the AC limit to its AC charging rating, and the charge (AC in less AC out) to that rating + 33 W, or UltraFast's + 33 W while the limit is skipped; AC in to its bypass rating + 33 W, on a decoded build the lower of that and `maxInputPower` + 33 W. On the recorded v1.1.2.6 the bypass alone bounds AC in, so AC out passes through above the 1200 W `maxInputPower`. The bypass and UltraFast ratings ride the state read-only (`ac_bypass_power`, `ultrafast_charge_power`) for the charge request's steps.
- AC out (`ac_output_power`) holds to the model's AC output peak (a1783-telemetry.md ratings); the overload trip time isn't modeled.
- AC out reads 0 W unless AC output is on (a1783-telemetry.md `a7` [1:3], `tlv_a7_AcData`). Switching `ac_output_status` off, by `set_values`, `4101 a2 00` or the AC timer running out, puts it at 0 W, and `a6[0:2]`, the flow and a full AC charge's pass-through follow; switched back on, it stays 0 W until set or drawn. AC out set over 0 W with the output off is refused with `TypeError` and sets nothing. A draw matches the status, so it never pairs the two.
- The DC input holds to the XT-60i's rating on the C2000 chassis whatever `dc_input_source` says, since solar, the car cable and the alternator share it, and to the C1000 Gen 2's solar rating (a1783-telemetry.md ratings). The solar current limits aren't modeled.
- With `dc_input_source` the car socket, the car cable holds ~8.1–8.2 A, so its watts follow the socket's voltage (a1783-telemetry.md ratings "Car input"), on every C Gen 2 model (the C1000 Gen 2's ratings list no car input; the cable is the same). `.23.6` `dc_input_voltage` (0.01 V) follows `pv1_input_power`: while charging, the power over the hidden per-run `car_cable_current` (0.01 A, 810–820; unset 817, the 2026-10-31 15:19 frame's 125 W at 15.30 V, and 814 gives the 17:07 frame's 119 W at 14.62 V); at 0 W with voltage on the input (`a8[0]` 1), the socket at rest, 16.9 V (the 2026-10-31 c490 posts read 16.89–16.96 V from 18:01 EDT; the 16.38 V just after the charge ended at 17:16 is set by name). With no voltage on the input, or on solar, `.23.6` reads as recorded, a car voltage going back to the recording as the cable leaves. A `.23.6` set by name is taken and holds until the power, the presence, the source or the current next changes. A power past 8.2 A at a `.23.6` set with it, or one needing more than the XT-60i's 60 V, is refused with `TypeError` and sets nothing. There's no 100 W cap: 119–129 W is the cable at a 15 V-class socket. Not modeled: a charge under the cable's current, such as the 15:46 EDT post's 69 W at 16.74 V (about 4.1 A), which the fixed current would put at 8.45 V; set its `.23.6` by name.
- The output ports hold to their ratings by the app's port name, PD1-PD3 being USB-C1-C3 (a1783-telemetry.md ratings, shared pairs included). A port's load is its power, or its plugged USB-C device's where higher, since the device draws it once attached. The C1000's PD1 holds no device unless set: the A1783 recording's 86 W load is over its shared 20 W. The C1000 has no USB-C3, so its `pd3` holds to 0 W, as both recordings read.
- Each of these refusals raises `TypeError` and sets nothing.
- Each pack's battery level (`battery_level`, `a5[2]` = `a6[8]` = `.23.1`, and the expansion's) is floor(SoC / 10) of its `pack_soc` / `sub_package_pack_soc` (a1783-telemetry.md `.23.1`). A level set alone puts the SoC at its whole percent; set together, each stays as set. The lag or lead of 1 at a whole-percent boundary isn't modeled.
- The derivation runs on every change of values (`set_values`, a draw, a command) and in every timed step that moves the port powers or the bus, before pack selection reads it.

C Gen 2 versions that drop out: `f9[12:16]` `inv_version` and `f9[4:8]` `sub_mcu_version` read 0 as a1783-telemetry.md "Versions (`f9`)" gives it. The emulator's figures: `inv_version` shows 1 s after the ACDC stage comes on (mains in, `a7[3]` 1 or 2, or AC output on) and reads 0 from 1 s after mains goes, or 49 s after AC output switches off with no mains, the stage back before then keeping it; `sub_mcu_version`'s 1 s of 0 once a minute runs on a timer from the MCU's start, its phase the emulator's. The hidden `_inv_version` / `_sub_mcu_version` hold the version while it reads 0, and the `4866` log chunk's header reads the same values (both `version_get`). Not modeled: the other subMCU zeroings (idle sleep, 7 failed DSP reads, power-up).

C Gen 2 pack selection, with an expansion attached, follows MainBMS `pack_select_eval` as firmware/mainbms-control-fsms.md "Pack selection" gives it: its switch table (rows named here by their switch code), "Latches", "ALT byte +9", "Charge-cap latch counters" and "Discharge-latch drop baselines"; a1783-operation.md "Observed handovers" for the recorded handovers. Each rule is re-checked on every change of values. How the emulator holds it:

- State: the hidden `pack_on_bus` (1 main, 2 expansion; unset, the expansion, as recorded), `charge_cap_latch`, `charge_cap_latch_charge_count` / `_since` (the 1 s charging count), `charge_cap_latch_spent`, `charge_cap_latch_pulsing`, `charge_cap_latch_clear_count` / `_since` (the 15 s clear count), `bus_switched_at` (the device clock of the last switch, for `0x20000b3a`'s 300 steps), `discharge_latch`, `discharge_latch_from`, `high_soc_status` (the main's 0xc), `sub_package_low_soc_status` (the BP2000's 0xd), `alternator_byte_9` (ALT +9, default 0) and `sub_package_path_hold` (the expansion BMS's `raw+0x95`, clear unless set; it blocks both main → expansion rows). The SoCs are the 0.1 % `pack_soc` / `sub_package_pack_soc`. "Charging" / "discharge" is the on-bus pack's current at ±0.3 A, not its port flow, except for the discharge latch, which reads the packs' summed current at 0.1 A. Each switch shows in the flow state (above), and `.15.5` / `.15.6` read (8, 9) for the new holder, (3, 9) when it is quiet at or above its cap and (3, 3) for the other (a1783-operation.md "`.15.5` against the limits").
- Allowances: each node sends its own gated limits, record 1 being the host's copy of its own and record 2 the BP2000's CAN `0x0454` (fsms "Current-limit sources"). The cap they work to is `max_soc`, 100 % while a backup window runs (MAIN op `0x015`). The main's charge allowance (+0xe0) is 0 while its 0xc is set or its SoC is 100.0 % (a1783-telemetry.md "Top-off hysteresis": 0xc sets above the set threshold and clears below the clear one, held between); its discharge allowance is 600 (faults aren't modeled). The BP2000's discharge allowance is 0 while its own 0xd is set: under `min_soc` + 0.9 %, cleared above it, held at it (fsms "Pack selection", the floor-band paragraphs); it shows as bit 13, 0x2000, of the expansion's `.15#1.8` / `.9`. That held the 2026-09-03 expansion in its band off the bus while the main fell 96 → 85 % (a1783-operation.md "Expansion to its floor, 2026-09-03"). Each node's `soc_status_eval` moves 0xc and 0xd on the 3rd 200 ms evaluation past the line (a1783-operation.md, its row); the emulator takes the first at the crossing, so they settle 0.4 s on, and the warm-up and run gates aren't modeled. The BP2000's charge allowance is a stand-in: it may charge below its cap.
- The charge-cap latch sets, clears and counts as the latch table and its counters give it, the 15 s clear count carried across a clear and reset only by `flag_00c7`. The 1 s charging count adds up qualifying time since boot, held (not reset) through the 300 steps (3 s) after a pack switch; it sets the latch on its 101st step (1.01 s), and after that on any qualifying step. Once the +9 path's 15 s runs out (`charge_cap_latch_spent`), +9 alone re-sets the latch and the next step clears it again (`charge_cap_latch_pulsing`, from 300 steps after a switch): `charge_cap_latch` reads 0, the counter-free rows (main → `0x12`, expansion → `0x11`) see the latch, and each re-set clears the discharge latch and re-takes its baseline at both edges. A pack charging with no source in (`pack_current` set by name) is the +9 path's case. A charge starting into a main that holds the bus at its cap goes to the main, and the latch's count moves it.
- The discharge latch arms on the main's 1.0 % drop (the latch table's path (a)), its baseline re-taken as "Discharge-latch drop baselines" gives it; the firmware's 1 s settle after charging stops, and the expansion's own baseline and drop, aren't modeled. The two latches clear as fsms's two "clears" lists give it: setting the charge-cap latch clears the discharge latch, but arming the discharge latch leaves the charge-cap latch, so both can be set. Main → `0x22` on the discharge latch then clears the charge-cap latch. Expansion → `0x11` and each counting step of the main's charge-ineligible row clear the discharge latch; on the step main → `0x22` switches, that row has already cleared the charge-cap latch, so the count doesn't run and the discharge latch stays (fsms "Pack selection", the paragraph under its table). Main → `0x11` (the charge-cap latch set, the main able to charge and below its cap; the bus stays) clears it too, except while the `0x22` row's conditions hold: they skip main → `0x11` and `0x12` even before its 200-step dwell passes. With the expansion switched off, "Forced main" (`pack1_flag_0b56_clear`) skips every row, main → `0x11` included; its `0x01` write 300 steps on changes only the direction, which isn't modeled. `status_2bit_a(0,3)` in main → `0x11` reads 0. A pack switch keeps a running 1 s count's time (the count runs again 300 steps on). The firmware sees the pack-switch hold two steps (20 ms) after the switch ("Selection byte"); a stretch running across it comes out the same, so that lag isn't modeled. A row queued for a later step reads its conditions again when it runs, since a live draw due then lands first.
- Rows modeled: main → `0x12` on the charge-cap latch with `pack0_alarm5_or_a1c` (the main not discharging and its 0xc set, displayed SoC > cap + 0.7 %; 2026-10-06 20:20:00 → :03, taken as the main past 95.7 %), main → `0x12` on the latch with the main's charge allowance 0, 300 steps on (21:11:30), main → `0x22` (the discharge on the discharge latch, more than 2 s after the last switch; how a reverted `min_soc` hands the bus back, a1783-operation.md "`min_soc` as a lever"), expansion → `0x11` (the latch set, the main's charge allowance non-zero, more than 2 s after the last switch; 21:00:04), expansion → `0x21` (under `min_soc` + 0.9 % with the latch clear and the main's charge allowance non-zero, at once, its dwell counter passing on the first step after boot, `pack_on_bus` by name included; 2026-09-03 03:29:25), and the expansion → `0x21` ineligible row (the expansion not charging, its discharge allowance 0, the latch clear, 300 steps (3.01 s) on its counter, each counting step clearing the discharge latch; a raised `min_soc` on 2026-08-31, the main past 99.9 % at its 100 % cap, a1783-operation.md "`min_soc` as a lever"). An expansion under its line keeps the bus while the latch holds (2026-10-06, the expansion at 5 %); with the latch clear the floor row hands it to a main that may charge, else the ineligible row 300 steps on.

Not modeled: the once-per-boot `0x22`, the pack-switch-code rows (`0xaa` / `0x55`), main → `0x22` after 300 steps on the main's discharge allowance, the ineligible row's `0x11` half (an expansion at its cap charging hands the charge to a main that may), the main's charge-full flag (`pack_p54_10_get(0,5)`, `0x20000ff3`, set by its charge-end detectors; its one-step main → `0x12` at the end of a CV taper), the discharge latch's high-current path (b), the charge-cap latch's other set paths (the idle and no-SoC counts, which read the min cell, vext and vbat that no value carries, and the fault path), the latches' `pb1_low_handler` reset, the expansion's quiet 13 at its cap, `.15.5` following power or SoC between switches, the one-frame `c0[24]` flap after the cap handover, and the bus voltage `.15.4`.

C Gen 2 expansion switch (`4104 a4`): the override, the 2 s reread and the off's `flag_00c7` gate run as a1783-control.md "`4104`" gives them, the expansion's own switch-on state (`flag_0b56`) being the hidden `expansion_switched_on` (unset = on). An off that reaches the expansion returns the selection to the main at once, through the switch event the `4104` path posts (a1783-control.md "`4104`"), and while off the expansion takes neither charge nor discharge. `expansion_switched_on` set to 0 by name moves the bus at once too, standing in for that path; an off with no switch event (the pack button) would move it only by "Forced main"'s `0x01` write 300 steps on (fsms "Forced main"), which isn't modeled. `flag_00c7` reads AC in (`a7[3]` 1 or 2, Battery-Only included), PV in, or the alternator charger in its Charging Mode (a1783-telemetry.md "`.14.30` bits"). Not modeled: `flag_0a55` and the on it gates, the PC12 gate on the off's CAN send, the pack button, and the locate blink (`a5`).

C Gen 2 AC top-off: with mains in, Battery-Only Power off and the main on the bus, the main's `pack_soc` falling below "Top-off hysteresis"'s clear threshold (a1783-telemetry.md) starts a burst at once at the full charge, the flow state following. The emulator ends it 60 s later on the first 0.1 % past the set threshold (100.0 % at a 100 % cap), where the charge gate closes, `pack_soc` set there (the recorded burst, a1783-telemetry.md "AC top-off burst": 2026-10-20 04:57:40, off by 04:59). That refills a dip just under the clear threshold; from deeper, the charge would run on to the set threshold, which no value models, so it isn't ended. An expansion holding the bus (its own band) isn't modeled.

C Gen 2 OTA precheck: the pair `ota_enable` / `ota_block_reason` follows the SoCs as a1783-control.md "`4089`" gives it (`ota_precheck_update`), and a change of it pushes `0489` 0.15 s later. The pair compared is the one the SoCs give, not the recorded one (every recording carries 0 2 at a full SoC); a call that sets the pair itself keeps it. Upgrade and BMS boot mode aren't modeled.

C Gen 2 Battery-Only Power at the floor: the 2026-10-15 run of a1783-operation.md "Battery-Only Power at the floor" is replayed. With Battery-Only on and mains in, the main's `pack_soc` falling under `min_soc` + 0.9 % (its BMS's low-battery bit) drops the mode to state 2 at once, mains accepted; AC charging starts 4 s later by the cap rules, from the 118 W first step of the mains ramp (above); back over the line, state 2 clears to 0 1 s later and the screen wakes; the expansion takes the bus later by pack selection. The `dc` low-battery code, the outputs' dip during the drop and the min-cell path aren't modeled.

S2000 ratings (s2000-as220.md "Ratings"): a value set by name past a rating is refused with `TypeError` and sets nothing. Each is checked on the state after the change, when the change sets a power it reads (the totals' parts below included). No time limits are modeled.

- AC in (`ac_input_power`) holds to 1 833 W: the 1800 W bypass rating plus the C Gen 2's 33 W overshoot band. AC in is the charge plus the AC out (`ac_output_power`) it passes through.
- The charge, AC in less AC out, holds to the 1600 W UltraFast rating whatever `ac_recharge_power` and `super_fast_charge_status` read: the unit charges past its limit for 1-3 s after a switch (s2000-as220.md "Charge past the limit after a switch"), and the emulator doesn't model that decay. Less AC out under a charge that would then pass 1600 W is refused too.
- Solar (`pv1_input_power`) holds to 400 W and AC out to its 3000 W peak; with no time modeled, the 1500 W continuous rating isn't. `aa` (`pd1_output_power`), one USB total, holds to 118 W: 100 W plus the 18 W the USB-A and the 15 W USB-C share.
- The AC charge limit (`ac_recharge_power`) has no documented accepted range, so none is refused; `a3`'s fixed 1200 W `ac_input_limit_max` is the unit's reported maximum (s2000-as220.md "Telemetry").

S2000 totals (s2000-as220.md "Telemetry", the totals tie): the input total (`total_input_power`) follows AC in + solar and the output total (`total_output_power`) AC out + `aa`. The parts' ratings bound them.

- A change of AC in or solar moves the input total to their sum, and a change of AC out or USB moves the output total.
- An input total set alone splits: AC in takes the charge the limit requests (`ac_recharge_power`, 1600 W with UltraFast on) plus the AC out, at most the total and 1 833 W, and solar the rest. The charge settles at the limit, not over it (600 W in at a 600 W limit with AC out 0, s2000-as220.md "Charge past the limit after a switch", 12:24:27). 1 500 W at the 1200 W limit with 55 W out reads 1 255 W AC and 245 W solar. Set with one input, the other is the rest; set with both, they must sum to it. A negative rest, or solar over 400 W, is refused with `TypeError` and sets nothing.
- An output total set by name, alone or with parts, must equal AC out + USB after the change; one off it is refused with `TypeError` and sets nothing.

S2000 setters (s2000-as220.md "Setters"): `4101` and `4103` set the fields that table maps, with the C Gen 2's codecs (above), and answer with the recorded ack and then a `0421` carrying the change.

- `4101 aa` sets `smart_ac_output_timeout` (`a4[28:30]`, minutes; no app name is known). It sits in the A1783 settings tail's reserved bytes, beside `a4[26:28]`, which reads "US" in the #322 frames (unnamed in PiField) and stays as recorded.
- `4103 a2`'s `screen_switch` shows in the `0421` after the reply's ("the second"), the next of the unit's stream. The emulator streams no `0421` (the stream after `4100`, s2000-as220.md "Telemetry", isn't modeled), so it sends that one itself: the switch is held (the hidden `screen_switch_request`), then set 0.5 s later with a `0421` push; the doc gives no time, so the 0.5 s is the emulator's. A repeat while one is held keeps the held one's time.
- `ultrafast_charge_state` (`f0[3]`; the emulator's name) reads 3 with `super_fast_charge_status` on and 0 with it off, a frame late (s2000-as220.md "Telemetry"): a change of the flag sets it 0.5 s later with the same stand-in `0421` push, so the `4101 a7` reply's `0421` still shows the old value and that push the new. One set by name is taken.
- Params the doc's table doesn't show (`4101 a3`/`a5`/`a6`/`ab`, `4103 a9`/`b0`) and the SoC-limit clamp follow the C Gen 2's handling.
- A setter changes only its setting, power staying as set or drawn, except that the AC output switched off reads AC out 0 W, as on the C Gen 2 (above), with the totals tie and the pass-through following.
- Not modeled: the C Gen 2's screen wake and timeout, which s2000-as220.md doesn't record for the S2000.

S2000 AC pass-through: `ac_pass_through_status` (`f0[0]`; the emulator's name, since no app name is known) follows s2000-as220.md "Telemetry"'s `f0[0]` rule: 1 with `ac_output_status` (`a7[0]`) on and AC in over 0 W. It's set on every change of either, and is separate from `a7[3]` `ac_input_status`. One set by name off the rule is taken (5 of the 433 #322 payloads read so, beside a change) and holds until the next change sets it from the rule.

Module session ops below `0x40` are the ESP32's own, answered on `03 00 0f` once the link is authorized. `0030` → `0830` is built on every build from the module build, the device firmware and the product's names (C Gen 2: `<pn>_low`, `<pn>_mcu_low`, `<pn>_esp32_low`; Prime: `<pn>`, `<pn>_mcu`, `<pn>_esp32`). The A1783's recorded `0020`, `0028`, `002e`, `002f`, `0036` and `0038` replies come only with v0.3.3.0, the build they were recorded on.

Every wire parse and build is a [construct](https://construct.readthedocs.io) layout: the frame (`PATTERN_LAYOUT`, `COMMAND_LAYOUT` with the link flags and 12-bit msgtype, `FRAME_LAYOUT`, `FRAGMENT_LAYOUT`), the fields and messages, the key material (`GCM_KEYS_LAYOUT`, `CBC_KEYS_LAYOUT` over the shared secret), the P-256 point (`POINT_LAYOUT`) and the advert record (`ADVERT_LAYOUT`). Frames and parsed messages are construct `Container`s; plain classes hold only settings and link state, which have no wire form.

The module and MCU layers are synchronous and transport-free: a write in, a list of frames out, each with a delay. Time is injected, so timers are testable without sleeping.

## Behaviour emulated

- Frames, the `cmd` flags and the fragmenting follow anker-crypto-and-negotiation.md "Frame" and "Fragmentation and MTU"; the fragment cap is ATT MTU − 3, 253 by default.
- The outers and the session ciphers follow its "Path selection and the static key" and "Authentication generations": the encrypted outer under the static GCM key, then the session GCM from the raw-X shared secret; the plain outer in clear, then the session CBC, which checks only the last pad byte on the way in (its "Frame" status split). A fresh P-256 point answers each `4021`.
- Port context: an encrypted frame with no session opens under the module's key and IV as that doc's "Frame" key row and "Authentication generations" bootstrap give them: zeros at boot, then whatever the last `0001`, `0021` or legacy confer set. A new link keeps them, so an encrypted frame before its `0001` meets the last link's key.
- Authorization (its "Registration and the side button (`0027`)"): an enrolled token authorizes at once; a new one gets `09` and the confirmation window, granted by a simulated button press (`press_button`, `4827 00` on `030101`). Opcodes `>= 0x40` reach the MCU only once authorized.
- Module policy and the authorize timer follow its "Module authorization policy (v0.3.3.0)": v0.3.3.0 enforces the auth mode on the encrypted outer, the earlier builds (v0.2.9.7, v0.3.0.6) take either connect frame, and an unauthorized link drops on the 10 s timer's schedule.
- The MCU's RTC and the module's TZ follow a1783-control.md "Clock": an accepted `0022` sets the RTC to local time through the module's floor and it then runs on the device clock, counting from 0 before any set; the module keeps the UTC epoch a push's `fe` carries, and its TZ timer re-sends the stored zone's offset on that section's schedule, so DST switches with no new `0022`. Each MCU applies its own rules on top (the C Gen 2's in "Clock"; the Primes' in prime-a2345-a91b2.md fid 0x10 ops `0x26` / `0x09`).
- A recorded frame the MCU replays (a push, a read's reply, its MQTT copy) carries that epoch in place of its recorded `fe`, as the device stamps its own clock (a1783-telemetry.md `fe` `msg_timestamp`; prime-a2345-a91b2.md Shared "Commands", "Reply `a1`"), counting from 0 at boot, as the RTC does, until a clock set. A layout that names `fe` itself (the AS200 and A17C0 `timestamp`) keeps its own, a frame recorded without `fe` gains none, and a device with no layout replays its frames as recorded.
- Account-gated clock set `002b`: answered as a1783-control.md's `0x02b` row and anker-crypto-and-negotiation.md's `check_account_id` give it, sign quirk and full-width reads included. The bound account lives in the module's RAM: it outlives a link and a factory reset, and a new module starts with none.
- Decrypt failure: an encrypted request the link's key can't open gets the status anker-crypto-and-negotiation.md "Decrypt-failure `01`" and its "Frame" status split give, sealed under that key on the request's pattern; the link stays up and the MCU never sees the frame.
- Timed events: the module keeps a queue of events on the device clock, checked every `push_period` (0.1 s). Each event's action sees the set values and the device's whole state (the recorded values, set ones over them, the RTC in local seconds, and the UTC epoch a push's `fe` carries; a clock set puts the RTC at the `a1` UTC less the `a3` offset and the epoch at the UTC itself). It sets values or clears them back to the recording, sends recorded pushes and frames it builds on an authorized link, and can start the next event, timed from its own due time so a cadence holds when a check catches up. Scheduling an event replaces any queued one with its key; link events (a burst, a factory reset's drop) end with the link; one that falls due with no link sets its values and sends nothing. A layout's `timed` hook starts events from a change of state, whether from `set_values` (a change made on the unit), a command (its request msgtype passed along, so a layout can tell the two apart), an on-unit event no field carries (`unit_event(name, **hidden)`, a screen switched on the unit, say, with its own data as hidden `_` values), or a clock set (`0022`/`002b`, which re-times what depends on the RTC); those due at once run there, so a command's own reply and follow-ups carry what they set, and their pushes follow the reply. Each of those changes (and `set_cloud`) first runs whatever already fell due, so an overdue event sees the state it fell due in, and a command's side effects see the same whole state a timed action does. An event run late (a long advance between checks) reads the RTC and epoch at its own due time, and its pushes are built with that RTC. The clock is injected: `ManualClock.advance` runs everything that falls due on the way, `ManualClock.jump` moves past it (each bypassed event sets its values, sends nothing), and `ScaledClock` runs real time at a chosen speed.
- Bursts: the Prime `420b` realtime trigger (prime-a2345-a91b2.md Shared "Commands"): `4a0b` and the first of its 10 `4303` pushes, the rest 1 s apart as a link event; a `420b` mid-burst sets the count back to 10.
- Factory reset (`Profile.factory_reset`): the A2345's `4201` acks `00`, clears every set value back to the recorded frames and forgets every enrolled token, then drops the link after the MCU's 10-tick debounce (1 s, checked every `push_period`); the next `0027` needs the button again (prime-a2345-a91b2.md A2345 "Commands" `4201`).
- Routing: a session request's `a1` route and the fid-scoped opcodes follow anker-crypto-and-negotiation.md "Frame" (its `a1` routing table and channel list) and a1783-control.md "WiFi provisioning": the module answers its own ops on the arrival port on the fids its handlers serve, relays to the MCU only a request routed from BLE to the MCU on fid `0x0f`, drops one with no route, an unknown source or an unhandled destination, and answers a logging-channel (source `a`) request itself with `00`. An MCU request on fid `0x11` or `0x13` draws no reply, and every MCU frame on the BLE link is routed `a1 31`.
- Relay: post-authorization requests go to the MCU script; its cleartext replies and pushes are encrypted for the session and sent on `03010f`. A command the product's layout handles with no recorded reply gets `<status> a1 01 31`: `00` when the layout's validator accepts its values, `04` when not.
- Command table (`Profile.known_commands`): a request nothing recorded or modeled answers gets the firmware's own answer from the product's table, an ack with its status or no reply; a request past the table's last op gets `past_table_status` (none: dropped); anything else is dropped. The C Gen 2 display board answers by a1783-control.md "Command map": `4051`/`4059` ack `00`, `4051` restoring as "`4051` factory defaults" gives it (the four per-region values keep the unit's own); `4065` / `4066` serve the header chunk alone as "BLE log upload (`4065` / `4066`)" lays it out by the `f9` MainMcu version (`READ_REPLIES` builds a read's own fields; the slots no frame reports are its constants), any later chunk getting no data; `4064` before an OTA start and every op outside the table are dropped. The Prime MCUs ack every real handler `00`, op past the table included, say nothing to their no-op stubs, and drop an op below `0x200` they don't handle inline (prime-a2345-a91b2.md Shared "Commands"). Two A2345 handlers answer by branch: `4212` and an accepted `4222` send nothing, while a `4222` without `a2`, or a `420d` whose `a2` isn't typed `02`, gets `04` (`SILENT` marks a layout command whose accepted request goes unanswered). A `4222` of 0 or 1 sets the `4a02` `a6` switch; a nonzero `420d` draws a `0305` with trigger 0. The A2345's `4218` answers each USB-C port's offered power-sharing budget, looked up by which USB-C ports are active and whether a USB-A port is (prime-a2345-a91b2.md "`4218` field5 power-sharing budget"), then each USB-C port's `0303` output status. The A91B2's `4202` answers with the snapshot's `ac` byte (screensaver switch and theme), the field its `4205` writes (a theme past 2 stored as 2), then the unit's clock.
- Setter replies and pushes from captures: a layout's `ECHOES` name the request fields an accepted ack carries back after its `a1` (the Prime port setters `4207`/`4208`/`4209`: the port and `4208`'s slot), and its `CLOCKED` acks then carry the unit's clock, its UTC epoch, whatever `fe` the request sent (prime-a2345-a91b2.md Shared "Commands", "Reply `a1`"). Its `FOLLOW_UPS` are the pushes an accepted command can draw, each built from the request and the device's state before and after it (`McuScript.state`: every named value the recordings carry, the set values over them), or skipped when the change doesn't trip it; a push ends with the unit's clock as its `fe`, as that bullet gives it. Its `SIDE_EFFECTS` are further values a command sets from that state (`4208`'s conflict-clear). A refused command gets the bare `04` ack and no push. A2345 `4207` answers `04` only when `a2` or `a3` isn't type + one byte; a port past 4 or a state past 1 is acked and ignored. A `4208` `a3` other than 0 / 1 is acked and dropped. A `4206` mode 5 applies only with its whole profile (`a3` 7 B, stored to `b8`; `a4` 12 B, its port records not modeled); otherwise it's acked and dropped. The A91B2's `4206` (A91B2 `4206` row) acks `00` first and then changes nothing for byte0 ≥ 2, or byte0 1 with byte1 ≥ 3; with byte0 0 it stores byte1 unchecked.
- Prime pushes: `0302`, `0307`, `0308` and the A2345's `030f` go out on the changes prime-a2345-a91b2.md A2345 and A91B2 "MCU pushes" give them, `0308` before the `4208`'s ack (`LEADING`). On a `4208` collision (both halves enabled, the unset `ff` included, at the same hh:mm), both MCUs check two once halves as always colliding, a once half against a repeating one by its stored date's weekday bit ANDed with the mask, and two repeating halves mask against mask; the just-written half wins (prime-a2345-a91b2.md "Defaults and collisions", the A91B2 `0308` row). The unset `ff 0c 00 00` half is a once 12:00 dated 0/0/0, which reads as Monday (0x01) on both, so it meets any once 12:00 write, as the recorded 2026-09-09 `0208` → `0308` does, and a repeating 12:00 only on Monday's bit. On the A2345 each port's `0302` goes out on the 5th `tick_100ms_group` tick after that port's own last switch change (`port_switch_change_mark?` writes count 0 and restarts only that port's count; each tick counts 1 up and the 5th sends): a change made between ticks (a command, `set_values`) counts from the next tick, 0.4–0.5 s on; a change from the 150 ms pass (countdown expiry, timed task) from the 100 ms tick after that pass (prime-a2345-a91b2.md "Report timing", "Countdown timing"), with its switch as it then stands. One source byte (`DAT_2000a7ce`) serves all ports: a firmware change (countdown expiry, timed task, the port screen's power-on tap, which `set_values` turning a port on stands in for) writes 2, an app `4207` writes 1 and marks its port if it changes it; at a port's send a 1 drops it and resets the byte to 0, and 0 or 2 sends; ports falling due on one tick go in port order (prime-a2345-a91b2.md push table `0302`). So an app `4207` alone draws none, but a second one whose port falls due after the first's, or one followed by a firmware change, is reported. The SysTick groups (100 ms, 150 ms, 1 s; prime-a2345-a91b2.md "Scheduler groups") each first fire one period after boot and every period after, nothing at boot itself; boot's instant on the device clock is the hidden per-run `systick_phase` (0–3 s, default 0), and a value outside that is refused with `TypeError`. At a shared instant the 1 s countdown step (in the ISR) and the 100 ms group run before the 150 ms pass, so a switch the pass makes is applied on the next 100 ms tick. The A91B2's TIM1 tasks (its "Timer timing", "Task dispatch") share that phase: each first runs one period after boot, and `sched_dispatch?` runs every task due at one tick in slot order, `ac_switch_push_0302?`, then `timer_group_tick_150?`, then `usbc_switch_push_0302?`. The firmware reloads each counter at dispatch, so its periods drift by the main-loop latency; the emulator keeps them on a fixed grid (the zero-latency case) and doesn't model that drift. Within a tick the screen reports go before the `0302`s. The A91B2 (prime-a2345-a91b2.md A91B2 `0302` row, "`0302` recorded timing") reports every switch, from a `4207`, a timer, a countdown or the button, with no source gate: its period-100 tasks compare each port with a last-reported shadow (hidden `_<port>_switch_shadow`, seeded from the switch before its first change). `ac_switch_push_0302?` sends an AC port's `0302` on the pass that sees the change; `usbc_switch_push_0302?` marks a USB-C port there, setting its shadow, and sends that shadow on the 5th call counting that one, 4 periods on (0.4–0.5 s after a change between passes; the A91B2 "MCU pushes" shadow bullet). A change seen on any later pass, the send's own included (the pass compares before it counts), marks it again from 0, so a port flipped and flipped back inside the debounce draws one `0302` with its last state, and one flipped back before a pass sees it draws none.
- Prime timed events: a pushed timer frame ends with the device's UTC epoch as its `fe`, as a command's acks and pushes do. On the A2345 a change of `charging_mode` (a `4206`, `420c` entry, or `set_values`) sends `030d` after the mode-apply settle and drops the port blocks while the ports renegotiate, as A2345 "MCU pushes" `030f` and "Commands" `4206` give them (3.3 s, 8 s); `420c` entry is assumed to share the path. Each block then gets back its set value, else its recording; one set during the window keeps that value, and a further mode change in the window keeps the one window. The 100 ms and 300 ms ticks that read the ports (Feature 2's edge loop, Power Expert's count, the port-activity scan and the budget switch) see both the drop and the return.
- Prime countdowns: an armed `4209` countdown ticks into the values, so every frame (a mid-countdown `4a00` included) reads it as it stands; arming, re-arming or setting the remaining time restarts the count. On the A91B2 (prime-a2345-a91b2.md A91B2 "Countdown timing") `remaining` drops in the RTC second interrupt, on the RTC's own seconds (the state's `rtc_second_at`, the device-clock instant the current RTC second began), and a clock set re-times it; the next `timer_group_tick_150?` pass after it reaches 0 switches the port off and pushes the disarm `0307` (`remaining` 0 on USB-C, the seconds set on AC), the port's `0302` following from its switch task. A `4209` only sets the record and replies: armed or not, it writes its enable and its seconds into both set and remaining (`ac/usbc_countdown_set`; A91B2 `4209` row), so a `4a00` before the next pass reads the sent seconds, and that pass gives a disarmed countdown remaining 0 on USB-C and its set on AC. A port past 5 is acked `00` and dropped. Its `0307` comes from the next `timer_group_tick_150?` pass, where `ac/usbc_countdown_tick_push_0307?` pushes it on the edge between the enable and the one it last showed (hidden `_<port>_countdown_shown`, seeded from the enable before the first change), as on the A2345: a re-arm 1→1 is silent, and a countdown that ends before it is shown armed (a 0 s `4209`) pushes none. The AC countdown record's `+0` (`ff` from defaults, 1 from the first arming `4209`, never cleared) gates the AC tick and the button's countdown re-arm (event 6); every arming path the emulator has also sets it, so it isn't kept, and the button re-arm isn't modelled. On the A2345 (prime-a2345-a91b2.md "Countdown timing") `remaining` steps on the boot-phased 1 s grid, so an n-second countdown reaches 0 on the n-th 1 s boundary after the `4209`, n-1 to n s after it. Every 150 ms pass (`countdown_tick_push_0307`) then does three things. At 0, it writes source 2, switches the port off and counts its `0302` from the next 100 ms tick. On a port that is off, it disarms the countdown. It pushes `0307` when the enable differs from the one it last showed: an arm, or a disarm with `remaining` 0. A re-arm 1→1, or a countdown that never showed armed, pushes none. The enable last shown starts as the recorded one; a disarm on an off port leaves the stored remaining. `cmd209` answers `04` only for an `a2` / `a3` of TLV length other than 2 / 6; a port past 4 is acked and changes nothing; any nonzero `en` is 1, and the seconds go in unchecked for every `4209`, a disarm's into the set seconds with the remaining forced to 0.
- Prime timed tasks: on the A91B2 (prime-a2345-a91b2.md A91B2 "Timer timing", "Schedule firing", `4208` row) every `timer_group_tick_150?` pass checks each enabled slot: a repeating one fires when its hour and minute match, the seconds read 0 and its weekday bit is set, latched until a pass that doesn't match, so a clock set into :05 of its minute doesn't fire it; a once one is dated as on the A2345, by every enabled `4208` write, today if its hh:mm is strictly later, else tomorrow, fires only in second 0 of its exact date and minute (its `time_cmp?` compares seconds against hh:mm:00, so from second 1 it reads as passed), and fired or passed is disabled with `0308` en 00, without switching when passed. A firing switches the port only if that changes it, its `0302` from the port's switch task. On the A2345 (prime-a2345-a91b2.md "Schedule timing") the schedule runs from the 10th 150 ms pass with the RTC valid (≥ `0x66311581`; hidden `_schedule_from`; 1.5 s after boot if valid from boot), and each pass then checks every enabled slot (switch 1; the unset `ff` never fires). A repeating slot fires on the first pass in its hour:minute on a set weekday bit, latched until a pass sees the minute no longer matching, so a clock set into its minute fires it and one out of it clears the latch. A once slot (weekdays 0) is dated by every enabled `4208` write of it, an `en 0` write leaving the date (hidden `_<port>_timed_task_<half>_date`, as year · 10000 + month · 100 + day, the zeroed 0/0/0 until dated; the MCU keeps it at `0x2000101c` / `0x20001026` + 0x14 per port), and by `set_values` on a change: today if its hh:mm is strictly later than now, else tomorrow, so an equal minute rolls over (prime-a2345-a91b2.md "Slot record"). Nothing else dates it: boot and a clock set leave it, and each pass judges it against the time as it stands, so it fires at that exact date and minute, a passed one is disabled with `0308` en 00 and no switching, and a future one waits. A firing writes source 2 every time, before it switches the port, even one already in that state, so it releases a pending app `4207`'s 1; its `0302` counts from the next 100 ms tick only if the switch changes the port. A countdown writes 2 only when it finds the port on at expiry.
- A2345 owner (`420a`): the recorded `4a0a` answers every send, and an accepted one acts as prime-a2345-a91b2.md "`420a`" gives it (the change detector, the custom theme back to 0, custom mode 5 left for the last mode below 5). The owner and that last mode are hidden (`_owner`, `_last_mode`, 1 unset); a fresh device has no owner, so its first `420a` counts as a change. The mode change reports `030d` and renegotiates the ports like any other. `4211 a2` 0 in mode 5 leaves custom mode the same way; `4211 a2` 1 has no documented effect and changes nothing.
- A2345 screen reports: a setting changed on the unit (`set_values`) sends its report as prime-a2345-a91b2.md "Screen reports" gives it, on the 5th `tick_100ms_group` tick after the change (`screen_report_service_tick`, on the `0302` grid and `systick_phase`; each `*_mark_pending` writes count 0, so a change or write inside that restarts it), 0.4–0.5 s on; the service tick's skip while `knob_gesture_bright_flag_get?` (0x0001c758) reads nonzero isn't modeled; `030a` / `0309` / `0310` are 14 B with no `a3`, and `030b` adds the theme id in `a3`, as recorded. While the holiday flag reads 1 (A2345 display state, below), `030b` adds `a4` (type 04), the holiday slot's string that `4a02`'s `a4` carries; no `030b` with `a4` is recorded. The same change from an app command sends only its ack. `4203` / `4204` / `420e` / `420d` answer `04` only for an `a2` missing or of TLV length other than 2 (any type byte); otherwise they ack `00`, and the value setter's range check (`screen_timeout_set` < 5, `screen_brightness_set` ≤ 100, `knob_direction_set` < 2) ignores a value past it. On the unit, setting the brightness reports `030a` even unchanged (`screen_brightness_set`); the other settings report only a change. Each report's source byte (`report_src_*_set`; hidden `_report_source_<msgtype>`, 0 at boot) decides at send time: 1 drops the report and resets the byte to 0, 0 or 2 sends it. The app's handler writes 1: every acked `4203` / `4204` / `420e`, a `4205` that applies a change (a preset, clock off, an already-stored network or custom theme), a `4221` last chunk stored with its CRC, and the self-fetch's landing (`esp_op3e_theme_chunk`); a `04`, a `4205` that stages, fetches or drops its theme, an ordinary chunk and a bad CRC leave it. An on-unit change writes 2, as does a once window's end turning the clock off. So an app write drops a report pending at its send, and stays 1 until the next send of that report, which an on-unit change overrides. A change no handler writes a byte for (a failed draw's fallback, an owner change's theme reset) reports with whatever byte stands. `030b` is marked only by a change of the screen target (`af[0]`'s clock switch and index, `DAT_200001a5`): the holiday switch or the theme id alone marks nothing.
- A2345 display state (prime-a2345-a91b2.md "Display state"; hidden `_display_state`): 0 on at boot, 2 black, 1 the screensaver, 3 the transition screen.
  - The `b0` timeout (30 s / 1 min / 5 min / 30 min; 0 never), counted only while on, blanks it; black moves to the screensaver on the next 0.1 s tick once the clock switch (`af[0]` bit 7) is on, the RTC is at least `0x66311581`, the `4213` window reads inside and the screen-off inhibit (hidden `_screensaver_inhibit`, `DAT_20000b1c`, 0 at boot) is 0; the screensaver goes back to black when the clock switch goes off. The window's edges move it too, on the 0.1 s tick after the pass that changes the phase (`theme_state_change_watch`): from outside to inside, black moves to the screensaver with no clock-switch, RTC or inhibit check, and a clock-off unit drops back to black a tick later; from inside to outside, the screensaver goes to black, the clock switch left as it is. Any change of the phase is an edge, the first evaluation's move from 0 included (the last phase, `DAT_2000b48b`, boots 0), so a late first evaluation can move a black unit to the screensaver past the inhibit.
  - An app setting command acked `00` (`4203`, `4204`, `4206`–`4209`, `420e`, `4213`, `4223`, including a `4206`–`4209` whose change the setter drops, a `4209` with a port past 4 among them) wakes it to 0 and restarts the count, clearing the inhibit; a `04`, a `4205` (it wakes only on a clock-on `a2` while the screen-off inhibit is 1), any other command and an on-unit change don't, though any valid `b0` write while on (`screen_timeout_set`, < 5), from the app or the unit and even unchanged, restarts the count.
  - The `4213` window's phase (hidden `_screensaver_window_phase`) is evaluated by `clock_holiday_autoscreen?` on every 150 ms pass, after the countdown and schedule ticks: first on the 10th pass with the RTC valid (1.5 s after boot if valid from boot), then on the first pass at or after each start and end minute, and on the next pass after a clock set or a weekly window change (a weekly store sets no phase itself). The inside rule is prime-a2345-a91b2.md's "`4213` inside rule": Start < end: start ≤ now < end, on today's bit. Start ≥ end wraps midnight: now ≥ start on today's bit, or now ≤ end (end minute included) on the day before's bit (Monday: bit 6). So start = end covers the whole day. Weekmask 0 is a one-shot dated window. `screensaver_window_store` dates its start and end (hidden `_screensaver_window_start_date` / `_screensaver_window_end_date` for `b4a0` / `b4aa`, as year · 10000 + month · 100 + day) by now's hh:mm against them (prime-a2345-a91b2.md "`4213` window dates"): before both, both today, the end tomorrow if end ≤ start; at or after both, the start tomorrow if start < end, else today, and the end tomorrow; at or after the start but before the end, both today; before the start but at or after the end, the start today and the end tomorrow. Every "tomorrow" is a plain day + 1 with no month carry, and the date compares year, then month, then day, so a roll past a month's end (Oct 32) never matches and reads as passed from the 1st. The store sets the phase itself, inside for start ≤ now < end (start < end) or now ≥ start (start ≥ end), so a window stored while inside is entered at once. After that it goes inside only at the exact start date and minute, and is skipped for good once that has passed, so a clock set past the start never enters it. At the exact end date and minute it goes outside, and `screen_target_set(0, theme)` with source 2 turns the clock off, which reports `030b`; an end found already passed turns the clock off the same way with the phase left inside, as `clock_holiday_autoscreen?` does.
  - The holiday flag is evaluated at the move to the screensaver, and in it at each holiday window bound and a tick after a holiday switch, country, record or clock change; a change between 1 and 2 pushes `030b` at once, with no source byte or debounce, and an edge crossed while on is pushed at the next evaluation.
  - Edges land on the tick the whole-second RTC reaches them.

  - `4205` (`_theme_staging`, `_theme_selected`): a stored slot (hidden `_theme_crc_<id>`, `_theme_size_<id>`, `_theme_kind_<id>`, `_theme_image_<id>`) shows at once; any other id is staged (hidden `_theme_staged_id`) with WiFi down, or fetched with WiFi up.

The emulator fetches no bytes, so the image always passes. ## Recorded data

MCU replies and pushes are recorded cleartext from real units, packaged as `devices/data/<pn>.json` (msgtype → cleartext hex) by `tools/sanitize_frames.py`; a profile lists its files, and the first that holds a msgtype supplies it. The tool reads collector logs and MQTT records (anker-solix-api `.ndjson` examples, `mqtt_monitor` dumps). An MQTT frame is the same frame the MCU sends to BLE with another routing marker in its leading `a1` (`34` or `32` for `31`), which the tool sets back to `31`; `--fix-checksum` recomputes the checksum of records whose serial was anonymized after capture. Sources are listed in [device-sources.md](device-sources.md). The tool takes the real identifiers on its command line, never stores them, and fails on any printable run it wasn't told is safe. The frames are sanitized before they enter the package: the serial, MAC, expansion serials, account tokens and device clocks are replaced with synthetic values of the same length, and the frames are re-encoded. The fixed handshake frames (`4801`, `4803`) are reproduced byte for byte; frames that carry the serial or MAC match a real capture everywhere except those fields.

## Live values

Off by default, so every frame is the recording with the set values over it. The A2345 and A91B2 have tables (`a2345_live.json`, `a91b2_live.json`: the `0303` and `4a00` port blocks). `device.vary_live_values(seed)` turns it on with `random.Random(seed)`; `vary_live_values(None)` turns it off. Only a device with recorded live values has a table (`Profile.live = LiveSource(table, period)`); any other raises `LayoutError` naming the device, as does a table that names a field the device sends in no message.

- Tables: `devices/data/<pn>_live.json` (compact JSON), built by `uv run python tools/build_live_tables.py <survey dir> [--only <PN> ...]` from the frame survey's per-device JSON. A match key one message records at a single value carries to the same-named group of a message whose frame lacks it, at that value: the Prime port relays (`pdN_relay_switch`, the A2345's shared `usb_relay_switch`) are in `4a00` only and read 1 in every recorded frame, so a port switched off with `4207` matches no sample and idles in `0303` too; a key that would carry but was recorded at more than one value is refused. Per message it keeps the groups (fields that move together, like a port's status, voltage, current and power: their `live` fields, the idle values of those, the rest as match keys, any further match keys from outside the group's field (`match`, an AC input's switch and status), and the recorded samples with their counts), the groups recorded active together (`active_sets`), the totals that held in every frame, the paired draws (fields recorded beside a given tuple, like a pack current beside a total), the slow fields' steps, range and interval (the survey's median time between recorded steps; a slow block without one is refused), and `remaining_time` split by output idle and active. Counters, the totals that didn't always hold, and identifier fields are left out; a table holds numbers only, apart from the match wildcard below. A survey of a device the emulator doesn't have is refused, as is a table that draws (a group's live field, a total, a paired field, `remaining_time`) a field the device's layout derives from others (`LayoutProtocol.derived`, empty by default); a derived slow field is left out with a note, since the layout works it out from the field it follows, and a derived field may still be a match key. The survey's `mirrors` (names that are one state value here) are ignored. Samples are read by their column names (`sample_columns`, `sample_columns_short_a4`), summed over `transport`: the BLE and cloud frames come from one state. A sample list the survey hasn't cut (no `dropped` / `dropped_short_a4`) is cut after that sum: every idle tuple stays, and the active ones, commonest first, until they cover 99 % of the group's active frames (`COVER`), the one that reaches it included; a tie goes to the lower tuple. A named section (a joint table, like the A1783's `ac_charge`) and a `0490` section of a schema the emulator doesn't send (it sends `_0009`) build nothing, with a note. A C Gen 2 frame whose `a4` has no byte 31 (26 B) comes from firmware without Battery-Only Power, which v1.2.1.6's 7 appended bytes bring (a1783-telemetry.md's `a4` row). Those samples (`samples_short_a4`) keep the match keys the frame carries (`match_short_a4`); the emulated v1.2.1.6 lets them draw only with `ac_input_disable_switch` at 0: a modelling choice that takes that firmware's AC behaviour as Battery-Only off, not a recorded switch state. They merge into the group's samples, a tuple both hold adding its counts. The AC charge limits govern the AC input, not the AC output: a sample whose `ac_input_power` is idle takes `*` (`live.ANY`, which matches any state value) on `ac_recharge_power`, `silent_recharge_power` and `super_fast_charge_status` (the builder's `INPUT_ONLY`), and such samples merge. The DC input's group (`pv1`) also matches on the hidden `dc_input_source` (0 solar, 1 car socket; the app has no name for it, and its `carChargerInputPower` reads the same XT-60i value as `pv1InputPower`). A plugged-in sample (`pv1_charge_status` 1) takes the source of the era its days (`a8_by_day_local`, America/New_York) fall in, by the owner's era table for the XT-60i: 2 × PS400 solar before 2026-08-08, the car-socket adapter from then. One with nothing plugged in (status 0) takes `*`. A plugged-in sample with no day, or with days in both eras, is refused. Each frame sample counts 2 s, the collector's poll. The solar samples come from the `_0005` `0490` posts' `.23.5` (the DC input's register, as `a8[1:3]`; `dc_in_by_day_local`), each counting 540 s, the push interval: longer gaps are missing posts. A day the frames also cover keeps the frames and skips its posts. A day with no post above 0 W had nothing plugged in and gives no samples: on 07-21 to 07-23, inside that week of 0 W posts, the device's own frames read `pv1_charge_status` 0. Every other post is status 1, 0 W included (night with the panels in): the emulator's choice, since a post carries no status. A car-socket day the frames don't cover with a post above 0 W is refused. The `_0009` posts aren't a source: their days are car-socket ones the frames cover more finely. The group draws on its own (`independent`), out of the active sets.
- When: a frame is built (a push the device sends on its own, a timed event's frame, an answer to a request, `device.push`, `mqtt_frame`) after at least one telemetry period has passed since the last draw: the device first runs the events due by then, so each sees the state of its own due time, then draws, then runs what the draw starts. Turning it on draws at once, and draws fall on a period grid from there, so frames built within one period share a draw and the same seed with the same clock steps gives the same frames. The period is the device's stream period: 1 s for the Prime `0303` (`REALTIME_BURST`).
- A draw, per message in table order: pick an active set by its count, leaving out groups with no drawable sample (an active group draws a sample whose match keys equal the device's current values, so a port switched off stays idle); each active group takes its sample, every other group its idle values; an independent group isn't in the active sets and takes one of all the samples matching the current values, idle ones included (its idle values with none), so it is active as often as it was recorded active given its match keys; a total sums its parts as they then stand, set ones included; a paired draw takes a tuple recorded beside the current given values, or holds the fields (`unpaired`); each slow field takes one recorded step per interval passed since its last step (each on its own clock, the remainder carried, so a `0490` field recorded 540 s apart steps every 540 s whatever the draw period), clamped to its recorded range; `remaining_time` comes from the output-idle split when `total_output_power` is 0, else the output-active one. After each message the layout's `derive` gives the values that follow from the state (`LayoutProtocol.derive`, none by default), which a later message's draw reads; they are never part of the draw. A field an earlier message drew isn't drawn again, so a name in two messages (`pd1_output_power` in `0303` and `4a00`) is one value. A group with a pinned field isn't drawn at all, so its fields stay one recorded sample's. Values come from the recorded frequencies as they are.
- Drawn values go the way `set_values` sends them: into every frame that carries the name, with the layout's implied values, and the timed events the change starts run before the frame is built. A value given to `set_values` is pinned and a draw never changes it; implied values and those a timed event sets aren't.
- C Gen 2: the A1783 has a table (`a1783_live.json`). From `0421`/`0900`, one section: the port groups (AC in and out matching the Battery-Only switch, the AC status, `ac_recharge_power`, `silent_recharge_power` and `super_fast_charge_status`, the last three on the AC input only, so a limit never recorded still draws AC output but never AC input; DC in on its own: plugged in, the car socket drew power in 2 236 of the 2 282 frames the table keeps (121-129 W), the solar panels in 433 of 1 002 Pennsic posts (1-486 W), and `dc_input_source` reads 1, the car socket, while unset (`LayoutProtocol.defaults`: the values hidden inputs read while unset, none by default); PD1-PD3, USB-A, the car socket, the alternator charger), the output total of all seven port outputs, the temperatures and WiFi signal, and `remaining_time`. From `0490`: each pack's SoCs, estimators, reserve and voltages, and its pack currents and pack-side powers paired with `.23.4` / `.23.2` / `.23.7`. It draws every 1 s, the `c421` stream's period (`c421_change_tick`'s 1000-tick timer, a1783-control.md `4057`); the slow fields drift by their recorded steps per recorded interval, counted on the device clock whatever the client's poll rate. The `0421`/`0900` steps were recorded per collector poll (median 2 s, the collector's `runtime.poll_interval_s`; the log cadence follows the poll), so they apply per 2 s elapsed; the `0490` ones per post, 540 s. The A1763, A1765 and A1785 have no recordings and refuse. The `0421`/`0900` section comes first, so the names it shares with the `0490` (the output total, AC output, DC input, `remaining_time`) are one value, and the `0490` posted in a period carries that period's. The flow state, the battery levels and `.23.4` aren't drawn: the layout's `derive`, the same derivation its changes run, hands them to the draw after each section, so the `0490`'s paired tuple is looked up against this period's totals, and a pack current a pair draws stays in that change.

## Layouts

Each product's commands and telemetry are hand-written in its own device module as a layout class satisfying `LayoutProtocol`, passed as `Profile.layout` (`CGen2Layout` in `solix_c_gen2.py`, `A2345Layout`, `AS220Layout`, `A17C0Layout`, ...). A layout builds on `parameters.py`: `TableLayout` for a recorded device, which declares per message its typed blocks (`FIELDS`: tag -> codec, type byte, field zeros) and its repeated blocks (`GROUPS`: one codec at several tags, a port or a timer per tag), with five hooks for the rest (`timed` gives the timed events a change of values starts; by default none, the C Gen 2 mains and Battery-Only sequence, the car socket's USB-C re-attach, the output timers and the low-SoC `0403`s, the screen wake and timeout, and the backup windows; `sends` says whether a push goes out now: by default always, a C Gen 2 `0490` only with the device-point switch on; `implied` gives the values a set value implies, the C Gen 2's stored TOU plan from `tou_periods` and AC input 0 W with no mains; `finish` reshapes a frame once its fields are written: a grid-loss `0425`, and the C Gen 2 `d9` active period and the AC-charge hold of Peak and of Battery-Only Power; `publishes` says whether a message goes to MQTT in the current state, given any other message's cloud payload; by default always, a C Gen 2 `0503` only while its `0421` reports an active TOU period); `ScalarFieldLayout` for a flat run of single-value fields (the Solarbank `0405`); and `CommandDispatchLayout`, whose `COMMANDS` map a msgtype to a validator that returns the telemetry values an accepted request sets (`{}` for none), or `None` to refuse it. Every request field and every block is a construct `Struct`; a TLV field's length byte is always rebuilt from its value, never written by hand.

A field's tag, type byte and width come from real evidence: a recorded frame, checked by the product's tests, or a cited client's decode. Bytes nothing names stay as recorded, and a rebuilt field keeps them. A product without a layout answers only its recorded requests.

anker-solix-api's maps, hand-transcribed from its `mqttmap.py`, sit in `reference/anker-solix-api-maps/` as reverse-engineering reference for writing a layout. Nothing loads them at runtime.

## Testing

The package's own tests do not depend on any client library:

- known-answer tests: the fixed handshake frames, recorded cleartext round trips, fragment layouts;
- a client-side fixture that drives real `bleak.BleakClient` through the backend and performs the client half of the handshake.

Client libraries (SolixBLE, through its `MockDevice` adapter) test against the emulator in their own suites.

[SolixBLE theme upload](solixble-theme-upload.md) keeps the script SolixBLE #87's A2345 custom-theme upload was run with against the emulator, as a record of how to replicate it.

## Releases

The version is the git tag (hatch-vcs).

| trigger                              | TestPyPI | PyPI | GitHub                                                 |
| ------------------------------------ | -------- | ---- | ------------------------------------------------------ |
| tag `vX.Y.Z`                         | yes      | yes  | release; then every pre-release and its tag is deleted |
| tag `vX.Y.Z-(alpha\|beta\|rc\|dev)N` | yes      | no   | pre-release                                            |
| push to `main` (CI green)            | no       | no   | the rolling `dev` pre-release is replaced              |

Any other tag is ignored, and the build fails unless the built version equals the tag's (`v0.2.0-rc1` → `0.2.0rc1`).
