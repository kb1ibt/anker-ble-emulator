# anker-ble-emulator design

An emulated Anker Solix BLE device (the comms module and the device MCU behind it) for testing BLE clients. It plugs in under [bleak](https://github.com/hbldh/bleak) as a client backend, so the client's real stack (bleak, bleak-retry-connector, the client library) runs unchanged above it. There is no radio and no OS Bluetooth stack.

## Layers

| layer    | module        | role                                                                                                                                                                                                                                                                                                                                                              |
| -------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| frame    | `frame.py`    | `ff09` frame codec: length, pattern, cmd, payload, XOR checksum; fragmenting and reassembly at the fragment cap                                                                                                                                                                                                                                                   |
| fields   | `tlv.py`      | negotiation TLVs (`tag len value`, tags from `a1`)                                                                                                                                                                                                                                                                                                                |
| messages | `messages.py` | one typed layout per negotiation reply (`0801`, `0803`, `0829`, `0821`, `0827 09`, status-only); request fields typed per msgtype (`0003` MTU u16, `0005` method, `0022` time u32 / offset int32 / TZ, `0027` token, `002b` time u32 / account / zone)                                                                                                                                              |
| crypto   | `crypto.py`   | static GCM, session GCM, session CBC, P-256 device key pair                                                                                                                                                                                                                                                                                                       |
| module   | `module.py`   | the comms module: negotiation handlers, link state, authorization policy, the authorize timer, the relay to and from the MCU                                                                                                                                                                                                                                      |
| MCU      | `mcu.py`      | `McuScript`: recorded cleartext replies by message type, and pushes; for a command the product's layout handles and no recording answers, an ack whose status is the layout's check. Its starting state is every named value the recordings carry: the recorded `0490`'s fields (the 0.1 % `pack_soc` / `sub_package_pack_soc`, the bus slots), then the replies and pushes over them |
| layouts  | `layouts.py`  | `LayoutProtocol`, what `McuScript` and `EmulatedDevice` need from a product's layout; `LayoutError`; the TLV type bytes; shared field codecs (`ui`, `ScalarField` and its constructors) |
| parameters | `parameters.py` | `Parameter` / `Parameters`, SolixBLE's TLV shape (optional type byte, optional status prefix); the layout bases `TableLayout` (a recorded device's telemetry, named by per-message tables of `FieldSpec`s and `FieldGroup`s), `ScalarFieldLayout` (flat single-value fields) and `CommandDispatchLayout` (per-command validators), and the table helpers `leaf_zeros`, `struct_zeros`, `one_field` and `flat`; `validators.py` holds `OptionsValidator` |
| products | `products.py` | `Product` part numbers with their SolixBLE class and anker-solix-api category; `Transport`, `Outer`, `Path`                                                                                                                                                                                                                                                       |
| devices  | `devices/`    | `base.py`: `EmulatedDevice`, `ProductDevice` (a subclass names only its `PRODUCT`), `Profile`, `Advert`; one module per product holding its profile and subclass; `solix_c_gen2.py`: the display board's command set and codecs (the C Gen 2 line, and the S2000's shared tags); `prime.py`: what the A2345 and A91B2 share; recorded frames in `devices/data/`                                                                                                                                                           |
| backend  | `backend.py`  | `EmulatedBleakBackend(BaseBleakClient)`: GATT services from bleak's own classes (service `8c850001`, write `8c850002`, notify `8c850003`; `ff09` is only advertised), writes into the module, notifications out                                                                                                                                                   |
| testing  | `testing.py`  | `EmulatedConnection`: patches a client library's `establish_connection` (SolixBLE's by default) to return a real connected `BleakClient` on the emulator; keeps SolixBLE `MockDevice`'s names (`expect_ordered` as an optional write assertion, `refuse_after`, `disconnect`, `send_data`, `new_connection_error`, `allow_connect`, `check_assertions`, `writes`) |

The C Gen 2 models run one display-board build, which picks the model from its factory record, so the MCU answers the same commands on all four: `4100` → `c900` + `c421`; `4057` → `4857`; `405e` → `485e` + `c421`; `4063` → `4863`; `4089` → `4889`; `4090`/`4091`/`4092` → `4890`/`4891`/`4892` + `c421`; `4101`–`4104` → `4901`–`4904` + `c421`. Frames that name the unit (`0421`, `0900`, `0490`, `0425`) come from each model's own recording, and the X models report their base model's PN in them (the A1785's say `A1783`). The identity-free replies are shared (`solix_c_gen2.json`).

C Gen 2 state that follows the request rather than a setting (a1783-control.md "TOU (4090)", a1783-telemetry.md `a3`, `fd`):

- `4090` copies `a7` raw over the stored periods (`d9[6..]`); `a6` sets the count, else the stored count stays, and `a3`/`a4` are never read. An `a7` over 18 bytes (six periods) would overrun the handler's stack buffer, so it is acked and changes nothing. `d9[0]`, the active period, and its Peak / Mid-Peak hold (AC input at 0 W in `a6` and `a7` while the main pack's SoC, c490 `pack_soc` at 0.1 % and the recorded `0490`'s unless set, is at least min(100.0 %, max(reserve, min + 5)); a1783-control.md "TOU" effects; the bus holder's `a5[1]` / `c0[24]` reads the port flow of the DC input against the output, and a charging `a3[0]` reads 0 unless that flow still charges: the cloud `0421` of 2026-10-21 15:49:53, a1783-telemetry.md "Flow state") show only in what the unit publishes to MQTT (`mqtt_frame`): the firmware activates a period only when the unit is bound and on WiFi, and then it has no BLE link, so over BLE `d9[0]` reads 0. When a holding record ends on the RTC, AC input ramps back rather than returning at once: 0 W for 7 s, then the 2026-10-21 16:00:07-16:00:13 samples (86, 57, 178, 770 W, then the full 1290 W) scaled to the charge waiting, in full from 13 s; a record that wasn't holding ends with no ramp, and one running into another held record keeps holding. It follows the RTC, so a clock set re-times it. `0503` publishes only while it is non-zero.
- `4100` sets `a3[10:12]`, the silent recharge power: 1000 when bit 0 of `a2`'s sixth value byte is set (the app's request), else 600 (a bare request or a collector's). The v1.2.1.1 recordings (A1763, A1765) have a 10-byte `a3` without it.
- Any request carrying an `fd` puts up to 15 bytes of it in the telemetry's `fd`; a request without one leaves it.

C Gen 2 mains and Battery-Only Power (`a4[31]` bits 2-3: 0 off, 1 on, 2 cleared by the firmware; `a7[3]` `ac_input_status`: 0 no mains, 1 mains, 2 mains with Battery-Only on), timed from a change of `ac_input_status` or `ac_input_disable_switch` (a1783-control.md "`a4[31]` witnesses", the 2026-10-23 and 2026-10-26 mains runs and the 2026-10-06 Battery-Only steps). `a7[3]` is the live mains-lead read; the auto-off, the accept and the alert key on the power stage's AC-input flag (`0x2000054a` bit 0, hidden `ac_input_flag`), which settles on `a7[3]` after the power stage's report time and the input monitor's 100 ms debounce (10 ticks of 10 ms). The power stage's report time and its charge ramp aren't in MainMcu: the emulator takes them as measured on the two bench runs, as marked below.

- Mains lost: AC input reads 0 W at once, and the flag drops 0.1 s on (the power stage's report: 0 s, measured). With Battery-Only on, `ac_input_autooff_eval` clears it as the flag drops (state 2) and wakes the screen (`a4[21]` 1).
- Off-grid alert: `offgrid_alert_poll_tick` (1 s) commits a flag change on the 5th consecutive tick that differs from the committed value (hidden `ac_input_flag_committed`). The tick's phase isn't modeled: the first counted tick is the change itself, so a drop commits 4 s after the flag, 4.1 s after `a7[3]` (4-5 s on the runs). A committed drop with the outage alert on (`a4[31]` bit 1) pushes the 0x59 off-grid `0425` with the SoC, on the A1783 and A1785 only (the models whose recordings carry a `0425`). A flag back before the 5th tick commits nothing; a committed return posts nothing.
- Mains back: `a7[3]` 1; the flag returns 3.0 s on (the power stage's report: 2.9 s, measured as the accept 2-3 s after `a7[3]`), and a state 2 clears to 0 then (the accept).
- AC charging: `ac_inverter_ctrl`'s 1 s tick enables it once its 7 s one-shot expires, 8 s after the accept. The one-shot counts from the charge branch's first tick (a running timer isn't restarted), taken at the accept since the tick's phase isn't modeled. That is the firmware's upper bound: the power stage's ready bit, which can enable it sooner, isn't modeled. Then the power stage's ramp, as measured on both runs: 118 W at the enable and the full charge 5 s on (the runs: power 4-8 s after the accept, 118 W first, 1 220-1 240 W about 5 s later).
- The full AC charge follows the charge request (a1783-telemetry.md "AC charge request", `chg_src1_ac_limit_calc`): `maxInputPower` (`a3[4:6]` `max_input_power`, 1800 W here) less the AC-out draw (`a7[1:3]` `ac_output_power`), capped at the AC limit (`a4[4:6]` `ac_recharge_power`), + 10 W; AC input is that plus the AC out it passes through. DC-side loads aren't subtracted. The +10 W is the 1200 W limit's steady band (survey mode 1 210 W, main or expansion charging, AC out 0); the modes at the recorded limits are 808 / 1 013 / 1 122 / 1 210 W at 800 / 1 000 / 1 100 / 1 200 W, and a second band at about +20 W (all of 1 100, part of 1 200) is unattributed. The pass-through is recorded at 16-78 W out (1200 W limit, AC in = limit + out + 24 in the main run); the ceiling's cut (AC out over 1800 W − limit) is the firmware's, unrecorded. A change of the limit, `maxInputPower` or AC out moves a charge at the full rate to the new request at once (`chg_src1_ac_limit_calc` re-runs each pass, a1783-control.md "TOU (`4090`)"; its period isn't documented); an AC input set by name off the full charge stays.
- With Ultrafast on (`a4[20]` `super_fast_charge_status`) or a backup window running (the Fast Charging Plan or Storm Guard, `tou_setting_system_status` ≠ 0), the firmware skips the limit and requests `maxInputPower` less AC out. The charge holds to the recorded band: min(`maxInputPower` − AC out, 1 643 W), no +10 W, and AC input adds the AC out. 1 643 W is the mode of the 1 808 frames at 1 553-1 673 W (p5-p95 1 624-1 648 W, AC out 0) recorded in the Fast Charging Plan windows of 2026-09-18 06:00-07:00 EDT and 2026-10-06 19:00-23:00 EDT. Ultrafast on, a window starting or one ending moves a charge at the full rate the same way.
- Battery-Only on with mains in: `a7[3]` 2 and AC input 0 W at once, and while it stays on every frame shows AC input 0 W and no charging state only AC could cause. Off with mains in: `a7[3]` 1 at once, AC charging 7.5 s on (the median of the 6 s and 9 s the collector logs show), by the same ramp.
- AC charging goes into the pack below its cap (`a4[23]`), by the ramp above: with the main below its cap the charge shows on the bus holder's flow; with the main at its cap an attached expansion below its own takes the charge and the bus (`c0[24]` 2); with every pack at its cap, no AC input.
- A name the triggering change sets itself stays as set; each step acts only if the state it needs still holds when it comes due.

C Gen 2 car socket and the USB-C ports (a1783-control.md "`4102 a2` and the USB-C ports"): an edge of `car_charge1_output_status` (`b2[0]`) either way, from a `4102 a2` or `set_values`, re-attaches each USB-C port (`pd1`-`pd3`) that reads `[0]` 0 with a device in it.

- The device is two hidden inputs per port, no field carries them and the app has no name for them: `<port>_device_plugged` (0/1) and `<port>_device_power` (W). Unset, `pd1` holds the A1783 recording's 86 W load and `pd2`/`pd3` none; a port without a device stays 0.
- The port's `[0]` reads 1 1 s after the edge (0-3 s in the collector logs), and its device's power 3 s after that (+3-8 s from the edge), adding to `a6[0:2]`, and the port flow follows (an idle main on the bus reads `a5[1]` 1). A port detached again before then draws nothing. `b2[1:3]`, the other ports, USB-A, AC and `a3[0]` don't move.
- A port reading 1 holds through the edge. A port power the edge's own call sets stands, with no power step after it.

C Gen 2 `0403` events (a1783-control.md "`0403` push"): MainMcu's own push, `a1 01 31 · a2 02 01 <code>` with no `fe`, built on every model since no `0403` is recorded.

- Output timers: `ac_timer_value` (`a4[0..3]`, `4101 a3`) and `car_charger_timer_value` (`a4[8..11]`, `4102 a3`) count down 2 s at a time while their output is on, 0 disabling. At 0 the output goes off (`a7[0]` / `b2[0]`) and `0x55` (AC) / `0x56` (car) goes out; the car socket going off is a socket edge (above). With the output off, the next 10 ms pass clears the timer: one set then reads 0, and switching the output off discards the rest (a1783-control.md "Output timers").
- Low SoC: the main pack's SoC (`battery_level`) falling to 10 % sends `0x52`, and to 1 % `0x50` (firmware only, `soc_floor_event_eval(1, ...)`), after 3 evaluations at or below the floor: one per MainBMS block-0 reply (500 ms), and one per block-1 reply too with an expansion attached (`sub_package_connection_status`), so 0.49 s with one (BLE 2026-10-15 05:00:23) and 1 s without. Each re-arms once the SoC is above its floor; one evaluation above it resets the count, so a SoC back above it first sends none.

C Gen 2 screen (`a4[21]` `screen_switch`, a1783-control.md "`4103`"): a wake turns it on and (re-)arms its timeout, `a4[15..16]` `screen_off_time` seconds (0 = never), after which it goes off. Wakes: `screen_switch` set to 1 (`4103 a2`), and a change of brightness (`4103 a3`), language (`4103 a9`) or the car socket (`4102 a2`), the setters the app_log shows waking it; the other `4101`-`4104` setters and the `40xx` ops leave it. The mains auto-off wakes it too. A wake runs at once, so the command's own reply shows the screen on.

C Gen 2 backup plans (`405e`, a1783-control.md "`005e` means different things across families" and the `d9` tail): table 1 is the manual plan (the app's Fast Charging Plan, `manual_backup_switch` and `manual_backup_start_time` / `_end_time` in the `d9` tail), table 2 the three Storm Guard entries (`auto_backup_switch`, and the hidden `auto_backup_plans`, 3 × u32 start / end UTC, empty unset; no field carries it).

- `405e` needs `a3` 3. `a4` 2 clears both tables and both switches and reads nothing else. Otherwise, in the firmware's order: `a5` sets that table's switch (the plan switched off also turns every Storm Guard entry covering now into the never record), `aa` 1 cancels the running window (its entry and every Storm Guard entry covering now become the never record, and a Storm Guard cancel turns the plan off where table 1 covers now; nothing while no window runs), then `a7`'s plans go into table 1 (the first) or table 2.
- The window pass runs 100 ms after any change of a plan, a switch or the clock, and at each window's start and end (every 100 ms within a second of one): a running window keeps going until it ends or its switch goes off; with none running, Storm Guard is chosen before the plan. A start posts `0425` `0x0a` / `0x07` with the window's epochs, sets `d9`'s type and active pair, and moves an expansion's charge and the bus to a main pack below 100 % (`c0[24]` 0, `a5[1]` 2, `a3[0]` following); an end posts `0x0b` / `0x08` with zero epochs; a hand-over between types changes the type and pair with no `0425`. No window runs before the RTC reads 2025. The `0425`s go out on the A1783 and A1785 only, whose recordings carry one; the others' `d9` tail moves all the same.

C Gen 2 flow state (a1783-telemetry.md "Flow state"), filled from the port powers, the pack currents and the bus holder. A flow-state name set by name (`charge_discharge_status`, `sub_package_status`, `work_status`, `on_bus_pack_status`, `total_input_power`) reads as set until its inputs next change: the follow below skips a status set by name since the change of the pack currents that queued it (the hidden `flow_statuses_held`, which the next such change starts over). The Battery-Only / Peak hold still applies to a by-name `a5[1]` / `c0[24]`, since it reshapes the published frame:

- The port-flow code: 2 with Σ input (AC in plus DC in, `a6[2:4]` + `a6[4:6]`) over Σ output (`a6[0:2]`), 0 with no output, else 1, at once (no debounce). It shows in `a5[1]` while the main holds the bus and in `c0[24]` while the expansion does, the other reading 0. With no `c0` (the C1000 Gen 2) the main always holds it.
- The pack currents (`.14.29` / `.14#1.29`, 10 mA, + charging): the bus holder carries the net port flow over its voltage (`.15.3` / `.15#1.3`, 0.1 V): 10 mA = (Σ in − Σ out) × 1000 / V, the units of a1783-telemetry.md's current source; the other pack carries 0. A current given in the same change, by name or drawn, stays.
- `a3[0]` `work_status` is the main pack's status and `.23.7` `on_bus_pack_status` the bus holder's: 2 at +0.3 A (30) or more, 1 at −0.3 A or less, else 0, settled 2 s after a change of the settled value (the 20-sample test; 2.0-3.0 s on the wire, e.g. 2026-10-26 15:29:01 → :02). A charge needs `flag_00c7` on the main, the expansion's charge reads 0, and `a3[0]` reads 0 while the expansion holds the bus. Battery-Only Power switched on with mains in leaves `a3[0]` charging for its lag (19:39:18 → 19:39:22); the Peak hold, built per frame, shows it idle at once.
- The emulator takes `.23.2` and `.23.4` from the `0421` state: `.23.2` is `a6[0:2]`'s `total_output_power`, one value, and `.23.4` `total_input_power` is Σ input. The recordings agree within 5 s in 5 432 of 6 464 pairs for `.23.2` (at most 86 W apart) and 6 395 of 6 464 for `.23.4` (at most 20 W).
- Each pack's battery level shows its 0.1 % SoC: `battery_level` (`a5[2]` = `a6[8]` = `.23.1`) = floor(`pack_soc` / 10), and the expansion's from `sub_package_pack_soc`. A level set alone puts the SoC at its whole percent; set together, each stays as set. The lag of 1 at a whole-percent boundary isn't modeled.
- The derivation runs on every change of values (`set_values`, a draw, a command) and in every timed step that moves the port powers or the bus, before pack selection reads it.

C Gen 2 versions that drop out (a1783-telemetry.md "Versions (`f9`)"): `f9[12:16]` `inv_version` reads only while the ACDC stage is energised (mains in, `a7[3]` 1 or 2, or AC output on). It shows 1 s after the stage comes on and reads 0 from 1 s after mains goes, or 49 s after AC output switches off with no mains (the recorded bracket is 47-49 s); the stage back before then keeps it. With both AC paths off, `f9[4:8]` `sub_mcu_version` reads 0 for 1 s once a minute, on a timer that free-runs from the MCU's start (the phase is the emulator's). The hidden `_inv_version` / `_sub_mcu_version` hold the version while it reads 0; the `4866` log chunk's header reads the same values, as the firmware's does (both read `version_get` live). Not modeled: the other subMCU zeroings (idle sleep entry, 7 failed DSP reads, power-up).

C Gen 2 pack selection (MainBMS `pack_select_eval`, firmware/mainbms-control-fsms.md "Pack selection"; a1783-operation.md "Observed handovers"), with an expansion attached. The hidden `pack_on_bus` (1 main, 2 expansion; unset, the expansion, as on the A1783 recording) holds the selection, and each rule is re-checked on every change of values. The emulator stands in for the per-pack charge and discharge allowances by SoC: a pack may charge below its cap, and the expansion's discharge allowance reads 0 under `min_soc` + 0.9 % (unconfirmed; see :164 below). The hidden `sub_package_path_hold` stands for the expansion BMS's own `raw+0x95` (its CAN `0x045a` report, a contactor / active-path hold; firmware/mainbms-control-fsms.md, the note after "Latches"): clear unless set by name, and while set it blocks both handovers from the main to the expansion (:164, :165). Which pack record holds which limits, and whether the BP2000 enforces `min_soc` itself, are open in the firmware notes (firmware/mainbms-control-fsms.md "Current-limit sources"). The SoCs are the 0.1 % `pack_soc` / `sub_package_pack_soc`. At each switch the `0490` slots `.15.5` / `.15.6` read (8, 9) for the new holder, (3, 9) when it is quiet at or above its cap, and (3, 3) for the other (a1783-operation.md "`.15.5` against the limits"):

- The charge-cap latch (:193, hidden `charge_cap_latch`; firmware/mainbms-control-fsms.md "Charge-cap latch counters"): sets with the on-bus pack charging at or above its cap and a source in, whatever the expansion's SoC, switch or path hold. The first time that takes 1 s; the firmware never resets that count, so after it the latch sets at once whenever the condition holds (hidden `charge_cap_latch_primed`, kept for the device's life; a charge shorter than 1 s doesn't add to it here, where the firmware's count would keep it). The source is `flag_00c7` (AC in, `a7[3]` 1 or 2, PV in, or the alternator charger in its Charging Mode) or ALT byte +9 at 2. That byte is hidden `alternator_byte_9`, default 0: the `0x0c01` frame's +0x09 (block 0xe +0x36), separate from the mode at +8, meaning unread (firmware/mainbms-control-fsms.md, "ALT byte +9" below the latch table). It clears in discharge (the on-bus pack's flow 1). With `flag_00c7` gone it clears at once, or 15 s (1 500 steps) later while +9 is 2; `flag_00c7` back within that keeps it. The firmware resets that count only when `flag_00c7` is 1, not on the clear (the same section), so once it runs out +9 alone sets nothing until `flag_00c7` returns (hidden `charge_cap_latch_spent`). Setting the latch clears the discharge latch, and the discharge latch arming clears it (:194). "Charging" and "discharge" here are the on-bus pack's current (`.14.29` / `.14#1.29`, ±0.3 A), not its port flow, so a pack charging with no source in (`pack_current` set by name) is the +9 path's case.
- Main to expansion, charge (:165): with the charge-cap latch set, the charge moves to an expansion below its cap, switched on, with its path hold clear: `a3[0]` and `a5[1]` 0, `c0[24]` 2 (2026-10-06: 95 % at 20:20:00, moved at 20:20:03). Set under the path hold, the latch moves the charge as soon as the hold clears.
- Main to expansion, discharge (:164): the discharge latch (:194 (a), hidden `discharge_latch`) arms once the main, not charging (by its current) and above `min_soc` + 0.9 %, has dropped 1.0 % from its baseline, and stays set until the charge-cap latch sets. The baseline (hidden `discharge_latch_from`) is re-taken only while the latch is clear: as the main charges (the SoC when charging stops; the firmware's 1 s settle after that isn't modeled), when the latch arms, and when the charge-cap latch sets or clears; never on a switch or a SoC rise without charging, and first seen as the main's SoC before the first change (firmware/mainbms-control-fsms.md, the list after "Latches"). The expansion's own baseline and drop aren't modeled. With the latch set, more than 2 s after the last switch, an expansion whose discharge allowance is non-zero and path hold clear takes the discharge (the path doesn't re-check the expansion's SoC; :194 (a)'s SoC test is the main's): `a3[0]` and `a5[1]` 0, `c0[24]` the port flow. This is how a reverted `min_soc` hands the bus back (a1783-operation.md "`min_soc` as a lever"). An expansion inside the band between `min_soc` and `min_soc` + 0.9 % never gets it back: after the 2026-09-03 03:29:25 handover `c0[24]` read 0 to 08:00 while the main fell 96 → 85 % (a1783-operation.md "Expansion to its floor"). The latch still arms there on the main's own drops, so another gate held the path off: the expansion's discharge allowance or its path hold, which one unread (firmware/mainbms-control-fsms.md, the note after "Latches"). The emulator's allowance stand-in reads 0 over the band to match.
- Expansion to main, discharge (:170): with the charge-cap latch clear and the expansion's SoC under `min_soc` + 0.9 %, checked from 3.01 s after it took the bus on (`pack_on_bus` set by name included): `c0[24]` 0, `a5[1]` the port flow, `a3[0]` following (2026-09-03 03:29:25). A `min_soc` raised over the expansion's SoC does the same (2026-08-31, main 100 % under a 100 % cap). The row also needs the main's charge allowance non-zero; which record holds it, and its value at the main's cap, are open, so it is taken as non-zero and the at-cap behavior isn't modeled. An expansion charging from under its line keeps the bus only while the latch holds: handed the charge at the main's cap (2026-10-06, expansion at 5 %), it stays, even quiet, until a discharge or the source going clears the latch.
- Expansion to main, discharge (:172): the expansion's discharge allowance at 0 for 300 steps. With the stand-in above, that allowance is 0 only at or under `min_soc`, inside :170's line, so :170 moves the bus first and :172 adds no switch of its own.

Not modeled: the once-per-boot switch (:163), the pack-switch code (:167, :173), the rows that turn on the allowances alone (:168, :169, :171), the expansion's own SoC drop arming the discharge latch, the discharge latch's high-current path (:194 (b)), the charge-cap latch's other set paths (:193: the idle count, which runs while `cfg_get_byte3` ≠ 1, charging included, for 60 s or 3 s by the BP2000's min cell voltage; the no-SoC count `0x20000b7a`, which runs while no pack discharges with output on and resets on a pack discharging, on `cfg_get_byte3` == 1, or on vext < 56.0 V and vext < vbat + 0.3 V with output on; `charge_cap_latch_eval` resets the idle count on the same three conditions (fsms "Charge-cap latch counters"); no value carries the min cell, vext or vbat; and the fault path), the latches' `pb1_low_handler` reset, the expansion's quiet 13 at its cap, `.15.5` following power or SoC between switches, the one-frame `c0[24]` flap after the cap handover, and the bus voltage `.15.4`.

C Gen 2 expansion switch (`4104 a4`, a1783-control.md "`4104`"): `c0[28]` shows the app's value at once (the display board's override), and 2 s later the block-0xf reread pushes a `0421` with `c0[28]` back on the expansion's own switch-on state (`flag_0b56`; hidden `expansion_switched_on`, unset = on; MQTT 2026-10-06 19:43:30 → :32). An on reaches the expansion. An off reaches it only with no external charge source (`flag_00c7`); then the selection returns to the main at once (`c0[24]` 0, `a5[1]` the port flow), and while off the expansion takes neither charge nor discharge. `flag_00c7` is `.14.30` bit 0x02 (AC in: `a7[3]` 1 or 2, Battery-Only included; a1783-telemetry.md "`.14.30` bits") or bit 0x01 (PV in). Not modeled: `flag_0a55` and the on it gates, the PC12 gate on the off's CAN send, the pack button, and the locate blink (`a5`).

C Gen 2 AC top-off (a1783-telemetry.md "AC top-off burst", "Top-off hysteresis"): with mains in, Battery-Only Power off and the main on the bus (`pack_on_bus`), the main pack's 0.1 % SoC (`pack_soc`) falling below the clear threshold (`max_soc`; 98.5 % at a 99 % cap, 99.9 % at 100 %) starts a burst at once: AC input the full charge (the limit + 10 W), `a5[1]` the port flow with `a3[0]` following. 60 s later (2026-10-20 04:57:40, off by 04:59) it ends at the set threshold (`max_soc` + 0.7 %; 98.9 % / 100.0 %): AC input 0 W, `a5[1]` the port flow, `pack_soc` at the set threshold. The burst refills a dip just under the clear threshold; from deeper, the charge runs on to the set threshold, which no value models, so it isn't ended. An expansion holding the bus (its own band) isn't modeled.

C Gen 2 OTA precheck (a1783-control.md "`4089`"): the pair `ota_enable` / `ota_block_reason` is 0 2 while the main's SoC, or an attached expansion's, is under 6 % (whole percent), else 1 0. When a SoC change changes the pair those SoCs give, MainMcu sets it and pushes `0489` 0.15 s later (MQTT 2026-10-06 20:21:28, BLE 2026-10-15 07:45:55). The pair compared is the one the SoCs give, not the recorded one (every recording carries 0 2 at a full SoC); a call that sets the pair itself keeps it. Upgrade and BMS boot mode aren't modeled.

C Gen 2 Battery-Only Power at the floor (a1783-operation.md "Battery-Only Power at the floor", 2026-10-15): with Battery-Only on and mains in, the main's `pack_soc` falling under `min_soc` + 0.9 % (its BMS's low-battery bit) drops the mode to state 2 at once, mains accepted (`a7[3]` 1; 05:45:36); AC charging starts 4 s later by the cap rules, from the power stage's 118 W first step (05:45:40-45: 96 → 609 → 1 227 W); back over the line, state 2 clears to 0 1 s later and the screen wakes (05:46:20 → :21). Later the expansion takes the bus at the main's cap (the pack handover). The `dc` low-battery code, the outputs' dip during the drop and the min-cell path aren't modeled.

Module session ops below `0x40` are the ESP32's own, answered on `03 00 0f` once the link is authorized. `0030` → `0830` is built on every build from the module build, the device firmware and the product's names (C Gen 2: `<pn>_low`, `<pn>_mcu_low`, `<pn>_esp32_low`; Prime: `<pn>`, `<pn>_mcu`, `<pn>_esp32`). The A1783's recorded `0020`, `0028`, `002e`, `002f`, `0036` and `0038` replies come only with v0.3.3.0, the build they were recorded on.

Every wire parse and build is a [construct](https://construct.readthedocs.io) layout: the frame (`PATTERN_LAYOUT`, `COMMAND_LAYOUT` with the link flags and 12-bit msgtype, `FRAME_LAYOUT`, `FRAGMENT_LAYOUT`), the fields and messages, the key material (`GCM_KEYS_LAYOUT`, `CBC_KEYS_LAYOUT` over the shared secret), the P-256 point (`POINT_LAYOUT`) and the advert record (`ADVERT_LAYOUT`). Frames and parsed messages are construct `Container`s; plain classes hold only settings and link state, which have no wire form.

The module and MCU layers are synchronous and transport-free: a write in, a list of frames out, each with a delay. Time is injected, so timers are testable without sleeping.

## Behaviour emulated

- Frames: `ff09 | len LE | pattern 03 <composer> <channel> | cmd | payload | xor`. Replies to module opcodes echo the request pattern; device-originated frames use composer `01`.
- cmd: `0x40` encrypted link flag, `0x80` fragment flag, msgtype = the low 12 bits, response = request `| 0x800`.
- Fragmenting: frames longer than the fragment cap (ATT MTU − 3, 253 by default) split into frames of the cap, each payload led by `index << 4 | total`.
- Encrypted outer: `4001 4003 4029 4005 4021` under the static AES-128-GCM key, nonce and AAD; `4021` answers the device's fresh P-256 point; the shared secret is the raw X coordinate; the session runs AES-128-GCM with key `ss[:16]`, nonce `ss[16:28]`, the static AAD and a 16-byte tag.
- Plain outer: `0001 0003 0029 0005 0021` in clear, then AES-128-CBC with key `ss[:16]`, IV `ss[16:32]`, PKCS7 out; on the way in only the last pad byte is checked (1-16, that many bytes stripped).
- Port context: an encrypted frame with no session opens under the module's key and IV, CBC unless the link's `0001` was encrypted (then the static GCM key). They are zeros at boot, the account (`0001 a2`, else `ANKER_DEFAULT_ACCOUNT_1`) and serial after a cleartext `0001`, the static key and IV after an encrypted one, `ss[:16]` / `ss[16:32]` after `0021`, and the derived key after a legacy confer. A new link keeps them, so an encrypted frame before its `0001` meets the last link's key.
- Authorization: `0027` with an enrolled token authorizes at once; a new token gets `09` with the confirmation window and is granted by a simulated button press (`4827 00` on `030101`). Opcodes `>= 0x40` reach the MCU only once authorized.
- Module policy: v0.3.3.0 enforces the auth mode on the encrypted outer: it drops a cleartext `0001`, refuses a non-ECDH `0005` method, and answers `0027` only after an encrypted ECDH. Earlier builds (v0.2.9.7, v0.3.0.6) accept either connect frame.
- The authorize timer: an unauthorized link drops 30 s after connect, or `auth_timeout + 5` s after a confirmation window opens, checked every 10 s.
- The MCU's RTC: an accepted `0022` sets it to local time, `a1` UTC less the `a3` offset (seconds west), and it then runs on the device clock; a `0022` whose UTC is before 2023-11-25 08:13:20 (`0x6561aca0`) is acked but never reaches it; before any clock set it counts from 0 (a1783-control.md "Clock"). The module keeps the UTC epoch beside it, which a push's `fe` carries. The `0022 a5` POSIX TZ is stored (a bare `GMT0` becomes the `a3` offset; an unparsed string keeps the stored one) and the module's TZ timer sends the MCU the zone's current offset 100 ms later, then every 30 min, every 300 s within 30 min of a DST change and every 5 s within 300 s, so the zone overrides `a3` and DST switches with no new `0022` (a zero offset goes as -1). The MCUs apply their own rules on top: the C Gen 2 MainMcu keeps its previous offset for a 0 or -1 (a1783-control.md "Clock"); both Primes set clock and RTC one second past the UTC, the A2345 only from `0x66311580` (2024-04-30 16:00 UTC), and apply any offset as sent (prime-a2345-a91b2.md fid 0x10 ops `0x26` / `0x09`).
- Account-gated clock set `002b`: `a1` UTC, `a2` account, `a3` = signed hours then tenths of an hour, all three required (`04` otherwise). `a1` and `a3` are read at full width with no length check, so a short or empty one reads the bytes after it. `a2` passes when the account the last `0023` bound starts with it, so an empty `a2` always passes (`02` otherwise). The bound account lives in the module's RAM: it outlives a link and a factory reset, and a new module starts with none. The zone sets the RTC through the same floor as `0022`, with the firmware's sign quirk: the offset is `hours × 3600 + tenths × 360` seconds east for a positive hour, `|hours| × 3600 − tenths × 360` east for a negative one, so a zone west of UTC lands east (−5 h 5 tenths → 16 200 s east). Like the other negotiation ops it needs no authorization and runs in clear; the reply is status only (a1783-control.md `0x02b`, anker-crypto-and-negotiation.md `check_account_id`).
- Decrypt failure: an encrypted request the link's current key can't open gets the dispatcher's one-byte status, sealed under that key, on the request's pattern with msgtype `| 0x800`: `08` for an empty payload or a CBC one that isn't whole 16-byte blocks, `01` for a failed decrypt (a bad GCM tag or one under 16 bytes, a CBC pad byte of 0 or over 16). The link stays up and the MCU never sees the frame. An encrypted `0001` switches the link to the static GCM key first, then fails like any op; `0021` drops either failure, and `0022` sends `08` but drops a failed decrypt (anker-crypto-and-negotiation.md "Decrypt-failure `01`").
- Timed events: the module keeps a queue of events on the device clock, checked every `push_period` (0.1 s). Each event's action sees the set values and the device's whole state (the recorded values, set ones over them, the RTC in local seconds, and the UTC epoch a push's `fe` carries; a clock set puts the RTC at the `a1` UTC less the `a3` offset and the epoch at the UTC itself). It sets values or clears them back to the recording, sends recorded pushes and frames it builds on an authorized link, and can start the next event, timed from its own due time so a cadence holds when a check catches up. Scheduling an event replaces any queued one with its key; link events (a burst, a factory reset's drop) end with the link; one that falls due with no link sets its values and sends nothing. A layout's `timed` hook starts events from a change of state, whether from `set_values` (a change made on the unit), a command (its request msgtype passed along, so a layout can tell the two apart), an on-unit event no field carries (`unit_event(name, **hidden)`, a screen switched on the unit, say, with its own data as hidden `_` values), or a clock set (`0022`/`002b`, which re-times what depends on the RTC); those due at once run there, so a command's own reply and follow-ups carry what they set, and their pushes follow the reply. Each of those changes (and `set_cloud`) first runs whatever already fell due, so an overdue event sees the state it fell due in, and a command's side effects see the same whole state a timed action does. An event run late (a long advance between checks) reads the RTC and epoch at its own due time, and its pushes are built with that RTC. The clock is injected: `ManualClock.advance` runs everything that falls due on the way, `ManualClock.jump` moves past it (each bypassed event sets its values, sends nothing), and `ScaledClock` runs real time at a chosen speed.
- Bursts: the Prime MCUs answer `420b` with `4a0b` and the first of 10 `4303` pushes, then push the rest 1 s apart (a link event); a `420b` mid-burst sets the count back to 10.
- Factory reset (`Profile.factory_reset`): the A2345's `4201` acks `00`, clears every set value back to the recorded frames and forgets every enrolled token, then drops the link after the MCU's 10-tick debounce (1 s, checked every `push_period`); the next `0027` needs the button again (prime-a2345-a91b2.md "Commands" `4201`).
- Routing: a session request's `a1` is its route, destination in the high nibble and source in the low (`21`: BLE to the MCU). The module answers its own ops (below `0x40`) on the arrival port whatever the `a1`, on the fids its handlers serve: the WiFi handler's `0x22`-`0x25` on `0x0f` and `0x13`, every other op on `0x0f` and `0x11`. Opcodes are fid-scoped: the session `0022` on `0x0f` is scanWifi, not the negotiation `0022` clock set. For the MCU it relays only a request routed from BLE to the MCU on fid `0x0f`; it drops one with no route, an unknown source or an unhandled destination, and answers a logging-channel (source `a`) request itself with status `00`. An MCU request on fid `0x11` (`030011`) or `0x13` draws no reply. Every MCU frame on the BLE link is routed `a1 31`.
- Relay: post-authorization requests go to the MCU script; its cleartext replies and pushes are encrypted for the session and sent on `03010f`. A command the product's layout handles with no recorded reply gets `<status> a1 01 31`: `00` when the layout's validator accepts its values, `04` when not.
- Command table (`Profile.known_commands`): a request nothing recorded or modeled answers gets the firmware's own answer from the product's table, an ack with its status or no reply; a request past the table's last op gets `past_table_status` (none: dropped); anything else is dropped. The C Gen 2 display board acks `4051`/`4059` `00` (`4051` restores the factory block's settings and turns Ultrafast off; the four the firmware recomputes per region, recharge power, frequency, temperature unit and language, keep the unit's own values), answers the `4065` log-size read with the 250-byte header chunk alone (250 bytes, 1 chunk; `READ_REPLIES` builds a read's own fields), answers `4066` chunk 0 with that header, laid out by the MainMcu version the `f9` reports (a1783-control.md "BLE log upload (`4065` / `4066`)"): from v1.2.1.6, `[` + the RTC as 8 hex digits + `00`, the 17-byte `0421` `a2` serial and 13 `,d.d.d.d` versions; below it, `[RTC]`, the first 16 bytes of the serial, `,,` and 9 five-character versions whose first digit is `'0'` + v/100; the slots no frame reports are the firmware's constants (boot 1000, LCD 196, USB-PD 310), and any later chunk gets no data, and drops `4064` before an OTA start and every op outside its table (a1783-control.md "Command map"). The Prime MCUs ack every real handler `00`, op past the table included, say nothing to their no-op stubs, and drop an op below `0x200` they don't handle inline (prime-a2345-a91b2.md "Commands"). Two A2345 handlers answer by branch: `4212` and an accepted `4222` send nothing, while a `4222` without `a2`, or a `420d` whose `a2` isn't typed `02`, gets `04` (`SILENT` marks a layout command whose accepted request goes unanswered). A `4222` of 0 or 1 sets the `4a02` `a6` switch; a nonzero `420d` draws a `0305` with trigger 0. The A2345's `4218` answers each USB-C port's offered power-sharing budget, looked up by which USB-C ports are active and whether a USB-A port is (prime-a2345-a91b2.md "`4218` field5 power-sharing budget"), then each USB-C port's `0303` output status. The A91B2's `4202` answers with the snapshot's `ac` byte (screensaver switch and theme), the field its `4205` writes (a theme past 2 stored as 2), then the clock.
- Setter replies and pushes from captures: a layout's `ECHOES` name the request fields an accepted ack carries back after its `a1` (the Prime port setters `4207`/`4208`/`4209`: the port, `4208`'s slot, and the clock, the request's standing in for the device's). Its `FOLLOW_UPS` are the pushes an accepted command can draw, each built from the request and the device's state before and after it (`McuScript.state`: every named value the recordings carry, the set values over them), or skipped when the change doesn't trip it; a push ends with the request's `fe`. Its `SIDE_EFFECTS` are further values a command sets from that state (`4208`'s conflict-clear). A refused command gets the bare `04` ack and no push.
- Prime pushes (prime-a2345-a91b2.md "MCU pushes"): `0302` after every A91B2 `4207`, and on the A2345 when a `4207` changes the switch; `0307` when a `4209` arms or disarms a countdown, not on a re-arm (arming starts the remaining time at the seconds set; a disarm zeroes it, except on the A91B2's AC ports, where it copies the seconds back into it; the A91B2's `0307` puts the remaining time before the seconds); `0308` when a `4208` half collides with the port's other half (both enabled, the unset `ff` included, at the same time on a shared weekday), which disables the other half and reports it, before the `4208`'s ack (`LEADING`); on the A2345, `030f` (the designated-port mask) when a `420c` or `4206` changes it, `420c` entering Port Priority (mode 2) and a `4206` out of it clearing the designations. A once half's weekday comes from the date the MCU stores off the wire, which the emulator doesn't keep: two once halves count as one day, and a once half never meets a repeating one.
- Prime timed events: a pushed timer frame ends with the device's UTC epoch as its `fe`, where a command's pushes carry the request's. On the A2345 a change of `charging_mode` (a `4206`, `420c` entry, or `set_values`) sends `030d` (the mode, `b8` and the designated-port mask, as they stand then) 3.3 s later on the fixed mode-apply settle counter, the same for `420c` and `4206` (prime-a2345-a91b2.md "MCU pushes" `030f`), and drops every port block (`0303` and `4a00`) to status 0, 0 W for 8 s while the ports renegotiate (doc "Commands" `4206`; assumed for `420c` entry too, the same mode-apply path). Each block then gets back what it had: its set value, else its recording; one set during the window keeps that value, and a further mode change in the window keeps the one window.
- Prime countdowns: an armed `4209` countdown's remaining time counts down once a second, ticked into the values so every frame (a mid-countdown `4a00` included) reads it as it stands. Arming, re-arming or setting the remaining time restarts the count from it; a disarm drops the pending expiry. At 0 the firmware (not a command) switches the port off (its record's `[0]`), sends `0302` (the port, off) if it was on, and `0307` with the countdown disarmed, its remaining time 0, or the seconds set on the A91B2's AC ports (doc "MCU pushes" `0302`/`0307`). The A2345's switch watcher sends `0302` only on a change; the A91B2's timer is assumed to do the same, though its `4207` reports every write.
- Prime timed tasks: an enabled `4208` half (switch 1; the unset `ff` never fires) fires at its hh:mm on one of its weekdays (bit 0 Monday) by the RTC, local time, so a clock set (`0022`/`002b`) re-times it. Firing is the firmware's per-minute run, not a command: an on-time switches its port on and an off-time switches it off (the record's `[0]`), with `0302` if the switch changed (the same change rule as a countdown). A repeating half fires again on its next weekday; a once half (weekdays 0) fires at its next hh:mm, since the emulator doesn't keep the stored date, and is then disabled and reported in `0308` with en 00 (doc "MCU pushes" `0308`). Disabling or rewriting a half drops what was queued.
- A2345 owner (`420a`): the recorded `4a0a` answers every send. An accepted `420a` (`a2` a 2-character country, `a3` a 40-byte owner or a 36-character UUID) stores its owner, which no frame carries; a fresh device has none, so its first `420a` counts as a change. Only a different owner is a change (prime-a2345-a91b2.md "`420a`", `region_owner_store_if_changed`): it puts a custom-upload screensaver theme (5) back to 0, and leaves custom charging mode 5 for the last mode below 5 the device changed to (`0x2000af62`, copied on every such change and held in no frame; 1, AI Power, from the factory). That mode change reports `030d` and renegotiates the ports like any other; no `030d` is skipped. An identical re-send does nothing. `4211 a2` 0 in mode 5 leaves custom mode the same way; `4211 a2` 1 has no documented effect and changes nothing.
- A2345 screen reports (prime-a2345-a91b2.md "Screen reports"): a setting changed on the unit, which is `set_values`, sends its report at once: `030a` the brightness (`b3`), `0309` the timeout (`b0`), `0310` the knob direction (`b4`), each `a1 31 · a2 02 01 <value> · fe`, without the `a3` the doc brackets as optional (none recorded); `030b` the screensaver byte `af[0]` (switch, holiday, theme) in `a2` and the theme id in `a3 05 04`, as recorded. The same change from an app command (`4203`/`4204`/`4205`/`420e`) sends only its ack (the recorded `0a05`s draw no `030b`).
- A2345 USB-C device identity (prime-a2345-a91b2.md `bd`/`be` rows, "`bb` Maximum Compatibility", "AI device identity (`be`)"): `A2345.plug(port, vid, pid, ext=None)` plugs a device into USB-C port 1-4, setting its attach flag (`pdN_output_status`); `unplug(port)` clears the flag and the port's power. Any change of an attach flag sends `0304` at once (firmware-only, none recorded: `a2 03 03 <u16 LE bitmask>` plus `fe`, assumed in the `0300` bitmap's order, bit 0 C1 ... bit 5 A2, set where attached). With `bb` 1 the device's VID and PID reach `bd` (`pdN_device_vid`/`_pid`, `4a00 bd` and `0303 a8`) 4 s after attach and `be` (`pdN_device_class`/`_code`, `be` and `a9`) 1 s later: the class by the VID table, the code by the PID's default row (`ffff` for any other), and `05ac:7800` to none, the doc's one case of it. With `bb` 0 the port stays `{fffa, fffb}` / `ffff` until `bb` turns 1, 6 s after which every attached device is read; a port identified before `bb` turns 0 keeps its identity. A detach clears `bd`/`be` at once and drops a pending read. `ext` is the extended identity word a revision 4 or later PD controller reads (in no frame; `None` for an older controller, read as `ffff`): with class 1, a PID's variant row whose variant equals a non-zero, non-`ffff` `ext` replaces the default code (e.g. `7117` with `012c` → 55, iPad Pro 11" M4, against the default 54, iPad Pro M4 series).
- A2345 theme images (prime-a2345-a91b2.md "`4311` theme image state", "Theme upload"): a network (`0x83`) or custom (`0x85`) `4205` needs a non-zero `a3` id and `a4` CRC, `a5`, and a URL of at least 16 characters in `a7` or `a6`; otherwise it is acked and dropped. An image stored under that id with that CRC is shown at once (`af`: on, theme 3 or 5, the id) and `4311` reports state 1; any other is staged and `4311` reports state 4, the app's cue to upload it. `4220` opens the upload (kind 0 network or 2 custom; any other kind gets no reply), zeroing the expected index and the CRC32. Each `4221` chunk at the expected index extends the CRC (the last over the bytes the size leaves); `4a21` answers `00` + the next index after each `a6`-chunk window and nothing in between, and on the last chunk `10` + the count when the CRC matches (the image stored and shown, `4311` 1 sent before that reply) or `11` + the count when it doesn't. A wrong index is dropped, except on a window's last slot, which answers `12` + the expected index. `4311` carries no clock (`UNCLOCKED`). Each accepted chunk is written as flash keeps it, at `a7` × its index: kind 0 as sent; kind 2 (custom) through one AES-128-CBC stream per `4220`, the doc's key and IV, each chunk encrypted over its length rounded up to 16 with zeros and chained from the cipher block before it, flash keeping only the received length (prime-a2345-a91b2.md :483-485, the chain in :485's first sentence). The real cipher is used, not a "last chunk % 16" rule, so any chunk size that breaks the chain fails as the device does: an unpadded last chunk that isn't a 16-multiple, or an `a7` that isn't one. The upload's own replies don't see it (`4a21 10`, `4311` 1 naming the upload's id and kind). The screen draws an image whenever it is shown: at the upload's end, a `4205` for a stored slot, and a `4222` change on screen 5 (hidden count `_screen_draws`). The draw ("Theme image display") checks the stored size (1-65 534 B), decrypts a custom image in one pass from the fixed IV over the size rounded up to 16 (flash past the stored bytes reading `ff`), compares the CRC over the size, and parses the JPEG header from byte 0: SOI; APPn, COM and DRI skipped by length; DQT 8-bit with ids 0-2; DHT ids 0-1; SOF0 8-bit, 3 components, luma 1×1 / 2×1 / 2×2; SOS one 3-component scan with `00 3f 00`; any other marker, a fill or stray byte, or a segment running past the data fails. A failing draw erases the slot (record and bytes) and drops `af`'s index to 1, the id kept (bench 2026-10-30: `af` `c1 a68adf5a` after the unpadded photo), so the next `4205` for that id gets `4311` 4. An image whose bytes the emulator doesn't hold (self-fetched, or the recording's) draws as shown. `4222` (`set_time_display`, `4a02 a6` `time_display`) stores the flag and redraws only on a change of value and only on screen 5. With WiFi up an image not stored is fetched by the device itself and the app sends nothing: no `0311` follows the ack, then `0311` 2 at 0.38 s, 3 at 1.73 s and 1 at 8.6 s after the `4205` (as recorded), all published at `64`, and with the 1 the image is stored and shown. The emulator fetches no bytes, so the image always passes. A network or custom `4205` while a fetch is busy changes nothing and draws `0311` 0 with its own id and kind; the fetch goes on. `4212` (the holiday theme, prime-a2345-a91b2.md `4212` row and "Theme upload") never replies and pushes no `0311`; a request missing a field changes nothing. With WiFi up the device fetches the image at once (kind 1); with WiFi down the request is dropped and nothing stored. No message marks the image landing, so the emulator lands it 8.6 s on, the recorded network self-fetch's time, and treats the CRC as matching since it fetches no bytes. The landed record (hidden: the id, `_holiday_crc`, `_holiday_a4` (role unread), `_holiday_start` / `_holiday_end` as sent, the URL) also captures the stored `420a` country. `a2 = 0` erases the slot record but doesn't cancel a fetch in flight, which still lands afterward and writes the record again (the firmware's race). A WiFi drop mid-fetch doesn't stop it either: the module resumes at its saved offset and the image lands on time; the retry budget running out (op `0x3d` status 3, no valid record, silent for kind 1) isn't modeled. The holiday theme shows while the holiday switch (the reply's own `a2` bit 6) is on, the record's country is the current `420a` country and the local RTC lies inside [start, end], the bounds read as `[year - 2000, month, day, hour, min, sec, -]`; then `4a02` carries the fetch URL in `a4` and `a5 02 01 01` after it. A later `420a` country change, the switch off or the erase hides it.
- A2345 Secret Features (prime-a2345-a91b2.md "Secret Features"; RAM-only counters, carried in no frame): Feature 1 (`0305 a2` 04) when a main-tile focus (`unit_event("switch_screen")`) is the 20th within 10 s, a sliding window (each focus ages out on its own; the count never clears); Feature 2 (05) on a USB-C port's 10th attach rise within 60 s of its first (fixed window, per port; the count clears at 10 or when the window ends); Feature Expert (01) on every 10th counted designation since boot (a `420c` counts one per set bit in port order, none made with 2 or more ports already designated; the mode menu and the re-apply on entering Port Priority aren't modeled; no cooldown); Device Expert (03) on each change into all six ports active. A trigger inside its cooldown (03: 24 h, 04: 60 s, 05: 300 s) is dropped. A nonzero `420d` triggers 0, the prompt. Pending features go out one a second in the order 0, 1, 2, 3, 4, 5 (no overlay is modeled): an idle service sends at once, and after a send waits a second before the next, so a `420d` right behind another feature's `0305` gets only its ack, its `0305` a second later. Power Expert (02) counts USB-C ports in a high-voltage class above 18 000 mV and fires on each rise of that count to 3 or more, with no cooldown. A change in the active USB-C port count zeroes every class for 21 s, and a class needs 2 or more ports active, so it fires no sooner than 21 s after the third port goes active, and again after one dips and recovers. The class comes from the port's voltage; the PD codes that also raise it aren't modeled.
- Prime link state (prime-a2345-a91b2.md "Push routing"): `set_wifi(up)` on the A2345 and A91B2 sets link-state bit 1; BLE is the link itself. WiFi coming up sends `0301` (`a2 02 <firmware_version u16>`, the snapshot's `a2`, as recorded). With WiFi up a push goes where the routing table sends it: the change pushes (`0302`, `0305`, `0307`-`030b`, `030d`, `030f`-`0311`) to `64`, `0303` to `34` (the BLE client gets no `4303` stream), `0304` to `64` then `44`, `0300`/`0312` to `32` (never BLE), the A91B2's `0308` to `34`; a layout's `sends` keeps each off the BLE link, replies stay. `mqtt_routed` gives each push's MQTT copies with their `a1`, and the module publishes them to the outbox (below). `420a` also stores its country, uppercased. While WiFi is up two periodics publish at `32` (prime-a2345-a91b2.md "Periodic pushes"): `0300` every 10 min on both (`a2` the active-port bitmap, bit 0 C1 ... bit 5 A2, set where the port block's status is 1, then six u16 port powers in 0.01 W, rounded down to 0.1 W on the A2345 and unrounded on the A91B2; `a3` their total; `a4` the s8 UTC offset in hours), and on the A2345 `0312` every 60 s with the holiday switch on and a country stored (`a2` the country, `a3` the int32 UTC offset in hours). The MCU's timers free-run from boot; here each starts a full period after WiFi comes up and stops when it goes down. Every `0312` is published; the cloud keeping about one an hour is outside the device.
- Cloud: `set_cloud(True)` puts the device on WiFi to the cloud, where it has no BLE link: the open link drops and connecting fails until `set_cloud(False)`. There `mqtt_frame(msgtype)` returns the plain `ff09` frame (`03 01 0f`, no link flags) the C Gen 2 unit publishes to MQTT, built from its state: the `param_info` messages (`0421`, `0489`, and the `0900`, `0889` and `0892` replies) at `a1 34`, and the `state_info` events (`0425` where the model sends one, `0503`) at `a1 12` (a1783-telemetry.md "MQTT channel routing"). Nothing goes out on a link. It raises off the cloud and for any other msgtype, `0490` included (an HTTPS upload, not MQTT). `0503`, the lifetime energy and TOU-time totals, is cloud-only, never a BLE push, and builds only while a TOU period is active (the cloud `0421`'s `d9[0]` non-zero; a1783-telemetry.md "0503"): outside one `mqtt_frame(0x503)` raises. Its values are set by name like any other (`battery_to_load_energy`, `peak_time`, `time_save`, ...), and the layout's `started` 10 s usage pass adds to them: each pass while a TOU period is active adds 10 s to that type's time (hidden `<total>_delta`, counted in the hidden `tou_usage_passes`), every 120 passes fold the deltas into `peak_time` / `mid_peak_time` / `off_peak_time`, and pass 720 (2 h) starts the count again and publishes the `0503` to `mqtt_published`, its `time_save` the RTC rounded down to the minute (a1783-telemetry.md "0503" Trigger); off the cloud the pass publishes nothing. The energy totals need the pack's charge power, which no value models, so they change only by name.
- MQTT outbox: `device.mqtt_published` lists what the device published to MQTT on its own, in send order, as (msgtype, plain `ff09` frame). Any push a layout's `sends` holds off BLE (a timed push, a follow-up, a burst's first push, `device.push`) goes through the layout's `mqtt_routed`, and its copies land there; the base layouts publish nothing for a held push. A timed step can also publish straight to MQTT (`Step.published`, cleartext with its MQTT `a1`). Publishing needs no BLE link, but a push a clock jump bypassed publishes nothing. Replies always go out on BLE. `mqtt_frame` stays for messages built on demand.
- Values: `set_values(name=value)` sets a telemetry field on the device: every later frame that carries the name, recorded or built, sends it. Names are the Anker app's in snake_case (`reference/app-names.md`); a device the app's logs don't cover takes the app's name for the same field on the closest equivalent hardware. The C Gen 2 line's `0490` push's names are listed in `devices/data/c490_fields.json` (path → name), and the ones it shares with `0421`/`0900` (`battery_level`, `ac_output_power`, `pv1_input_power`, and `sub_package_battery_level` on the models with the expansion port) are the same reading in both. One name on several tags (`a4[23]` and `d9[3]` are both `charging_limit_value`) sets them all.
- The `0490` push: a periodic push, not a summary (most fields are live reads at post time). Its payload is `a1 01 31`, `a2` (2-byte length, type `04`, a nanopb message), then the schema name in `a3`. `c_g2_490.py` walks the message and rewrites named leaves (varint, zigzag varint, fixed bytes at their recorded length), so one with nothing set is the recording byte for byte. `.14` and `.15` always hold two pack entries; on a model with no expansion (`Profile.expansion`) the second entries and the expansion's SoC (`.23.1#1`) start at zero. It goes out every 540 s on one grid from the display board's start (the layout's `started` timer), which neither a stop, the switch nor the link resets: 2026-10-07 20:34:08 → 22:40:07 is 14 × 540 s, 2026-09-19 04:48:33 → 18:54:34 is 94 × 540 s. A post goes out only while the hidden `device_point_switch` (the module's cloud device-point switch, no app name; on unless set) is 1; otherwise it is missed (a1783-telemetry.md "When the display board posts c490"). A post that falls due with no link up (no authorized BLE link, and not bound and on WiFi through `set_cloud`, where it is uploaded, not modeled) stays pending (hidden `c490_pending`): every 9 s accumulation queues it until one finds a link, and the next post is back on the 540 s grid, so an off-schedule post comes only when a boundary falls inside a link gap (firmware/mainmcu.md "c490 gates and cadence"). A `4057` stop (`a2 = 0`) turns it off, and a start or re-send leaves it off ("What stops and restores c490"). The cloud fetch and WiFi re-provision that restore it aren't modeled, so only `set_values(device_point_switch=1)` does. Not modeled either: a MainMcu reset restarting the 540 s phase (a1783-telemetry.md "c490 counters"; the emulator has no MainMcu reset). Each attached pack's counter page (`.14.25` / `.14.26`, a1783-telemetry.md "`.14.25` / `.14.26` pages") turns 0-3 every 360.1 s from the start (3 601 calls at 10 Hz, firmware/c490-schema.md `page_index_get`), so 540 s posts land 1.5 pages apart; `.14.26` is the page's second counter in whole hours. The four counters start at the recording's hours and count on; their zeroings (charge end, full charge, the OCV recalibration) aren't modeled.
- Commands shown in telemetry: an accepted command's validator (the layout's `COMMANDS`) returns the telemetry values its request sets, and its `SIDE_EFFECTS` any further ones from the device's state; each is set in every message that carries the name, before the reply and the telemetry that follows are built. A rejected command sets nothing. Its reply's status is `04` on an MCU that rejects (the Prime MCUs), whether or not the reply is recorded; the C Gen 2 display board acks every setter `00` (`fid0f_ack_reply`), so there a rejected setting is acked and left unapplied, as the A1783 does with a setting it can't read (`a2 01 01`, no type byte).
- MCU: `device.mcu` is the script; `use_mcu(script)` replaces it (`McuScript()` for a quiet MCU), `set_reply(request, (msgtype, cleartext), ...)` sets a request's answer (none for silence), and `set_push(msgtype, cleartext)` sets a push.

## Recorded data

MCU replies and pushes are recorded cleartext from real units, packaged as `devices/data/<pn>.json` (msgtype → cleartext hex) by `tools/sanitize_frames.py`; a profile lists its files, and the first that holds a msgtype supplies it. The tool reads collector logs and MQTT records (anker-solix-api `.ndjson` examples, `mqtt_monitor` dumps). An MQTT frame is the same frame the MCU sends to BLE with another routing marker in its leading `a1` (`34` or `32` for `31`), which the tool sets back to `31`; `--fix-checksum` recomputes the checksum of records whose serial was anonymized after capture. Sources are listed in [device-sources.md](device-sources.md). The tool takes the real identifiers on its command line, never stores them, and fails on any printable run it wasn't told is safe. The frames are sanitized before they enter the package: the serial, MAC, expansion serials, account tokens and device clocks are replaced with synthetic values of the same length, and the frames are re-encoded. The fixed handshake frames (`4801`, `4803`) are reproduced byte for byte; frames that carry the serial or MAC match a real capture everywhere except those fields.

## Live values

Off by default, so every frame is the recording with the set values over it. The A2345 and A91B2 have tables (`a2345_live.json`, `a91b2_live.json`: the `0303` and `4a00` port blocks). `device.vary_live_values(seed)` turns it on with `random.Random(seed)`; `vary_live_values(None)` turns it off. Only a device with recorded live values has a table (`Profile.live = LiveSource(table, period)`); any other raises `LayoutError` naming the device, as does a table that names a field the device sends in no message.

- Tables: `devices/data/<pn>_live.json` (compact JSON), built by `uv run python tools/build_live_tables.py <survey dir> [--only <PN> ...]` from the frame survey's per-device JSON. A match key one message records at a single value carries to the same-named group of a message whose frame lacks it, at that value: the Prime port relays (`pdN_relay_switch`, the A2345's shared `usb_relay_switch`) are in `4a00` only and read 1 in every recorded frame, so a port switched off with `4207` matches no sample and idles in `0303` too; a key that would carry but was recorded at more than one value is refused. Per message it keeps the groups (fields that move together, like a port's status, voltage, current and power: their `live` fields, the idle values of those, the rest as match keys, any further match keys from outside the group's field (`match`, an AC input's switch and status), and the recorded samples with their counts), the groups recorded active together (`active_sets`), the totals that held in every frame, the paired draws (fields recorded beside a given tuple, like a pack current beside a total), the slow fields' steps, range and interval (the survey's median time between recorded steps; a slow block without one is refused), and `remaining_time` split by output idle and active. Counters, the totals that didn't always hold, and identifier fields are left out; a table holds numbers only, apart from the match wildcard below. A survey of a device the emulator doesn't have is refused, as is a table that draws (a group's live field, a total, a paired field, `remaining_time`) a field the device's layout derives from others (`LayoutProtocol.derived`, empty by default); a derived slow field is left out with a note, since the layout works it out from the field it follows, and a derived field may still be a match key. The survey's `mirrors` (names that are one state value here) are ignored. A named section (a joint table, like the A1783's `ac_charge`) and a `0490` section of a schema the emulator doesn't send (it sends `_0009`) build nothing, with a note. A C Gen 2 frame whose `a4` has no byte 31 (26 B) comes from firmware without Battery-Only Power, which first appears in v1.2.1.6 (a1783-telemetry.md:153, :553). Those samples (`samples_short_a4`) keep the match keys the frame carries (`match_short_a4`); the emulated v1.2.1.6 lets them draw only with `ac_input_disable_switch` at 0: a modelling choice that takes that firmware's AC behaviour as Battery-Only off, not a recorded switch state. They merge into the group's samples, a tuple both hold adding its counts. The AC charge limits govern the AC input, not the AC output: a sample whose `ac_input_power` is idle takes `*` (`live.ANY`, which matches any state value) on `ac_recharge_power`, `silent_recharge_power` and `super_fast_charge_status` (the builder's `INPUT_ONLY`), and such samples merge. The DC input's group (`pv1`) also matches on the hidden `dc_input_source` (0 solar, 1 car socket; the app has no name for it, and its `carChargerInputPower` reads the same XT-60i value as `pv1InputPower`). A plugged-in sample (`pv1_charge_status` 1) takes the source of the era its days (`a8_by_day`) fall in, by the owner's era table for the XT-60i: 2 × PS400 solar before 2026-08-08, the car-socket adapter from then. One with nothing plugged in (status 0) takes `*`. A plugged-in sample with no day, or with days in both eras, is refused. Each frame sample counts 2 s, the collector's poll, so samples recorded on another clock can join the group. The group draws on its own (`independent`), out of the active sets.
- When: a frame is built (a push the device sends on its own, a timed event's frame, an answer to a request, `device.push`, `mqtt_frame`) after at least one telemetry period has passed since the last draw, and the device draws first. Turning it on draws at once, and draws fall on a period grid from there, so frames built within one period share a draw and the same seed with the same clock steps gives the same frames. The period is the device's stream period: 1 s for the Prime `0303` (`REALTIME_BURST`).
- A draw, per message in table order: pick an active set by its count, leaving out groups with no drawable sample (an active group draws a sample whose match keys equal the device's current values, so a port switched off stays idle); each active group takes its sample, every other group its idle values; an independent group isn't in the active sets and takes one of all the samples matching the current values, idle ones included, so it is active as often as it was recorded active given its match keys; totals sum the drawn fields; a paired draw takes a tuple recorded beside the current given values, or holds the fields (`unpaired`); each slow field takes one recorded step per interval passed since its last step (each on its own clock, the remainder carried, so a `0490` field recorded 540 s apart steps every 540 s whatever the draw period), clamped to its recorded range; `remaining_time` comes from the output-idle split when `total_output_power` is 0, else the output-active one. After each message the layout's `derive` gives the values that follow from the state (`LayoutProtocol.derive`, none by default), which a later message's draw reads; they are never part of the draw. A field an earlier message drew isn't drawn again, so a name in two messages (`pd1_output_power` in `0303` and `4a00`) is one value. A group with a pinned field isn't drawn at all, so its fields stay one recorded sample's. Values come from the recorded frequencies as they are.
- Drawn values go the way `set_values` sends them: into every frame that carries the name, with the layout's implied values, and the timed events the change starts run before the frame is built. A value given to `set_values` is pinned and a draw never changes it; implied values and those a timed event sets aren't.
- C Gen 2: the A1783 has a table (`a1783_live.json`). From `0421`/`0900`, one section: the port groups (AC in and out matching the Battery-Only switch, the AC status, `ac_recharge_power`, `silent_recharge_power` and `super_fast_charge_status`, the last three on the AC input only, so a limit never recorded still draws AC output but never AC input; DC in on its own: plugged in, it drew power in 2 253 of 2 299 recorded frames, all car socket, and `dc_input_source` reads 1, the car socket, while unset (`LayoutProtocol.defaults`: the values hidden inputs read while unset, none by default), so at 0 it idles until solar samples join; PD1-PD3, USB-A, the car socket, the alternator charger), the output total of all seven port outputs, the temperatures and WiFi signal, and `remaining_time`. From `0490`: each pack's SoCs, estimators, reserve and voltages, and its pack currents and pack-side powers paired with `.23.4` / `.23.2` / `.23.7`. It draws every 1 s, the `c421` stream's period (`c421_change_tick`'s 1000-tick timer, a1783-control.md `4057`); the slow fields drift by their recorded steps per recorded interval, counted on the device clock whatever the client's poll rate. The `0421`/`0900` steps were recorded per collector poll (median 2 s, the collector's `runtime.poll_interval_s`; the log cadence follows the poll), so they apply per 2 s elapsed; the `0490` ones per post, 540 s. The A1763, A1765 and A1785 have no recordings and refuse. The `0421`/`0900` section comes first, so the names it shares with the `0490` (the output total, AC output, DC input, `remaining_time`) are one value, and the `0490` posted in a period carries that period's. The flow state, the battery levels and `.23.4` aren't drawn: the layout's `derive`, the same derivation its changes run, hands them to the draw after each section, so the `0490`'s paired tuple is looked up against this period's totals, and a pack current a pair draws stays in that change.

## Layouts

Each product's commands and telemetry are hand-written in its own device module as a layout class satisfying `LayoutProtocol`, passed as `Profile.layout` (`CGen2Layout` in `solix_c_gen2.py`, `A2345Layout`, `AS220Layout`, `A17C0Layout`, ...). A layout builds on `parameters.py`: `TableLayout` for a recorded device, which declares per message its typed blocks (`FIELDS`: tag -> codec, type byte, field zeros) and its repeated blocks (`GROUPS`: one codec at several tags, a port or a timer per tag), with five hooks for the rest (`timed` gives the timed events a change of values starts; by default none, the C Gen 2 mains and Battery-Only sequence, the car socket's USB-C re-attach, the output timers and the low-SoC `0403`s, the screen wake and timeout, and the backup windows; `sends` says whether a push goes out now: by default always, a C Gen 2 `0490` only with the device-point switch on; `implied` gives the values a set value implies, the C Gen 2's stored TOU plan from `tou_periods` and AC input 0 W with no mains; `finish` reshapes a frame once its fields are written: a grid-loss `0425`, and the C Gen 2 `d9` active period and the AC-charge hold of Peak and of Battery-Only Power; `publishes` says whether a message goes to MQTT in the current state, given any other message's cloud payload; by default always, a C Gen 2 `0503` only while its `0421` reports an active TOU period); `ScalarFieldLayout` for a flat run of single-value fields (the Solarbank `0405`); and `CommandDispatchLayout`, whose `COMMANDS` map a msgtype to a validator that returns the telemetry values an accepted request sets (`{}` for none), or `None` to refuse it. Every request field and every block is a construct `Struct`; a TLV field's length byte is always rebuilt from its value, never written by hand.

A field's tag, type byte and width come from real evidence: a recorded frame, checked by the product's tests, or a cited client's decode. Bytes nothing names stay as recorded, and a rebuilt field keeps them. A product without a layout answers only its recorded requests.

anker-solix-api's maps, hand-transcribed from its `mqttmap.py`, sit in `reference/anker-solix-api-maps/` as reverse-engineering reference for writing a layout. Nothing loads them at runtime.

## Testing

The package's own tests do not depend on any client library:

- known-answer tests: the fixed handshake frames, recorded cleartext round trips, fragment layouts;
- a client-side fixture that drives real `bleak.BleakClient` through the backend and performs the client half of the handshake.

Client libraries (SolixBLE, through its `MockDevice` adapter) test against the emulator in their own suites.

Client checks kept here, run by hand with the client checkout's Python and the emulator importable (installed, or `PYTHONPATH=<emulator>/src`):

- `tools/solixble_theme_check.py`: SolixBLE's A2345 custom-theme upload (SolixBLE #87, `FileTransfer.pad_last_chunk`) through `EmulatedConnection`, with `tests/fixtures/prime/themes/custom-test.jpg`, padded and unpadded. Padded, the photo shows and a repeat select sends no second `4220`; unpadded, the first draw fails, the theme falls back to screen 1, and the repeat select uploads again (as on the bench, 2026-10-30). It takes about 30 s on the real clock. It could become a test in SolixBLE's own suite.

## Releases

The version is the git tag (hatch-vcs).

| trigger                              | TestPyPI | PyPI | GitHub                                                 |
| ------------------------------------ | -------- | ---- | ------------------------------------------------------ |
| tag `vX.Y.Z`                         | yes      | yes  | release; then every pre-release and its tag is deleted |
| tag `vX.Y.Z-(alpha\|beta\|rc\|dev)N` | yes      | no   | pre-release                                            |
| push to `main` (CI green)            | no       | no   | the rolling `dev` pre-release is replaced              |

Any other tag is ignored, and the build fails unless the built version equals the tag's (`v0.2.0-rc1` → `0.2.0rc1`).
