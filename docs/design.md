# anker-ble-emulator design

An emulated Anker Solix BLE device (the comms module and the device MCU behind it) for testing BLE clients. It plugs in under [bleak](https://github.com/hbldh/bleak) as a client backend, so the client's real stack (bleak, bleak-retry-connector, the client library) runs unchanged above it. There is no radio and no OS Bluetooth stack.

## Layers

| layer    | module        | role                                                                                                                                                                                                                                                                                                                                                              |
| -------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| frame    | `frame.py`    | `ff09` frame codec: length, pattern, cmd, payload, XOR checksum; fragmenting and reassembly at the fragment cap                                                                                                                                                                                                                                                   |
| fields   | `tlv.py`      | negotiation TLVs (`tag len value`, tags from `a1`)                                                                                                                                                                                                                                                                                                                |
| messages | `messages.py` | one typed layout per negotiation reply (`0801`, `0803`, `0829`, `0821`, `0827 09`, status-only); request fields typed per msgtype (`0003` MTU u16, `0005` method, `0022` time u32 / offset int32 / TZ, `0027` token, `002b` time u32 / account / zone)                                                                                                                                              |
| crypto   | `crypto.py`   | static GCM, session GCM, session CBC, P-256 device key pair                                                                                                                                                                                                                                                                                                       |
| module   | `module.py`   | the comms module: negotiation handlers, link state, authorization policy, the authorize timer, the relay to and from the MCU                                                                                                                                                                                                                                      |
| MCU      | `mcu.py`      | `McuScript`: recorded cleartext replies by message type, and pushes; for a command the product's layout handles and no recording answers, an ack whose status is the layout's check. Its starting state is every named value the recordings carry: the recorded `0490`'s fields (the 0.1 % `pack_soc` / `sub_package_pack_soc`, the bus slots), then the replies and pushes over them |
| layouts  | `layouts.py`  | `LayoutProtocol`, what `McuScript` and `EmulatedDevice` need from a product's layout; `LayoutError`; the TLV type bytes; shared field codecs (`ui`, `ScalarField` and its constructors) |
| parameters | `parameters.py` | `Parameter` / `Parameters`, SolixBLE's TLV shape (optional type byte, optional status prefix); the layout bases `TableLayout` (a recorded device's telemetry, named by per-message tables of `FieldSpec`s and `FieldGroup`s), `ScalarFieldLayout` (flat single-value fields) and `CommandDispatchLayout` (per-command validators), and the table helpers `leaf_zeros`, `struct_zeros`, `one_field` and `flat`; `validators.py` holds `OptionsValidator` |
| products | `products.py` | `Product` part numbers with their SolixBLE class and anker-solix-api category; `Transport`, `Outer`, `Path`                                                                                                                                                                                                                                                       |
| devices  | `devices/`    | `base.py`: `EmulatedDevice`, `ProductDevice` (a subclass names only its `PRODUCT`), `Profile`, `Advert`; one module per product holding its profile and subclass; `solix_c_gen2.py`: the display board's command set and codecs (the C Gen 2 line, and the S2000's shared tags); `prime.py`: what the A2345 and A91B2 share; recorded frames in `devices/data/`                                                                                                                                                           |
| backend  | `backend.py`  | `EmulatedBleakBackend(BaseBleakClient)`: GATT services from bleak's own classes (service `8c850001`, write `8c850002`, notify `8c850003`; `ff09` is only advertised), writes into the module, notifications out                                                                                                                                                   |
| testing  | `testing.py`  | `EmulatedConnection`: patches a client library's `establish_connection` (SolixBLE's by default) to return a real connected `BleakClient` on the emulator; keeps SolixBLE `MockDevice`'s names (`expect_ordered` as an optional write assertion, `refuse_after`, `disconnect`, `send_data`, `new_connection_error`, `allow_connect`, `check_assertions`, `writes`) |

The C Gen 2 models run one MainMcu build (firmware/mainmcu.md "Model and device identity"), so the emulator answers the same commands on all four: `4100` → `c900` + `c421`; `4057` → `4857`; `405e` → `485e` + `c421`; `4063` → `4863`; `4089` → `4889`; `4090`/`4091`/`4092` → `4890`/`4891`/`4892` + `c421`; `4101`–`4104` → `4901`–`4904` + `c421`. Frames that name the unit (`0421`, `0900`, `0490`, `0425`) come from each model's own recording, PN strings as recorded (the A1785's say `A1783`, firmware/mainmcu.md). The identity-free replies are shared (`solix_c_gen2.json`).

C Gen 2 state that follows the request rather than a setting:

- `4090` stores the plan as a1783-control.md's `4090` row and "TOU (`4090`)" describe; an `a7` past 18 bytes, the stack overrun, is acked and changes nothing. The active period (`d9[0]`, that section's conditions) and the Peak / Mid-Peak hold (its "What an active period does" table) show only in `mqtt_frame`, since condition 2 needs the cloud and the emulator's cloud has no BLE link. The hold is applied when the frame is built: AC input 0 W in `a6` and `a7`, the bus holder's `a5[1]` / `c0[24]` and a charging `a3[0]` as a1783-telemetry.md "Flow state" reads them under the hold, the SoC being c490 `pack_soc` (the recorded `0490`'s unless set). When a holding record ends, AC input ramps back over the recorded end of 2026-10-21 (a1783-control.md "TOU (`4090`)", by the device clock), scaled to the charge waiting: 0 W until 6 s, the recorded samples between, the full charge from 13 s. Its own reading: a record that wasn't holding ends with no ramp, one running into another held record keeps holding, and a clock set re-times it. `0503` publishes only while a period is active.
- `4100` sets `a3[10:12]` `silent_recharge_power` as a1783-control.md's `a3` `[10..11]` row gives it (1000 for the app's request, else 600); the v1.1.2.6 recordings (A1763, A1765) keep their 10-byte `a3`.
- Every request passes `fid0f_app_id_time_store` (a1783-control.md "Session frames", a1783-telemetry.md `fd`): a request's `fd` goes into the telemetry's, one without leaves it.

C Gen 2 mains and Battery-Only Power (`a4[31]` and `a7[3]` as a1783-control.md's `a4` `[31]` row and "`a4[31]` witnesses" give them), timed from a change of `ac_input_status` or `ac_input_disable_switch`. The power stage's AC-input flag, which the auto-off, the accept and the alert key on, is the hidden `ac_input_flag`, settling on `a7[3]` after the power stage's report and the 100 ms debounce. The report and the charge ramp are the power stage's, so the emulator takes them from the witnesses' bench runs:

- Mains lost: AC input reads 0 W at once and the flag drops 0.1 s on. With Battery-Only on, the auto-off clears it as the flag drops (state 2) and wakes the screen (`a4[21]` 1).
- Off-grid alert: the 5-tick commit (hidden `ac_input_flag_committed`). The tick's phase isn't modeled: the change is the first counted tick, so a drop commits 4 s after the flag. The committed drop's `0425` 0x59 goes out on the A1783 and A1785 only, the models whose recordings carry a `0425`.
- Mains back: `a7[3]` 1; the flag returns 3.0 s on, and a state 2 clears to 0 then (the accept).
- AC charging: the 7 s one-shot, counted from the accept since the tick's phase isn't modeled, enables it 8 s after the accept; the power stage's ready bit, which can enable it sooner, isn't modeled. Then the ramp: 118 W at the enable and the full charge 5 s on.
- The full AC charge follows the charge request (a1783-telemetry.md "AC charge request", `chg_src1_ac_limit_calc`): `maxInputPower` (`a3[4:6]` `max_input_power`, 1800 W here) less the AC-out draw (`a7[1:3]` `ac_output_power`), capped at the AC limit (`a4[4:6]` `ac_recharge_power`), + 10 W; AC input is that plus the AC out, up to the inlet's `maxInputPower` + 33 W. The inlet and the inverter output are separate ratings (a1783-telemetry.md ratings), so the outlets' draw beyond what AC input supplies comes from the on-bus pack, whose current and flow state follow from the port powers below. DC-side loads aren't subtracted. The +10 W is the 1200 W limit's recorded mode (a1783-telemetry.md "AC charge request", with the modes at the other limits and the pass-through's limit + out + about 24 W). The request never goes negative (step 1 there): with charge source 2 able to charge (the hidden `charge_source_2_can_charge`, clear unless set) it is 0 once AC out reaches the ceiling, otherwise it holds to the floor from the main pack's voltage (`.15.3`). At 1 750 W out on an 1800 W unit at 53.5 V the floor makes AC in 1 824 W (source 2: 1 810 W); at 1 900 W or 4 000 W out AC in reads the 1 833 W cap either way, and the pack discharges the rest. A change of the limit, `maxInputPower` or AC out moves a charge at the full rate to the new request at once (`chg_src1_ac_limit_calc` re-runs each pass, a1783-control.md "TOU (`4090`)"; its period isn't documented); an AC input set by name off the full charge stays.
- With Ultrafast on (`a4[20]` `super_fast_charge_status`) or a backup window running (the Fast Charging Plan or Storm Guard, `tou_setting_system_status` ≠ 0), the firmware skips the limit and requests `maxInputPower` less AC out. The charge holds to the recorded band: min(`maxInputPower` − AC out, 1 643 W), no +10 W, and AC input adds the AC out. 1 643 W is the mode of the plan windows' 1 553-1 673 W (a1783-telemetry.md "AC charge request"; `PLAN_CHARGE_CAP` names its frames). On the C1000 Gen 2 it holds to its 1 600 W UltraFast rating too: 1 600 W at 1800 W `maxInputPower`. Ultrafast on, a window starting or one ending moves a charge at the full rate the same way.
- One MainMcu build serves all four models (PiField firmware/mainmcu.md: the factory record's model index changes only names and PN strings), so the decoded rules (the charge request and its floor, `maxInputPower`, Ultrafast skipping the limit, `port_power_out_sum`) key on the `0421` `f9` `mcu_version`, not the model: they hold from v1.2.1.1, the first decoded build (the A1785 records v1.2.1.1, the A1783 v1.2.1.6). The A1763 / A1765 record v1.1.2.6, undecoded, with `maxInputPower` 1200 W; the emulator runs the same charge request there, so its UltraFast charge stops at the 1 200 W the request leaves.
- On the C2000 chassis (A1783, A1785) on a decoded build, the AC charge's current holds to the on-bus pack's headroom (a1783-telemetry.md "AC charge request" step 3, `ac_charge_current_headroom?`): MainBMS's allowed charge current (`+0xe0`, `charge_current_limit_calc`: 58.0 A, at most 245 760 / the pack voltage in 0.1 V, i.e. 2 457.6 W, and 40.0 A while its TOU bit is set) less the current the other sources hold (`chg_source_current_sum?`, taken as the DC input's), at the on-bus pack's voltage (`.15.3`). So the AC charge gives way first and DC stays as set: UltraFast's 1 643 W with 800 W of solar reads 45.7 A at 53.5 V, under both caps; at 41.0 V the 58.0 A cap leaves 1 578 W; at 55.0 V an 1800 W limit's 1 810 W charge gives way to 1 653 W, 44.6 A. The derived pack current (the net port flow over the pack voltage) lands at the cap with no DC-side load; DC-side loads aren't subtracted, as in the request. The 58.0 A rides the C2000's state read-only (`pack_charge_current_limit`); the C1000 Gen 2's BMS isn't decoded, so it has none. A change of the DC input or a pack voltage moves a full charge to the new headroom at once. The power cap's division truncates (`0x3c000` / V, masked `0xffff`), and a pack reading 0 V takes the 58.0 A alone. The BP2000 runs the same MainBMS image, so on the bus it holds to the same cap at its own voltage.
- MainBMS's TOU bit (`0x20000a48` bit 7, the hidden `tou_status_bit`) is MainMcu's op-0x006 status bit `0x80`: a TOU period active (`tou_active_period_get` ≠ 0) and no backup window running (firmware/mainbms-control-fsms.md "The op-0x006 byte"). MainMcu sends the byte every 500 ms; as a modeling choice, which keeps long test clocks cheap, the emulator refreshes the bit every 10 s and 0.5 s after a change of what it reads (the plan, the TOU mode, mains, Battery-Only Power, the MainMcu version, the alternator, the backup window, the clock). A period is active only on the cloud, so over BLE the bit stays clear. An Off-Peak period on the cloud holds UltraFast with 800 W of solar at 53.5 V to 1 340 W, 40.0 A. A full charge follows the bit's change. Its other setter (MainBMS `canrx_cmd_11`, CAN `0x0042` sub `0x11`, the pack-switch code) and the other limits (2.0 A under a 2000 mV cell, 0 at 58.0 °C, the gate's 0 at 99.9 % SoC, and the minimum `charge_current_limit_calc` takes over a 12-entry table before the voltage cap, whose contents and inputs aren't decoded) aren't modeled. A `total_input_power` set alone over the cap reads as set: AC takes the charge it would with no DC beside it, so a total past the cap leaves the pack over it.
- Battery-Only on with mains in: `a7[3]` 2 and AC input 0 W at once, and while it stays on every frame shows AC input 0 W and no charging state only AC could cause. Off with mains in: `a7[3]` 1 at once and AC charging 7.5 s on, the median of the witnesses' 6 s and 9 s restarts, by the same ramp. The two frames of `a4[31]` `00` between the `02`s on 2026-10-26 aren't modeled.
- AC charging goes into the pack below its cap (`a4[23]`), by the ramp above: with the main below its cap the charge shows on the bus holder's flow; with the main at its cap an attached expansion below its own takes the charge and the bus (`c0[24]` 2); with every pack at its cap, no AC input.
- A name the triggering change sets itself stays as set; each step acts only if the state it needs still holds when it comes due.

C Gen 2 car socket and the USB-C ports: an edge of `car_charge1_output_status` (`b2[0]`), from a `4102 a2` or `set_values`, re-attaches the USB-C ports as a1783-control.md "`4102 a2` and the USB-C ports" records.

- The device is two hidden inputs per port, carried in no field and with no app name: `<port>_device_plugged` (0/1) and `<port>_device_power` (W). Unset, `pd1` holds the A1783 recording's 86 W load and `pd2`/`pd3` none (on the C1000 Gen 2 `pd1` none too); a port without a device stays 0.
- The emulator's timing, the medians of the collector logs' clusters: `[0]` 1 at 1 s after the edge and the device's power 3 s after that, with the output total and the port flow following. A port detached again before then draws nothing, and a port power the edge's own call sets stands with no power step after it.

C Gen 2 `0403` events: MainMcu's push as a1783-control.md "`0403` push" gives it, built on every model since no `0403` is recorded.

- Output timers: `ac_timer_value` (`a4[0..3]`) and `car_charger_timer_value` (`a4[8..11]`) run as that section's output-timer bullet gives them; the car socket going off at 0 is a socket edge (above).
- Low SoC: `0x52` / `0x50` follow that section's table on `battery_level`, an evaluation each 500 ms and one more per block-1 reply with an expansion attached (`sub_package_connection_status`).

C Gen 2 screen (`a4[21]` `screen_switch`, `a4[15..16]` `screen_off_time`; a1783-control.md "Display", a1783-operation.md's 05:46:21 wake): a wake turns it on and re-arms the timeout. Wakes: `4103 a2` 1, a change of brightness (`4103 a3`), language (`4103 a9`) or the car socket (`4102 a2`), and the mains auto-off; the other setters and the `40xx` ops leave it (to be added to "Display"). A wake runs at once, so the command's own reply shows the screen on.

C Gen 2 backup plans: `405e` writes its tables as a1783-control.md "`005e` means different things across families" gives them, and the window events are its "`0425` event report" table. Table 1 is `manual_backup_switch` with `manual_backup_start_time` / `_end_time` in the `d9` tail, table 2 `auto_backup_switch` with the hidden `auto_backup_plans` (3 × u32 start / end UTC, empty unset; no field carries it). How the emulator runs the window pass:

- It runs 100 ms after any change of a plan, a switch or the clock, and at each window's start and end, every 100 ms within a second of one, rather than every 100 ms throughout. A running window keeps going until it ends or its switch goes off; with none running, Storm Guard is chosen before the plan.
- A start sets `d9`'s type and active pair and moves an expansion's charge and the bus to a main pack below 100 % (`c0[24]` 0, `a5[1]` 2, `a3[0]` following; the 2026-10-06 21:00:04 run in "Telemetry from local state"). The `0425`s go out on the A1783 and A1785 only, whose recordings carry one; the others' `d9` tail moves all the same.

C Gen 2 flow state (a1783-telemetry.md "Flow state"), filled from the port powers, the pack currents and the bus holder. A flow-state name set by name (`charge_discharge_status`, `sub_package_status`, `work_status`, `on_bus_pack_status`, and `total_input_power` set with either input) reads as set until its inputs next change: the follow below skips a status set by name since the change of the pack currents that queued it (the hidden `flow_statuses_held`, which the next such change starts over). The Battery-Only / Peak hold still applies to a by-name `a5[1]` / `c0[24]`, since it reshapes the published frame:

- The port-flow code (`a5[1]` / `c0[24]`) follows that section's table at once; with no `c0` (the C1000 Gen 2) the main always holds the bus.
- The pack currents (`.14.29` / `.14#1.29`): the bus holder carries the net port flow over its voltage (`.15.3` / `.15#1.3`) in its current source's 10 mA, 10 mA = (Σ in − Σ out) × 1000 / V; the other pack carries 0. A current given in the same change, by name or drawn, stays.
- `a3[0]` `work_status` and `.23.7` `on_bus_pack_status` follow that section's ±0.3 A test, settled 2 s after a change of the settled value (its 20 samples). Battery-Only Power switched on with mains in leaves `a3[0]` charging for its lag (the 19:39:18 witness, a1783-control.md "`a4[31]` witnesses"); the Peak hold, built per frame, shows it idle at once.
- `.23.2` and `.23.4` (`port_power_out_sum`, `port_power_in_sum`; firmware/c490-schema.md) come from the `0421` state, the same sums `a6[0:2]` and Σ input read: one value each, where the recordings' pairs within 5 s agree in 5 432 / 6 395 of 6 464 (at most 86 / 20 W apart).
- `total_output_power` (`a6[0:2]`, `.23.2`) is the port outputs' sum (a1783-telemetry.md `a6`, `port_power_out_sum`). A change of any port output moves it by that change, as a USB-C device's power does, so AC out alone moves it and the on-bus pack discharges what AC in doesn't supply. A total set by name, alone or with ports, must equal the ports' sum after the change.
- `total_input_power` set alone splits: AC in takes the AC charge the request allows (0 W without mains or with Battery-Only on), at most the total, and DC in (`pv1_input_power`) the rest, so 1 950 W at the 1300 W limit reads 1 310 W AC and 640 W DC. `maxInputPower` bounds only the AC request, so AC + solar can pass it (a1783-telemetry.md ratings: AC + solar 2 600 W). Set with one input, the other is the rest; a total under that input is refused. Set with both, it reads as set.
- The +10 W over the limit is the split's default. AC in set by name is taken as given up to the ceiling below, since the overshoot varies on the unit (a1783-telemetry.md "AC charge request").
- AC in set by name holds to `maxInputPower` + 33 W whatever the limit, the same ceiling the charge request's AC in stops at. On a decoded build, `maxInputPower` is refused at any value `max_input_power_get` doesn't give (1500, 1800 or 2300 W; a1783-telemetry.md `a2` byte 30); on v1.1.2.6 any value sets. More AC in, or a `maxInputPower` lowered under it, is refused. The inlet's 3 h / 12 A continuous rating (a1783-telemetry.md ratings) isn't modeled.
- The C1000 Gen 2 (A1763, A1765) holds to its own ratings (a1783-telemetry.md ratings) over the build's: the AC limit and the charge (AC in less AC out) to its AC charging rating + 33 W, or UltraFast's + 33 W while the limit is skipped; AC in to its bypass rating + 33 W, on a decoded build the lower of that and `maxInputPower` + 33 W. On the recorded v1.1.2.6 the bypass alone bounds AC in, so AC out passes through above the 1200 W `maxInputPower`. The bypass and UltraFast ratings ride the state read-only (`ac_bypass_power`, `ultrafast_charge_power`) for the charge request's steps.
- AC out (`ac_output_power`) holds to the model's AC output peak (a1783-telemetry.md ratings); the overload trip time isn't modeled.
- AC out reads 0 W unless AC output is on (a1783-telemetry.md `a7` [1:3], `tlv_a7_AcData`). Switching `ac_output_status` off, by `set_values`, `4101 a2 00` or the AC timer running out, puts it at 0 W, and `a6[0:2]`, the flow and a full AC charge's pass-through follow; switched back on, it stays 0 W until set or drawn. AC out set over 0 W with the output off is refused with `TypeError` and sets nothing. A draw matches the status, so it never pairs the two.
- The DC input holds to the XT-60i's rating on the C2000 chassis whatever `dc_input_source` says, since solar, the car cable and the alternator share it, and to the C1000 Gen 2's solar rating (a1783-telemetry.md ratings). No DC input voltage is carried, so the current limits aren't modeled.
- The output ports hold to their ratings by the app's port name, PD1-PD3 being USB-C1-C3 (a1783-telemetry.md ratings, shared pairs included). A port's load is its power, or its plugged USB-C device's where higher, since the device draws it once attached. The C1000's PD1 holds no device unless set: the A1783 recording's 86 W load is over its shared 20 W.
- Each of these refusals raises `TypeError` and sets nothing.
- Each pack's battery level (`battery_level`, `a5[2]` = `a6[8]` = `.23.1`, and the expansion's) is floor(SoC / 10) of its `pack_soc` / `sub_package_pack_soc` (a1783-telemetry.md `.23.1`). A level set alone puts the SoC at its whole percent; set together, each stays as set. The lag or lead of 1 at a whole-percent boundary isn't modeled.
- The derivation runs on every change of values (`set_values`, a draw, a command) and in every timed step that moves the port powers or the bus, before pack selection reads it.

C Gen 2 versions that drop out: `f9[12:16]` `inv_version` and `f9[4:8]` `sub_mcu_version` read 0 as a1783-telemetry.md "Versions (`f9`)" gives it. The emulator's figures: `inv_version` shows 1 s after the ACDC stage comes on (mains in, `a7[3]` 1 or 2, or AC output on) and reads 0 from 1 s after mains goes, or 49 s after AC output switches off with no mains, the stage back before then keeping it; `sub_mcu_version`'s 1 s of 0 once a minute runs on a timer from the MCU's start, its phase the emulator's. The hidden `_inv_version` / `_sub_mcu_version` hold the version while it reads 0, and the `4866` log chunk's header reads the same values (both `version_get`). Not modeled: the other subMCU zeroings (idle sleep, 7 failed DSP reads, power-up).

C Gen 2 pack selection, with an expansion attached, follows MainBMS `pack_select_eval` as firmware/mainbms-control-fsms.md "Pack selection" gives it: its switch table (rows named here by their switch code), "Latches", the note after it and "Charge-cap latch counters"; a1783-operation.md "Observed handovers" for the recorded handovers. Each rule is re-checked on every change of values. How the emulator holds it:

- State: the hidden `pack_on_bus` (1 main, 2 expansion; unset, the expansion, as recorded), `charge_cap_latch`, `charge_cap_latch_primed`, `charge_cap_latch_spent`, `discharge_latch`, `discharge_latch_from`, `alternator_byte_9` (ALT +9, default 0) and `sub_package_path_hold` (the expansion BMS's `raw+0x95`, clear unless set; it blocks both main → expansion rows). The SoCs are the 0.1 % `pack_soc` / `sub_package_pack_soc`, and "charging" / "discharge" the on-bus pack's current at ±0.3 A, not its port flow. Each switch shows in the flow state (above), and `.15.5` / `.15.6` read (8, 9) for the new holder, (3, 9) when it is quiet at or above its cap and (3, 3) for the other (a1783-operation.md "`.15.5` against the limits").
- Stand-ins: the per-pack allowances by SoC, which pack record holds which limit being open (fsms "Current-limit sources"). A pack may charge below its cap; the expansion's discharge allowance reads 0 under `min_soc` + 0.9 %, matching the 2026-09-03 expansion left in that band with the bus (a1783-operation.md "Expansion to its floor"); the main's charge allowance is taken as non-zero, its value at the cap unmodeled.
- The charge-cap latch sets, clears and counts as the latch table and its counters give it. Emulator choices: a charge shorter than the first 1 s adds nothing to the count (the firmware's keeps it), and once the +9 path's 15 s runs out, +9 alone sets nothing until `flag_00c7` returns (`charge_cap_latch_spent`). A pack charging with no source in (`pack_current` set by name) is the +9 path's case.
- The discharge latch arms on the main's 1.0 % drop (the latch table's path (a)), its baseline re-taken as the list after "Latches" gives it; the firmware's 1 s settle after charging stops, and the expansion's own baseline and drop, aren't modeled.
- Rows modeled: main → `0x12` (the charge to the expansion on the charge-cap latch; 2026-10-06 20:20:00 → :03), main → `0x22` (the discharge on the discharge latch, more than 2 s after the last switch; how a reverted `min_soc` hands the bus back, a1783-operation.md "`min_soc` as a lever"), expansion → `0x21` (under `min_soc` + 0.9 % with the latch clear, checked from 3.01 s after it took the bus, `pack_on_bus` by name included; 2026-09-03 03:29:25, and a raised `min_soc` on 2026-08-31), and the expansion → `0x11` / `0x21` ineligible row, which under the stand-in adds no switch of its own. An expansion charging from under its line keeps the bus while the latch holds (2026-10-06, the expansion at 5 %).

Not modeled: the once-per-boot `0x22`, the pack-switch-code rows (`0xaa` / `0x55`), the allowance-only rows (main → `0x12` / `0x22` after 300 steps, expansion → `0x11` on the latch), the discharge latch's high-current path (b), the charge-cap latch's other set paths (the idle and no-SoC counts, which read the min cell, vext and vbat that no value carries, and the fault path), the latches' `pb1_low_handler` reset, the expansion's quiet 13 at its cap, `.15.5` following power or SoC between switches, the one-frame `c0[24]` flap after the cap handover, and the bus voltage `.15.4`.

C Gen 2 expansion switch (`4104 a4`): the override, the 2 s reread and the off's `flag_00c7` gate run as a1783-control.md "`4104`" gives them, the expansion's own switch-on state (`flag_0b56`) being the hidden `expansion_switched_on` (unset = on). An off that reaches the expansion returns the selection to the main at once, and while off the expansion takes neither charge nor discharge. `flag_00c7` reads AC in (`a7[3]` 1 or 2, Battery-Only included) or PV in (a1783-telemetry.md "`.14.30` bits"). Not modeled: `flag_0a55` and the on it gates, the PC12 gate on the off's CAN send, the pack button, and the locate blink (`a5`).

C Gen 2 AC top-off: with mains in, Battery-Only Power off and the main on the bus, the main's `pack_soc` falling below "Top-off hysteresis"'s clear threshold (a1783-telemetry.md) starts a burst at once at the full charge, the flow state following. The emulator ends it 60 s later at the set threshold, `pack_soc` set there (the recorded burst, a1783-telemetry.md "AC top-off burst": 2026-10-20 04:57:40, off by 04:59). That refills a dip just under the clear threshold; from deeper, the charge would run on to the set threshold, which no value models, so it isn't ended. An expansion holding the bus (its own band) isn't modeled.

C Gen 2 OTA precheck: the pair `ota_enable` / `ota_block_reason` follows the SoCs as a1783-control.md "`4089`" gives it (`ota_precheck_update`), and a change of it pushes `0489` 0.15 s later. The pair compared is the one the SoCs give, not the recorded one (every recording carries 0 2 at a full SoC); a call that sets the pair itself keeps it. Upgrade and BMS boot mode aren't modeled.

C Gen 2 Battery-Only Power at the floor: the 2026-10-15 run of a1783-operation.md "Battery-Only Power at the floor" is replayed. With Battery-Only on and mains in, the main's `pack_soc` falling under `min_soc` + 0.9 % (its BMS's low-battery bit) drops the mode to state 2 at once, mains accepted; AC charging starts 4 s later by the cap rules, from the 118 W first step of the mains ramp (above); back over the line, state 2 clears to 0 1 s later and the screen wakes; the expansion takes the bus later by pack selection. The `dc` low-battery code, the outputs' dip during the drop and the min-cell path aren't modeled.

S2000 ratings (s2000-as220.md "Ratings"): a value set by name past a rating is refused with `TypeError` and sets nothing. Each is checked on the state after the change, when the change sets a power it reads (the totals' parts below included). No time limits are modeled.

- AC in (`ac_input_power`) holds to 1 833 W: the 1800 W bypass rating plus the C Gen 2's 33 W overshoot band. AC in is the charge plus the AC out (`ac_output_power`) it passes through.
- The charge, AC in less AC out, holds to the 1600 W UltraFast rating whatever `ac_recharge_power` and `super_fast_charge_status` read: the unit charges past its limit for 1-3 s after a switch (s2000-as220.md "Charge past the limit after a switch"), and the emulator doesn't model that decay. Less AC out under a charge that would then pass 1600 W is refused too.
- Solar (`pv1_input_power`) holds to 400 W and AC out to its 3000 W peak; with no time modeled, the 1500 W continuous rating isn't. `aa` (`pd1_output_power`), one USB total, holds to 118 W: 100 W plus the 18 W the USB-A and the 15 W USB-C share.

S2000 totals (s2000-as220.md "Telemetry", the totals tie): the input total (`total_input_power`) follows AC in + solar and the output total (`total_output_power`) AC out + `aa`. The parts' ratings bound them.

- A change of AC in or solar moves the input total to their sum, and a change of AC out or USB moves the output total.
- An input total set alone splits: AC in takes the charge the limit requests (`ac_recharge_power` + 10 W, 1600 W with UltraFast on) plus the AC out, at most the total and 1 833 W, and solar the rest. 1 500 W at the 1200 W limit with 55 W out reads 1 265 W AC and 235 W solar. Set with one input, the other is the rest; set with both, they must sum to it. A negative rest, or solar over 400 W, is refused with `TypeError` and sets nothing.
- An output total set by name, alone or with parts, must equal AC out + USB after the change; one off it is refused with `TypeError` and sets nothing.

S2000 setters (s2000-as220.md "Setters"): `4101` and `4103` set the fields that table maps, with the C Gen 2's codecs (above), and answer with the recorded ack and then a `0421` carrying the change.

- `4101 aa` sets `smart_ac_output_timeout` (`a4[28:30]`, minutes; no app name is known). It sits in the A1783 settings tail's reserved bytes, beside `a4[26:28]`, the app's `countryCode`, which stays as recorded.
- `4103 a2`'s `screen_switch` shows in the `0421` after the reply's. It's held (the hidden `screen_switch_request`), then set 0.5 s later with its own `0421` push. The doc bounds the delay under a second; the 0.5 s is the emulator's. A repeat while one is held keeps the held one's time.
- Params the doc's table doesn't show (`4101 a3`/`a5`/`a6`/`ab`, `4103 a9`/`b0`) and the SoC-limit clamp follow the C Gen 2's handling.
- A setter changes only its setting, power staying as set or drawn, except that the AC output switched off reads AC out 0 W, as on the C Gen 2 (above), with the totals tie and the pass-through following.
- Not modeled: the C Gen 2's screen wake and timeout (s2000-as220.md's frames keep the screen on past `screen_off_time`), and `f0[3]` (s2000-as220.md "Telemetry").

S2000 AC pass-through: `ac_pass_through_status` (`f0[0]`; the emulator's name, since no app name is known) follows s2000-as220.md "Telemetry"'s `f0[0]` rule: 1 with `ac_output_status` (`a7[0]`) on and AC in over 0 W. It's set on every change of either, and is separate from `a7[3]` `ac_input_status`. One set by name off the rule is refused with `TypeError` and sets nothing.

Module session ops below `0x40` are the ESP32's own, answered on `03 00 0f` once the link is authorized. `0030` → `0830` is built on every build from the module build, the device firmware and the product's names (C Gen 2: `<pn>_low`, `<pn>_mcu_low`, `<pn>_esp32_low`; Prime: `<pn>`, `<pn>_mcu`, `<pn>_esp32`). The A1783's recorded `0020`, `0028`, `002e`, `002f`, `0036` and `0038` replies come only with v0.3.3.0, the build they were recorded on.

Every wire parse and build is a [construct](https://construct.readthedocs.io) layout: the frame (`PATTERN_LAYOUT`, `COMMAND_LAYOUT` with the link flags and 12-bit msgtype, `FRAME_LAYOUT`, `FRAGMENT_LAYOUT`), the fields and messages, the key material (`GCM_KEYS_LAYOUT`, `CBC_KEYS_LAYOUT` over the shared secret), the P-256 point (`POINT_LAYOUT`) and the advert record (`ADVERT_LAYOUT`). Frames and parsed messages are construct `Container`s; plain classes hold only settings and link state, which have no wire form.

The module and MCU layers are synchronous and transport-free: a write in, a list of frames out, each with a delay. Time is injected, so timers are testable without sleeping.

## Behaviour emulated

- Frames, the `cmd` flags and the fragmenting follow anker-crypto-and-negotiation.md "Frame" and "Fragmentation and MTU"; the fragment cap is ATT MTU − 3, 253 by default.
- The outers and the session ciphers follow its "Path selection and the static key" and "Authentication generations": the encrypted outer under the static GCM key, then the session GCM from the raw-X shared secret; the plain outer in clear, then the session CBC, which checks only the last pad byte on the way in (its "Frame" status split). A fresh P-256 point answers each `4021`.
- Port context: an encrypted frame with no session opens under the module's key and IV as that doc's "Frame" key row and "Authentication generations" bootstrap give them: zeros at boot, then whatever the last `0001`, `0021` or legacy confer set. A new link keeps them, so an encrypted frame before its `0001` meets the last link's key.
- Authorization (its "Registration and the side button (`0027`)"): an enrolled token authorizes at once; a new one gets `09` and the confirmation window, granted by a simulated button press (`press_button`, `4827 00` on `030101`). Opcodes `>= 0x40` reach the MCU only once authorized.
- Module policy and the authorize timer follow its "Module authorization policy (v0.3.3.0)": v0.3.3.0 enforces the auth mode on the encrypted outer, the earlier builds (v0.2.9.7, v0.3.0.6) take either connect frame, and an unauthorized link drops on the 10 s timer's schedule.
- The MCU's RTC and the module's TZ follow a1783-control.md "Clock": an accepted `0022` sets the RTC to local time through the module's floor and it then runs on the device clock, counting from 0 before any set; the module keeps the UTC epoch a push's `fe` carries, and its TZ timer re-sends the stored zone's offset on that section's schedule, so DST switches with no new `0022`. Each MCU applies its own rules on top (the C Gen 2's in "Clock"; the Primes' in prime-a2345-a91b2.md fid 0x10 ops `0x26` / `0x09`).
- Account-gated clock set `002b`: answered as a1783-control.md's `0x02b` row and anker-crypto-and-negotiation.md's `check_account_id` give it, sign quirk and full-width reads included. The bound account lives in the module's RAM: it outlives a link and a factory reset, and a new module starts with none.
- Decrypt failure: an encrypted request the link's key can't open gets the status anker-crypto-and-negotiation.md "Decrypt-failure `01`" and its "Frame" status split give, sealed under that key on the request's pattern; the link stays up and the MCU never sees the frame.
- Timed events: the module keeps a queue of events on the device clock, checked every `push_period` (0.1 s). Each event's action sees the set values and the device's whole state (the recorded values, set ones over them, the RTC in local seconds, and the UTC epoch a push's `fe` carries; a clock set puts the RTC at the `a1` UTC less the `a3` offset and the epoch at the UTC itself). It sets values or clears them back to the recording, sends recorded pushes and frames it builds on an authorized link, and can start the next event, timed from its own due time so a cadence holds when a check catches up. Scheduling an event replaces any queued one with its key; link events (a burst, a factory reset's drop) end with the link; one that falls due with no link sets its values and sends nothing. A layout's `timed` hook starts events from a change of state, whether from `set_values` (a change made on the unit), a command (its request msgtype passed along, so a layout can tell the two apart), an on-unit event no field carries (`unit_event(name, **hidden)`, a screen switched on the unit, say, with its own data as hidden `_` values), or a clock set (`0022`/`002b`, which re-times what depends on the RTC); those due at once run there, so a command's own reply and follow-ups carry what they set, and their pushes follow the reply. Each of those changes (and `set_cloud`) first runs whatever already fell due, so an overdue event sees the state it fell due in, and a command's side effects see the same whole state a timed action does. An event run late (a long advance between checks) reads the RTC and epoch at its own due time, and its pushes are built with that RTC. The clock is injected: `ManualClock.advance` runs everything that falls due on the way, `ManualClock.jump` moves past it (each bypassed event sets its values, sends nothing), and `ScaledClock` runs real time at a chosen speed.
- Bursts: the Prime `420b` realtime trigger (prime-a2345-a91b2.md "Commands"): `4a0b` and the first of its 10 `4303` pushes, the rest 1 s apart as a link event; a `420b` mid-burst sets the count back to 10.
- Factory reset (`Profile.factory_reset`): the A2345's `4201` acks `00`, clears every set value back to the recorded frames and forgets every enrolled token, then drops the link after the MCU's 10-tick debounce (1 s, checked every `push_period`); the next `0027` needs the button again (prime-a2345-a91b2.md "Commands" `4201`).
- Routing: a session request's `a1` route and the fid-scoped opcodes follow anker-crypto-and-negotiation.md "Frame" (its `a1` routing table and channel list) and a1783-control.md "WiFi provisioning": the module answers its own ops on the arrival port on the fids its handlers serve, relays to the MCU only a request routed from BLE to the MCU on fid `0x0f`, drops one with no route, an unknown source or an unhandled destination, and answers a logging-channel (source `a`) request itself with `00`. An MCU request on fid `0x11` or `0x13` draws no reply, and every MCU frame on the BLE link is routed `a1 31`.
- Relay: post-authorization requests go to the MCU script; its cleartext replies and pushes are encrypted for the session and sent on `03010f`. A command the product's layout handles with no recorded reply gets `<status> a1 01 31`: `00` when the layout's validator accepts its values, `04` when not.
- Command table (`Profile.known_commands`): a request nothing recorded or modeled answers gets the firmware's own answer from the product's table, an ack with its status or no reply; a request past the table's last op gets `past_table_status` (none: dropped); anything else is dropped. The C Gen 2 display board answers by a1783-control.md "Command map": `4051`/`4059` ack `00`, `4051` restoring as "`4051` factory defaults" gives it (the four per-region values keep the unit's own); `4065` / `4066` serve the header chunk alone as "BLE log upload (`4065` / `4066`)" lays it out by the `f9` MainMcu version (`READ_REPLIES` builds a read's own fields; the slots no frame reports are its constants), any later chunk getting no data; `4064` before an OTA start and every op outside the table are dropped. The Prime MCUs ack every real handler `00`, op past the table included, say nothing to their no-op stubs, and drop an op below `0x200` they don't handle inline (prime-a2345-a91b2.md "Commands"). Two A2345 handlers answer by branch: `4212` and an accepted `4222` send nothing, while a `4222` without `a2`, or a `420d` whose `a2` isn't typed `02`, gets `04` (`SILENT` marks a layout command whose accepted request goes unanswered). A `4222` of 0 or 1 sets the `4a02` `a6` switch; a nonzero `420d` draws a `0305` with trigger 0. The A2345's `4218` answers each USB-C port's offered power-sharing budget, looked up by which USB-C ports are active and whether a USB-A port is (prime-a2345-a91b2.md "`4218` field5 power-sharing budget"), then each USB-C port's `0303` output status. The A91B2's `4202` answers with the snapshot's `ac` byte (screensaver switch and theme), the field its `4205` writes (a theme past 2 stored as 2), then the clock.
- Setter replies and pushes from captures: a layout's `ECHOES` name the request fields an accepted ack carries back after its `a1` (the Prime port setters `4207`/`4208`/`4209`: the port, `4208`'s slot, and the clock, the request's standing in for the device's). Its `FOLLOW_UPS` are the pushes an accepted command can draw, each built from the request and the device's state before and after it (`McuScript.state`: every named value the recordings carry, the set values over them), or skipped when the change doesn't trip it; a push ends with the request's `fe`. Its `SIDE_EFFECTS` are further values a command sets from that state (`4208`'s conflict-clear). A refused command gets the bare `04` ack and no push.
- Prime pushes: `0302`, `0307`, `0308` and the A2345's `030f` go out on the changes prime-a2345-a91b2.md "MCU pushes" gives them, `0308` before the `4208`'s ack (`LEADING`). A once half's weekday comes from the date the MCU stores off the wire, which the emulator doesn't keep: two once halves count as one day, and a once half never meets a repeating one.
- Prime timed events: a pushed timer frame ends with the device's UTC epoch as its `fe`, a command's pushes with the request's. On the A2345 a change of `charging_mode` (a `4206`, `420c` entry, or `set_values`) sends `030d` after the mode-apply settle and drops the port blocks while the ports renegotiate, as "MCU pushes" `030f` and "Commands" `4206` give them (3.3 s, 8 s); `420c` entry is assumed to share the path. Each block then gets back its set value, else its recording; one set during the window keeps that value, and a further mode change in the window keeps the one window.
- Prime countdowns: an armed `4209` countdown ticks once a second into the values, so every frame (a mid-countdown `4a00` included) reads it as it stands; arming, re-arming or setting the remaining time restarts the count, and a disarm drops the pending expiry. The expiry is the firmware's, with its `0302` / `0307` as "MCU pushes" gives them. The A91B2's timer is assumed to send `0302` only on a change, as the A2345's watcher does, though its `4207` reports every write.
- Prime timed tasks: an enabled `4208` half fires at its hh:mm on its weekdays by the local RTC, so a clock set re-times it; the firmware's per-minute run switches the port with `0302` on a change. A once half fires at its next hh:mm, since the emulator doesn't keep the stored date, and is then disabled and reported in `0308` en 00 ("MCU pushes" `0308`). Disabling or rewriting a half drops what was queued.
- A2345 owner (`420a`): the recorded `4a0a` answers every send, and an accepted one acts as prime-a2345-a91b2.md "`420a`" gives it (the change detector, the custom theme back to 0, custom mode 5 left for the last mode below 5). The owner and that last mode are hidden (`_owner`, `_last_mode`, 1 unset); a fresh device has no owner, so its first `420a` counts as a change. The mode change reports `030d` and renegotiates the ports like any other. `4211 a2` 0 in mode 5 leaves custom mode the same way; `4211 a2` 1 has no documented effect and changes nothing.
- A2345 screen reports: a setting changed on the unit (`set_values`) sends its report at once as prime-a2345-a91b2.md "Screen reports" gives it, without the optional `a3` (none recorded) except `030b`'s theme id, as recorded; the same change from an app command sends only its ack.
- A2345 USB-C device identity (prime-a2345-a91b2.md `bd`/`be` rows, "`bb` Maximum Compatibility", "AI device identity (`be`)"): `A2345.plug(port, vid, pid, ext=None)` plugs a device into USB-C port 1-4, setting its attach flag (`pdN_output_status`); `unplug(port)` clears the flag and the port's power. Any change of an attach flag sends `0304` at once (none recorded; assumed `a2 03 03 <u16 LE bitmask>` plus `fe` in the `0300` bitmap's order). The identity reads follow those sections: `bd` (`pdN_device_vid`/`_pid`) 4 s after attach with `bb` 1 and `be` (`pdN_device_class`/`_code`) 1 s later, the `bb` 0 placeholders, the 6 s re-read when `bb` turns 1, the class and code tables (`05ac:7800` to none). A port identified before `bb` turns 0 keeps its identity, and a detach clears `bd`/`be` at once and drops a pending read. `ext` is the extended identity word a revision 4 or later PD controller reads (in no frame; `None` for an older controller, read as `ffff`), picking a PID's variant row as "AI device identity (`be`)" gives it.
- A2345 theme images: the theme commands answer as prime-a2345-a91b2.md "`4311` theme image state", "Theme upload" and "Theme image display" record them (what a `4205` needs, the `4311` states, the `4220` kinds, the `4221` index, window and CRC rules and their `4a21` answers, the custom cipher, the draw's checks); those facts aren't repeated here. SolixBLE #87's upload as it was run against the emulator is [solixble-theme-upload.md](solixble-theme-upload.md); `tests/test_a2345_theme_upload.py` replays its frames step by step, padded and unpadded, with the departures (a window re-sent after a lost reply, a second `4220` mid-upload, chunks after a finished upload, a `4220` CRC off the photo). How the emulator holds them:
  - `4205` (`_theme_staging`, `_theme_selected`): a stored slot (hidden `_theme_crc_<id>`, `_theme_size_<id>`, `_theme_kind_<id>`, `_theme_image_<id>`) shows at once; any other id is staged (hidden `_theme_staged_id`) with WiFi down, or fetched with WiFi up.
  - `4220` / `4221` (`_prepare_upload`, `_upload_step`, `_upload_answer`, `_upload_done`): the open upload is held in hidden `_upload_*` values, and each accepted chunk is written as flash keeps it, a custom photo through the real AES-128-CBC stream rather than a "last chunk % 16" rule, so any chunk size that breaks the chain fails its draw as on the unit while the upload's own replies don't see it. `4311` 1 goes out before the last `4a21` (`LEADING`) and carries no clock (`UNCLOCKED`). With no `4220` since boot a chunk gets no reply, as "Theme upload" gives it; the chunk 0 a unit then writes at external-flash offset 0 isn't modeled, the emulator keeping slot images rather than a flash image.
  - The draw (`_draw`) runs whenever an image is shown: at the upload's end, a `4205` for a stored slot, and a `4222` change on screen 5 (hidden count `_screen_draws`). A failing draw erases the slot (record and bytes) and drops `af`'s index to 1, the id kept (bench 2026-10-30: `af` `c1 a68adf5a` after the unpadded photo). An image whose bytes the emulator doesn't hold (self-fetched, or the recording's) draws as shown. `4222` (`set_time_display`, `4a02 a6` `time_display`) stores the flag and redraws only on a change of value and only on screen 5.
  - With WiFi up an image not stored is self-fetched: no `0311` follows the ack, then `0311` 2 at 0.38 s, 3 at 1.73 s and 1 at 8.6 s after the `4205` (as recorded), all published at `64`, and with the 1 the image is stored and shown. The emulator fetches no bytes, so the image always passes. A network or custom `4205` while a fetch is busy changes nothing and draws `0311` 0 with its own id and kind; the fetch goes on.
  - `4212` (the holiday theme, prime-a2345-a91b2.md `4212` row and "Theme upload") never replies and pushes no `0311`; a request missing a field changes nothing. With WiFi up the device fetches the image at once (kind 1); with WiFi down the request is dropped and nothing stored. No message marks the image landing, so the emulator lands it 8.6 s on, the recorded network self-fetch's time, and treats the CRC as matching since it fetches no bytes. The landed record (hidden: the id, `_holiday_crc`, `_holiday_a4` (role unread), `_holiday_start` / `_holiday_end` as sent, the URL) also captures the stored `420a` country. `a2 = 0` erases the slot record but doesn't cancel a fetch in flight, which still lands afterward and writes the record again (the firmware's race). A WiFi drop mid-fetch doesn't stop it either: the module resumes at its saved offset and the image lands on time; the retry budget running out (op `0x3d` status 3, no valid record, silent for kind 1) isn't modeled. The holiday theme shows while the holiday switch (the reply's own `a2` bit 6) is on, the record's country is the current `420a` country and the local RTC lies inside [start, end], the bounds read as `[year - 2000, month, day, hour, min, sec, -]`; then `4a02` carries the fetch URL in `a4` and `a5 02 01 01` after it. A later `420a` country change, the switch off or the erase hides it.
- A2345 Secret Features: the triggers, cooldowns and send order of prime-a2345-a91b2.md "Secret Features", its counters RAM-only and in no frame. A main-tile focus is `unit_event("switch_screen")`; a nonzero `420d` triggers 0, the prompt. Not modeled: the on-device mode menu and the re-apply on entering Port Priority (for Feature Expert), the overlay, and the PD codes that also raise Power Expert's high-voltage class (the class comes from the port's voltage).
- Prime link state: `set_wifi(up)` on the A2345 and A91B2 sets link-state bit 1, BLE being the link itself; WiFi coming up sends `0301` (the snapshot's `a2`, as recorded). With WiFi up each push goes where prime-a2345-a91b2.md "Push routing" sends it, a layout's `sends` keeping it off the BLE link (replies stay); `mqtt_routed` gives each push's MQTT copies with their `a1`, and the module publishes them to the outbox (below). `420a` also stores its country, uppercased. The two periodics (`0300` on both, `0312` on the A2345) publish as "Periodic pushes" gives them; the MCU's timers free-run from boot, but here each starts a full period after WiFi comes up and stops when it goes down. Every `0312` is published; the cloud keeping about one an hour is outside the device.
- Cloud: `set_cloud(True)` puts the device on WiFi to the cloud, where it has no BLE link: the open link drops and connecting fails until `set_cloud(False)`. There `mqtt_frame(msgtype)` returns the plain `ff09` frame (`03 01 0f`, no link flags) the C Gen 2 unit publishes to MQTT, built from its state: the `param_info` messages (`0421`, `0489`, and the `0900`, `0889` and `0892` replies) at `a1 34`, and the `state_info` events (`0425` where the model sends one, `0503`) at `a1 12` (a1783-telemetry.md "MQTT channel routing"). Nothing goes out on a link. It raises off the cloud and for any other msgtype, `0490` included (an HTTPS upload, not MQTT). `0503`, the lifetime energy and TOU-time totals, is cloud-only, never a BLE push, and builds only while a TOU period is active (the cloud `0421`'s `d9[0]` non-zero; a1783-telemetry.md "0503"): outside one `mqtt_frame(0x503)` raises. Its values are set by name like any other (`battery_to_load_energy`, `peak_time`, `time_save`, ...), and the layout's `started` 10 s usage pass adds to them: each pass while a TOU period is active adds 10 s to that type's time (hidden `<total>_delta`, counted in the hidden `tou_usage_passes`), every 120 passes fold the deltas into `peak_time` / `mid_peak_time` / `off_peak_time`, and pass 720 (2 h) starts the count again and publishes the `0503` to `mqtt_published`, its `time_save` the RTC rounded down to the minute (a1783-telemetry.md "0503" Trigger); off the cloud the pass publishes nothing. The energy totals need the pack's charge power, which no value models, so they change only by name.
- MQTT outbox: `device.mqtt_published` lists what the device published to MQTT on its own, in send order, as (msgtype, plain `ff09` frame). Any push a layout's `sends` holds off BLE (a timed push, a follow-up, a burst's first push, `device.push`) goes through the layout's `mqtt_routed`, and its copies land there; the base layouts publish nothing for a held push. A timed step can also publish straight to MQTT (`Step.published`, cleartext with its MQTT `a1`). Publishing needs no BLE link, but a push a clock jump bypassed publishes nothing. Replies always go out on BLE. `mqtt_frame` stays for messages built on demand.
- Values: `set_values(name=value)` sets a telemetry field on the device: every later frame that carries the name, recorded or built, sends it. Names are the Anker app's in snake_case (`reference/app-names.md`); a device the app's logs don't cover takes the app's name for the same field on the closest equivalent hardware. The C Gen 2 line's `0490` push's names are listed in `devices/data/c490_fields.json` (path → name), and the ones it shares with `0421`/`0900` (`battery_level`, `ac_output_power`, `pv1_input_power`, and `sub_package_battery_level` on the models with the expansion port) are the same reading in both. One name on several tags (`a4[23]` and `d9[3]` are both `charging_limit_value`) sets them all.
- The `0490` push: a periodic push, not a summary (most fields are live reads at post time). Its payload is `a1 01 31`, `a2` (2-byte length, type `04`, a nanopb message), then the schema name in `a3`. `c_g2_490.py` walks the message and rewrites named leaves (varint, zigzag varint, fixed bytes at their recorded length), so one with nothing set is the recording byte for byte. `.14` and `.15` always hold two pack entries; on a model with no expansion (`Profile.expansion`) the second entries and the expansion's SoC (`.23.1#1`) start at zero. It goes out every 540 s on one grid from the display board's start (the layout's `started` timer), which neither a stop, the switch nor the link resets: 2026-10-07 20:34:08 → 22:40:07 is 14 × 540 s, 2026-09-19 04:48:33 → 18:54:34 is 94 × 540 s. A post goes out only while the hidden `device_point_switch` (the module's cloud device-point switch, no app name; on unless set) is 1; otherwise it is missed (a1783-telemetry.md "When the display board posts c490"). A post that falls due with no link up (no authorized BLE link, and not bound and on WiFi through `set_cloud`, where it is uploaded, not modeled) stays pending (hidden `c490_pending`): every 9 s accumulation queues it until one finds a link, and the next post is back on the 540 s grid, so an off-schedule post comes only when a boundary falls inside a link gap (firmware/mainmcu.md "c490 gates and cadence"). A `4057` stop (`a2 = 0`) turns it off, and a start or re-send leaves it off ("What stops and restores c490"). The cloud fetch and WiFi re-provision that restore it aren't modeled, so only `set_values(device_point_switch=1)` does. Not modeled either: a MainMcu reset restarting the 540 s phase (a1783-telemetry.md "c490 counters"; the emulator has no MainMcu reset). Each attached pack's counter page (`.14.25` / `.14.26`, a1783-telemetry.md "`.14.25` / `.14.26` pages") turns 0-3 every 360.1 s from the start (3 601 calls at 10 Hz, firmware/c490-schema.md `page_index_get`), so 540 s posts land 1.5 pages apart; `.14.26` is the page's second counter in whole hours. The four counters start at the recording's hours and count on; their zeroings (charge end, full charge, the OCV recalibration) aren't modeled.
- Commands shown in telemetry: an accepted command's validator (the layout's `COMMANDS`) returns the telemetry values its request sets, and its `SIDE_EFFECTS` any further ones from the device's state; each is set in every message that carries the name, before the reply and the telemetry that follows are built. A rejected command sets nothing. Its reply's status is `04` on an MCU that rejects (the Prime MCUs), whether or not the reply is recorded; the C Gen 2 display board acks every setter `00` (`fid0f_ack_reply`), so there a rejected setting is acked and left unapplied, as the A1783 does with a setting it can't read (`a2 01 01`, no type byte).
- MCU: `device.mcu` is the script; `use_mcu(script)` replaces it (`McuScript()` for a quiet MCU), `set_reply(request, (msgtype, cleartext), ...)` sets a request's answer (none for silence), and `set_push(msgtype, cleartext)` sets a push.

## Recorded data

MCU replies and pushes are recorded cleartext from real units, packaged as `devices/data/<pn>.json` (msgtype → cleartext hex) by `tools/sanitize_frames.py`; a profile lists its files, and the first that holds a msgtype supplies it. The tool reads collector logs and MQTT records (anker-solix-api `.ndjson` examples, `mqtt_monitor` dumps). An MQTT frame is the same frame the MCU sends to BLE with another routing marker in its leading `a1` (`34` or `32` for `31`), which the tool sets back to `31`; `--fix-checksum` recomputes the checksum of records whose serial was anonymized after capture. Sources are listed in [device-sources.md](device-sources.md). The tool takes the real identifiers on its command line, never stores them, and fails on any printable run it wasn't told is safe. The frames are sanitized before they enter the package: the serial, MAC, expansion serials, account tokens and device clocks are replaced with synthetic values of the same length, and the frames are re-encoded. The fixed handshake frames (`4801`, `4803`) are reproduced byte for byte; frames that carry the serial or MAC match a real capture everywhere except those fields.

## Live values

Off by default, so every frame is the recording with the set values over it. The A2345 and A91B2 have tables (`a2345_live.json`, `a91b2_live.json`: the `0303` and `4a00` port blocks). `device.vary_live_values(seed)` turns it on with `random.Random(seed)`; `vary_live_values(None)` turns it off. Only a device with recorded live values has a table (`Profile.live = LiveSource(table, period)`); any other raises `LayoutError` naming the device, as does a table that names a field the device sends in no message.

- Tables: `devices/data/<pn>_live.json` (compact JSON), built by `uv run python tools/build_live_tables.py <survey dir> [--only <PN> ...]` from the frame survey's per-device JSON. A match key one message records at a single value carries to the same-named group of a message whose frame lacks it, at that value: the Prime port relays (`pdN_relay_switch`, the A2345's shared `usb_relay_switch`) are in `4a00` only and read 1 in every recorded frame, so a port switched off with `4207` matches no sample and idles in `0303` too; a key that would carry but was recorded at more than one value is refused. Per message it keeps the groups (fields that move together, like a port's status, voltage, current and power: their `live` fields, the idle values of those, the rest as match keys, any further match keys from outside the group's field (`match`, an AC input's switch and status), and the recorded samples with their counts), the groups recorded active together (`active_sets`), the totals that held in every frame, the paired draws (fields recorded beside a given tuple, like a pack current beside a total), the slow fields' steps, range and interval (the survey's median time between recorded steps; a slow block without one is refused), and `remaining_time` split by output idle and active. Counters, the totals that didn't always hold, and identifier fields are left out; a table holds numbers only, apart from the match wildcard below. A survey of a device the emulator doesn't have is refused, as is a table that draws (a group's live field, a total, a paired field, `remaining_time`) a field the device's layout derives from others (`LayoutProtocol.derived`, empty by default); a derived slow field is left out with a note, since the layout works it out from the field it follows, and a derived field may still be a match key. The survey's `mirrors` (names that are one state value here) are ignored. Samples are read by their column names (`sample_columns`, `sample_columns_short_a4`), summed over `transport`: the BLE and cloud frames come from one state. A sample list the survey hasn't cut (no `dropped` / `dropped_short_a4`) is cut after that sum: every idle tuple stays, and the active ones, commonest first, until they cover 99 % of the group's active frames (`COVER`), the one that reaches it included; a tie goes to the lower tuple. A named section (a joint table, like the A1783's `ac_charge`) and a `0490` section of a schema the emulator doesn't send (it sends `_0009`) build nothing, with a note. A C Gen 2 frame whose `a4` has no byte 31 (26 B) comes from firmware without Battery-Only Power, which first appears in v1.2.1.6 (a1783-telemetry.md:153, :553). Those samples (`samples_short_a4`) keep the match keys the frame carries (`match_short_a4`); the emulated v1.2.1.6 lets them draw only with `ac_input_disable_switch` at 0: a modelling choice that takes that firmware's AC behaviour as Battery-Only off, not a recorded switch state. They merge into the group's samples, a tuple both hold adding its counts. The AC charge limits govern the AC input, not the AC output: a sample whose `ac_input_power` is idle takes `*` (`live.ANY`, which matches any state value) on `ac_recharge_power`, `silent_recharge_power` and `super_fast_charge_status` (the builder's `INPUT_ONLY`), and such samples merge. The DC input's group (`pv1`) also matches on the hidden `dc_input_source` (0 solar, 1 car socket; the app has no name for it, and its `carChargerInputPower` reads the same XT-60i value as `pv1InputPower`). A plugged-in sample (`pv1_charge_status` 1) takes the source of the era its days (`a8_by_day_local`, America/New_York) fall in, by the owner's era table for the XT-60i: 2 × PS400 solar before 2026-08-08, the car-socket adapter from then. One with nothing plugged in (status 0) takes `*`. A plugged-in sample with no day, or with days in both eras, is refused. Each frame sample counts 2 s, the collector's poll. The solar samples come from the `_0005` `0490` posts' `.23.5` (the DC input's register, as `a8[1:3]`; `dc_in_by_day_local`), each counting 540 s, the push interval: longer gaps are missing posts. A day the frames also cover keeps the frames and skips its posts. A day with no post above 0 W had nothing plugged in and gives no samples: on 07-21 to 07-23, inside that week of 0 W posts, the device's own frames read `pv1_charge_status` 0. Every other post is status 1, 0 W included (night with the panels in): the emulator's choice, since a post carries no status. A post on a car-socket day the frames don't cover is refused. The `_0009` posts aren't a source: their days are car-socket ones the frames cover more finely. The group draws on its own (`independent`), out of the active sets.
- When: a frame is built (a push the device sends on its own, a timed event's frame, an answer to a request, `device.push`, `mqtt_frame`) after at least one telemetry period has passed since the last draw, and the device draws first. Turning it on draws at once, and draws fall on a period grid from there, so frames built within one period share a draw and the same seed with the same clock steps gives the same frames. The period is the device's stream period: 1 s for the Prime `0303` (`REALTIME_BURST`).
- A draw, per message in table order: pick an active set by its count, leaving out groups with no drawable sample (an active group draws a sample whose match keys equal the device's current values, so a port switched off stays idle); each active group takes its sample, every other group its idle values; an independent group isn't in the active sets and takes one of all the samples matching the current values, idle ones included, so it is active as often as it was recorded active given its match keys; totals sum the drawn fields; a paired draw takes a tuple recorded beside the current given values, or holds the fields (`unpaired`); each slow field takes one recorded step per interval passed since its last step (each on its own clock, the remainder carried, so a `0490` field recorded 540 s apart steps every 540 s whatever the draw period), clamped to its recorded range; `remaining_time` comes from the output-idle split when `total_output_power` is 0, else the output-active one. After each message the layout's `derive` gives the values that follow from the state (`LayoutProtocol.derive`, none by default), which a later message's draw reads; they are never part of the draw. A field an earlier message drew isn't drawn again, so a name in two messages (`pd1_output_power` in `0303` and `4a00`) is one value. A group with a pinned field isn't drawn at all, so its fields stay one recorded sample's. Values come from the recorded frequencies as they are.
- Drawn values go the way `set_values` sends them: into every frame that carries the name, with the layout's implied values, and the timed events the change starts run before the frame is built. A value given to `set_values` is pinned and a draw never changes it; implied values and those a timed event sets aren't.
- C Gen 2: the A1783 has a table (`a1783_live.json`). From `0421`/`0900`, one section: the port groups (AC in and out matching the Battery-Only switch, the AC status, `ac_recharge_power`, `silent_recharge_power` and `super_fast_charge_status`, the last three on the AC input only, so a limit never recorded still draws AC output but never AC input; DC in on its own: plugged in, the car socket drew power in 2 236 of the 2 282 frames the table keeps (121-129 W), the solar panels in 433 of 1 002 Pennsic posts (1-486 W), and `dc_input_source` reads 1, the car socket, while unset (`LayoutProtocol.defaults`: the values hidden inputs read while unset, none by default); PD1-PD3, USB-A, the car socket, the alternator charger), the output total of all seven port outputs, the temperatures and WiFi signal, and `remaining_time`. From `0490`: each pack's SoCs, estimators, reserve and voltages, and its pack currents and pack-side powers paired with `.23.4` / `.23.2` / `.23.7`. It draws every 1 s, the `c421` stream's period (`c421_change_tick`'s 1000-tick timer, a1783-control.md `4057`); the slow fields drift by their recorded steps per recorded interval, counted on the device clock whatever the client's poll rate. The `0421`/`0900` steps were recorded per collector poll (median 2 s, the collector's `runtime.poll_interval_s`; the log cadence follows the poll), so they apply per 2 s elapsed; the `0490` ones per post, 540 s. The A1763, A1765 and A1785 have no recordings and refuse. The `0421`/`0900` section comes first, so the names it shares with the `0490` (the output total, AC output, DC input, `remaining_time`) are one value, and the `0490` posted in a period carries that period's. The flow state, the battery levels and `.23.4` aren't drawn: the layout's `derive`, the same derivation its changes run, hands them to the draw after each section, so the `0490`'s paired tuple is looked up against this period's totals, and a pack current a pair draws stays in that change.

## Layouts

Each product's commands and telemetry are hand-written in its own device module as a layout class satisfying `LayoutProtocol`, passed as `Profile.layout` (`CGen2Layout` in `solix_c_gen2.py`, `A2345Layout`, `AS220Layout`, `A17C0Layout`, ...). A layout builds on `parameters.py`: `TableLayout` for a recorded device, which declares per message its typed blocks (`FIELDS`: tag -> codec, type byte, field zeros) and its repeated blocks (`GROUPS`: one codec at several tags, a port or a timer per tag), with five hooks for the rest (`timed` gives the timed events a change of values starts; by default none, the C Gen 2 mains and Battery-Only sequence, the car socket's USB-C re-attach, the output timers and the low-SoC `0403`s, the screen wake and timeout, and the backup windows; `sends` says whether a push goes out now: by default always, a C Gen 2 `0490` only with the device-point switch on; `implied` gives the values a set value implies, the C Gen 2's stored TOU plan from `tou_periods` and AC input 0 W with no mains; `finish` reshapes a frame once its fields are written: a grid-loss `0425`, and the C Gen 2 `d9` active period and the AC-charge hold of Peak and of Battery-Only Power; `publishes` says whether a message goes to MQTT in the current state, given any other message's cloud payload; by default always, a C Gen 2 `0503` only while its `0421` reports an active TOU period); `ScalarFieldLayout` for a flat run of single-value fields (the Solarbank `0405`); and `CommandDispatchLayout`, whose `COMMANDS` map a msgtype to a validator that returns the telemetry values an accepted request sets (`{}` for none), or `None` to refuse it. Every request field and every block is a construct `Struct`; a TLV field's length byte is always rebuilt from its value, never written by hand.

A field's tag, type byte and width come from real evidence: a recorded frame, checked by the product's tests, or a cited client's decode. Bytes nothing names stay as recorded, and a rebuilt field keeps them. A product without a layout answers only its recorded requests.

anker-solix-api's maps, hand-transcribed from its `mqttmap.py`, sit in `reference/anker-solix-api-maps/` as reverse-engineering reference for writing a layout. Nothing loads them at runtime.

## Testing

The package's own tests do not depend on any client library:

- known-answer tests: the fixed handshake frames, recorded cleartext round trips, fragment layouts;
- a client-side fixture that drives real `bleak.BleakClient` through the backend and performs the client half of the handshake.

Client libraries (SolixBLE, through its `MockDevice` adapter) test against the emulator in their own suites.

[SolixBLE theme upload](solixble-theme-upload.md) keeps the script SolixBLE #87's A2345 custom-theme upload was run with against the emulator, as a record of how to replicate it.
